# 第七章 面向对象技术

## 1. 面向对象核心概念与设计原则

### 面向对象三大特性与绑定机制
- **封装（Encapsulation）**：将数据和操作数据的函数捆绑在一起，对外隐藏内部实现细节，提供公共访问接口；
- **继承（Inheritance）**：子类自动拥有父类的属性和行为，支持代码复用与层次建模；多重继承易引发“菱形继承”同名成员二义性；
- **多态（Polymorphism）**：同一操作作用于不同的对象可以产生不同的解释和执行结果。

#### 方法重载（Overload）vs 方法覆盖（Override）
| 对比维度 | 方法重载（Overload） | 方法覆盖 / 重写（Override） |
|---|---|---|
| **定义范围** | **同一个类**内部 | **父子类继承关系**之间 |
| **方法名与参数** | 方法名必须相同，**参数列表必须不同**（个数、类型或顺序） | 方法名、参数列表、返回值类型**必须完全相同** |
| **多态类型** | **编译时多态（静态多态）** | **运行时多态（动态多态）** |
| **绑定机制** | **静态绑定（早期绑定）**，编译阶段确定调用版本 | **动态绑定（晚期绑定）**，运行阶段根据对象实际类型分派 |

#### Cardelli 多态四大分类体系
1. **通用多态**：
   - **参数多态（Parametric）**：结构中包含类型参数，同一代码段可适用于多种数据类型（如 C++ 模板、Java 泛型）；
   - **包含多态（Inclusion）**：同一操作可用于一个类型及其所有子类型（如子类重写父类虚方法并向上转型调用）；
2. **特定多态（特殊多态）**：
   - **过载多态 / 重载多态（Overloading）**：同一个名字在不同的上下文中代表不同的含义（如函数重载、运算符重载）；
   - **强制多态（Coercion）**：编译程序通过隐式类型转换自动变换操作数类型（如整型自动转为浮点型参与混合加法）。

### 面向对象 7 大设计原则
1. **单一职责原则 (SRP)**：类的职责要单一，一个类应该仅有一个引起它变化的原因；
2. **开放-封闭原则 (OCP，核心)**：对扩展开放，对修改关闭。通过增加子类实现新功能，而不修改已有稳定代码；
3. **里氏替换原则 (LSP)**：子类型必须能够透明地替换掉它们的父类型，且程序原有逻辑不被破坏；
4. **依赖倒置原则 (DIP)**：高层模块不应依赖低层模块，二者都应依赖抽象；抽象不应依赖细节，细节应依赖抽象；
5. **接口隔离原则 (ISP)**：客户端不应被迫依赖它们用不到的接口；建立小而专门的接口，比建立庞大的复合接口好；
6. **迪米特法则 / 最少知识原则 (LoD)**：一个对象应当对其他对象有尽可能少的了解，只与直接朋友通信；
7. **合成复用原则 (CARP)**：优先使用对象组合/聚合，而不是通过继承来实现复用。

## 2. UML 图分类体系与建模要素

### 高频 UML 图分类速查

| 图分类 | 图名称 | 核心建模视角与重点 | 典型应用场景 |
|---|---|---|---|
| **结构图（静态）** | **类图 (Class)** | 类的内部结构（属性、方法）及类间静态关系（泛化、实现、关联、聚合、组合、依赖） | 领域分析、系统设计架构 |
| | **对象图 (Object)** | 某一时点上类的实例（对象）及其关系的**静态快照** | 复杂数据结构验证、特定场景实例测试 |
| | **构件图 (Component)** | 软件构件（组件、模块、包）之间的组织与接口依赖关系 | 物理软件单元划分、接口规范 |
| | **部署图 (Deployment)** | 软件构件在物理计算节点（硬件、服务器、网络）上的配置与分布 | 拓扑网络部署、微服务环境拓扑 |
| | **包图 (Package)** | 模型元素的逻辑分组与依赖关系 | 模块划分、大型系统分层结构 |
| **行为图（动态）** | **用例图 (Use Case)** | 展现外部参与者（Actor）与系统功能（Use Case）间的交互边界 | 需求分析、功能边界确定 |
| | **活动图 (Activity)** | 业务工作流、操作流程、算法控制流，支持分支与**并发（泳道图）** | 业务流程建模、用例详细流程分析 |
| | **状态机图 (State)** | 单个反应型对象在其生命周期内因外部事件引发的状态迁移序列 | 生命周期复杂对象（订单、售货机、协议状态） |
| | **交互图 - 序列图** | 强调消息传递的**时间顺序**（对象生命线、激活期、时序消息） | 用例场景实现、对象协作时序追踪 |
| | **交互图 - 通信图** | 强调协作对象之间的**结构组织拓扑**（带编号的调用链，原名协作图） | 查看参与交互的对象网络布局 |

> **特别辨析**：对象图是某一时刻对象实例及其关系的静态快照；注意与类图的类间静态关系（关联、组合等）区分。

### 类间 6 大关系判断准则（耦合度由弱到强）
`依赖 (Dependency) < 关联 (Association) < 聚合 (Aggregation) < 组合 (Composition) < 泛化 (Generalization) / 实现 (Realization)`
- **依赖**（虚线箭头）：方法内部临时使用对端对象（局部变量、参数、静态方法调用）；
- **关联**（实线）：类成员变量长期持有对端引用；
- **聚合**（空心菱形在整体端）：弱“整体—部分”关系，**部分可以独立于整体存在**（如学校与老师）；
- **组合**（实心菱形在整体端）：强“整体—部分”关系，**部分不可独立存在，同生同灭**（如窗体与文本框、公司与部门）；
- **泛化**（实线空心三角）：子类继承父类；**实现**（虚线空心三角）：类实现接口。

## 3. GoF 23 种设计模式分类与意图口诀速查

### 创建型模式（5 种，关注对象创建过程）
1. **工厂方法 (Factory Method)**：定义创建对象的接口，让子类决定实例化哪一个类；
2. **抽象工厂 (Abstract Factory)**：创建**一系列相关或相互依赖的对象（产品族）**，无需指定具体类；
3. **单例 (Singleton)**：确保一个类仅有一个实例，并提供全局唯一访问点；
4. **生成器 / 建造者 (Builder)**：将复杂对象的**构建与表示分离**，使同一构建过程可创建不同的表示；
5. **原型 (Prototype)**：通过**拷贝/克隆原型实例**来创建新对象（用于简化大对象的重复创建）。

### 结构型模式（7 种，关注类和对象的组合）
1. **适配器 (Adapter)**：将一个类的接口转换成客户期望的另一个接口，消除接口不兼容问题；
2. **桥接 (Bridge)**：将**抽象部分与它的实现部分分离**，使它们都可以独立变化（多维度变化）；
3. **组合 (Composite)**：将对象组合成**树形结构**以表示“部分—整体”层次，统一处理单个对象和组合对象；
4. **装饰器 (Decorator)**：**动态地给一个对象添加额外职责**（比生成子类更灵活）；
5. **外观 / 门面 (Facade)**：为子系统中的一组接口提供一个一致的高层接口，降低子系统外部的复杂性；
6. **享元 (Flyweight)**：利用共享技术有效支持**大量细粒度对象**的复用，大幅减少内存开销；
7. **代理 (Proxy)**：为其他对象提供一种代理以**控制对这个对象的访问**（远程代理、虚拟代理、保护代理）。

### 行为型模式（11 种，关注对象间的通信与职责划分）
1. **责任链 (Chain of Responsibility)**：使多个对象都有机会处理请求，将这些对象连成一条链沿着链传递；
2. **命令 (Command)**：将**请求封装为一个对象**，支持请求排队、撤销/重做、日志记录；
3. **解释器 (Interpreter)**：定义语言的文法及其解释器，解释特定语法的句子；
4. **迭代器 (Iterator)**：提供一种方法顺序访问一个聚合对象中的各个元素，**而不暴露其内部表示**；
5. **中介者 (Mediator)**：用一个中介对象封装一系列对象交互，**将网状依赖解耦为星状依赖**；
6. **备忘录 (Memento)**：在不破坏封装性的前提下，**捕获并保存对象的内部状态**以便日后恢复；
7. **观察者 (Observer)**：定义对象间的一对多依赖关系，**当一个对象状态改变时，所有依赖者都自动得到通知并刷新**；
8. **状态 (State)**：允许一个对象在**其内部状态改变时改变它的行为**，对象看起来似乎修改了它的类；
- **避坑提示**：当看到“对象按当前内部状态处理请求并在状态改变时改变行为”时，应判定为状态模式，注意与状态机建模及网络协议状态区分。
9. **策略 (Strategy)**：定义一系列算法，**把它们一个个封装起来，并且使它们可以相互替换**；
- **避坑提示**：策略模式将算法族封装为可替换对象，Context 持有策略接口并委托执行；注意“多个算法可切换”属于设计模式中的策略模式，不等同于算法设计中的分治或动态规划策略。
10. **模板方法 (Template Method)**：定义一个操作中的算法骨架，而将一些步骤延迟到子类中实现；
11. **访问者 (Visitor)**：表示一个作用于某对象结构中各元素的操作，它使你可以在**不改变各元素类的前提下定义作用于这些元素的新操作**。

## 4. UML 建模要素精细规范：可见性、多重度与用例关系

### 类图可见性修饰符与多重度规范
1. **四大可见性修饰符（Visibility）**：
   - **`+` (Public / 公有)**：类内部、子类及外部任何对象均可自由访问；
   - **`-` (Private / 私有)**：仅在定义该属性或方法的**本类内部**可见，外部及子类均被屏蔽；
   - **`#` (Protected / 保护)**：仅在**本类内部及其所有派生子类**中可见；
   - **`~` (Package / 包内私有)**：在同一个包（Package）或命名空间内的其他类可见。
2. **多重度（Multiplicity）标准格式**：
   - 描述一个类的实例与另一个类的实例之间关联的数量对应关系：
     - `1`：表示恰好只有 1 个实例；
     - `0..1`：表示零个或一个实例（可选）；
     - `0..*` 或 `*`：表示零个到多个实例（任意数量）；
     - `1..*`：表示至少一个到多个实例；
     - `m..n`：表示从 m 到 n 个实例（如 `2..5`）。

### 用例图关系识别法则与箭头方向
用例图展现参与者（Actor）与系统用例（Use Case）之间的交互，用例之间的核心关系包括：
1. **包含关系 (`<<include>>`)**：
   - **语义**：基础用例（Base Case）在执行过程中**必须无条件调用**包含用例（Inclusion Case），抽取公共步骤；基础用例离开包含用例**自身逻辑不完整**；
   - **箭头方向**：**从基础用例指向包含用例（主指向辅）**；
2. **扩展关系 (`<<extend>>`)**：
   - **语义**：基础用例自身功能**完整独立**；扩展用例仅在满足特定扩展点条件时**可选触发执行**，用于扩充补充辅助功能；
   - **箭头方向**：**从扩展用例指向基础用例（辅指向主！）**；
3. **泛化关系 (Generalization)**：
   - **语义**：子用例继承父用例的所有特性，并提供更具体的业务实现；
   - **箭头方向**：实线空心三角箭头，从子用例指向父用例。

> **用例关系秒杀口诀**：
> “无则不能是包含（主指向辅），有则更佳是扩展（辅指向主）；泛化继承子指父。”

## 5. 高频相似设计模式成对混淆深度辨析

软考选择题极易将意图或结构相近的设计模式编排在同一题中考查：

| 成对对比模式 | 核心设计意图差异 | 驱动与控制机制对比 | 典型应用场景实例 |
|---|---|---|---|
| **策略模式 (Strategy) vs 状态模式 (State)** | • **策略模式**：封装一组**平行的可互相替换的算法族**<br>• **状态模式**：封装对象在**不同生命周期状态下的不同行为** | • 策略模式通常由**外部客户端明确指定**使用哪种具体算法<br>• 状态模式由**对象内部状态迁移自动驱动**行为切换，客户端无需关心内部状态 | • 策略：商城多种支付折扣算法（满减、八折、积分抵扣）<br>• 状态：订单生命周期（待支付、已发货、已签收、退款中） |
| **适配器 (Adapter) vs 代理 (Proxy) vs 装饰器 (Decorator)** | • **适配器**：**转换已有接口**以消除接口不兼容<br>• **代理模式**：**控制对目标对象的直接访问**<br>• **装饰器**：**动态透明地给对象添加额外职责** | • 适配器改变了原有接口形式<br>• 代理模式保持原有接口不变，控制访问权限或延迟加载<br>• 装饰器保持原有接口不变，增强原有功能 | • 适配器：三孔插头转两孔插头、旧日志库转新 SLF4J 接口<br>• 代理：权限认证代理、远程 RPC 代理、虚拟图片延迟加载<br>• 装饰器：Java I/O 流包装（`BufferedInputStream` 包装 `FileInputStream`） |
| **工厂方法 (Factory Method) vs 抽象工厂 (Abstract Factory)** | • **工厂方法**：针对**单一产品等级结构**，每个具体工厂只能生产一种具体产品<br>• **抽象工厂**：针对**多个产品族（相关联的一组产品）**，每个具体工厂能生产该产品族的全套产品 | • 工厂方法使用**类继承**，让子类决定实例化哪个类<br>• 抽象工厂使用**对象组合**，创建一系列相互依赖的对象 | • 工厂方法：只生产不同品牌的汽车（宝马工厂造宝马车，奔驰工厂造奔驰车）<br>• 抽象工厂：跨平台 UI 套件（Windows 工厂生产 Win 按钮和 Win 文本框，Mac 工厂生产 Mac 按钮和 Mac 文本框） |
| **桥接模式 (Bridge) vs 适配器模式 (Adapter)** | • **桥接模式**：在**系统设计前期**，将抽象化与实现化解耦，使二者可独立沿各自维度演化<br>• **适配器模式**：在**系统维护后期**，为复用已有类而解决接口不兼容问题 | • 桥接模式处理的是两个或多个独立维度的正交组合变化<br>• 适配器模式处理的是已存在的两个不兼容接口之间的粘合对接 | • 桥接：不同操作系统平台（Win/Mac/Linux）与不同图像格式（BMP/JPG/GIF）的跨平台绘制引擎<br>• 适配器：将第三方支付接口适配为系统统一的 `IPayment` 接口 |

## 6. 第七章核心易错陷阱防坑指南与做题检查清单

### 核心易错陷阱防坑指南
1. **用例扩展关系箭头方向画反**：
   - **陷阱**：误将扩展关系的箭头从基础用例画向扩展用例；
   - **避坑法宝**：扩展用例是指向基础用例的（**扩展用例 → 基础用例**），带 `<<extend>>` 构造型！
2. **聚合与组合生命周期混淆**：
   - **陷阱**：分不清空心菱形（聚合）与实心菱形（组合）；
   - **避坑法宝**：**实心同生共死（组合）**，部分随整体销毁而销毁（如公司与部门）；**空心各自分离（聚合）**，部分可独立存在（如学校与老师）。菱形始终位于整体端！
3. **策略模式与状态模式判定颠倒**：
   - **陷阱**：只要看到“行为改变”就选策略；
   - **避坑法宝**：看**触发条件**：根据不同算法逻辑由客户端选择是策略；根据对象自身状态流转自动改变是状态。
4. **单例模式多线程安全**：
   - **陷阱**：简单懒汉式单例在多线程并发环境下会导致创建多个实例；
   - **避坑法宝**：多线程环境下必须采用双重检查锁定（Double-Checked Locking）加 `volatile` 关键字，或静态内部类单例。

### 第七章做题自检检查清单
- [ ] 题干出现“名词短语/动词短语”时，先判断对象属性与职责，避免混淆分析和设计；
- [ ] 类图关系先看生命周期：临时使用是依赖，可独立的整体—部分是聚合，同生同灭是组合；
- [ ] UML 图题先锁定建模对象：需求用例、业务流程活动、消息时序序列、物理节点部署、组件依赖组件图；
- [ ] 模式题优先抓唯一意图：通知是观察者、状态切换是状态、封装交互是中介者、链式处理是责任链、对象共享是享元；
- [ ] 遇到设计模式辨析题时，紧扣核心意图与结构职责划分，注意区分结构型与行为型模式的边界；
- [ ] 用例图关系核对：包含主指辅，扩展辅指主。
