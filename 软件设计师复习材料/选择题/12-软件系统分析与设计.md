# 第十二章 软件系统分析与设计

## 1. 结构化分析方法：决策表结构、规则组合与化简法则

### 决策表（Decision Table）四大组成部分
1. **条件桩（Condition Stub）**：列出可能影响行动的所有判定条件；
2. **条件项（Condition Entry）**：给出各个条件在此规则下的取值（如 `Y/N` 或具体数值范围）；
3. **动作桩（Action Stub）**：列出可能执行的所有行动操作；
4. **动作项（Action Entry）**：指出在对应条件项组合下应执行的具体动作标记（如打钩或空缺）。

### 条件组合数与规则化简通用方法
- **初始规则总数计算**：
  若系统包含 k 个独立的判断条件，第 i 个条件有 m_i 个取值，则**最少初始规则组合数**为：
  初始规则总数 = ∏(i=1..k) m_i
  （若均为二值条件，则总组合数为 2^k）。
- **规则化简合并原则**：
  若两条（或多条）规则对应的**动作完全相同**，且**仅在一个条件上取值不同**（涵盖了该条件的所有可能取值），则可将这两条规则合并为一条，并将该条件项标记为“无关条件（-）”。

## 2. 数据库系统设计：概念模型集成与逻辑映射衔接

### 局部 E-R 图合并的三大冲突及其消除策略
在多部门或多用户视图分别设计局部 E-R 图后，集成全局概念模型时必须解决三大冲突：
1. **属性冲突**：
   - *属性域冲突*：同一属性在不同局部图中的类型、长度、取值范围或计量单位不一致（如工号一个是整型、一个是字符型）；
   - *属性值冲突*：同一种度量单位不同（如米 vs 厘米）；
2. **命名冲突**：
   - *同名异义*：不同实体使用了相同的名称；
   - *异名同义*：同一实体在不同部门中使用了不同名称（如“职工”与“教师”、“物资”与“商品”），需统一合并重命名；
3. **结构冲突**：
   - *抽象级别冲突*：同一对象在某分图中被当作“实体”，而在另一分图中被当作“属性”；
   - *联系类型冲突*：同一实体间的联系在不同分图中体现为不同的基数（如一处为 1:n，另一处为 m:n）。

### 逻辑结构设计的完整产出规范
- 概念 E-R 图必须转化为满足特定规范化级别（通常至少 3NF）的关系模式集合；
- 明确指定每个关系的**主键（Primary Key）** 与 **外键（Foreign Key）**；
- 定义实体完整性、参照完整性及用户定义的完整性约束（`CHECK`, `NOT NULL`, `UNIQUE`）。

## 3. 面向对象系统分析与设计（OOA & OOD）

### BCE 分析类模型（Boundary - Control - Entity）
面向对象分析中将识别出的领域类分为三类：
1. **边界类（Boundary Class）**：系统与外部参与者（用户、外部系统、硬件设备）之间交互和通信的屏障（如输入表单、用户界面、通信适配器）；
2. **控制类（Control Class）**：封装用例执行的核心控制逻辑、流程编排与跨实体业务计算（如借书控制器、结账事务流）；
3. **实体类（Entity Class）**：保存系统需要长期持久化存储的业务数据及对这些数据的原子操作（如用户、账户、订单）。
- **交互边界准则**：边界类不能直接访问数据库实体类，必须经过控制类的业务编排调度！

### 动态模型建模要素规范
- **状态机图语法规范**：
  状态迁移的标准标注语法：
> **状态机转换标注语法**：`事件 (Event) [守卫条件 (Guard)] / 动作 (Action)`
  - 方括号 `[ ]` 内为布尔判定，为真时才触发；斜杠 `/` 之后为迁移发生时执行的动作；
  - 状态是对象生命周期中持续存在的阶段（名词/形容词），事件是瞬时触发的外部输入（动词）。
- **活动图（Activity Diagram）**：
  - 适合用于复杂用例的业务流程建模；
  - 支持分支（Decision）、合并（Merge）、分流（Fork 并发分支）、汇合（Join 并发同步）；
  - **泳道（Swimlane）**：按组织角色或对象职责将活动划分在不同的泳道中，清晰展现每项活动的责任主体。

## 4. 人机界面（UI）设计三大黄金准则与用户交互体验

人机界面（User Interface，UI）是人与计算机系统之间进行信息传递和交互的媒介。Theo Mandel 提出了著名的“人机界面设计三大黄金准则”：

### 三大黄金设计准则与实现要求
1. **置用户于控制之下（Place the user in control）**：
   - 核心思想：以用户为中心，让用户感到自己是交互过程的主导者，而非被系统所强迫或控制；
   - **具体实现原则**：
     - 允许用户灵活中断、撤销（Undo）和重做（Redo）不希望的操作；
     - 允许用户根据自身习惯自定义界面布局、交互快捷方式与显示模式；
     - 避免强迫用户进入无休止的模态交互或不可跳过的流程中；
     - 提供直接交互机制（如直接拖拽、即时预览对象）。
2. **减少用户的记忆负担（Reduce the user's memory load）**：
   - 核心思想：人脑短时记忆容量有限（一般为 7 ± 2 个信息块），界面设计应尽量“让用户识别，而非让用户回忆”；
   - **具体实现原则**：
     - 提供直观的视觉线索、默认设置与智能补全输入；
     - 定义有意义的直观快捷键与上下文关联菜单；
     - 遵循“适度渐进揭示”原则，避免单屏信息量过载；
     - 在表单填写时显示当前进度与历史输入记忆。
3. **保持界面一致性（Make the interface consistent）**：
   - 核心思想：界面元素、术语规范与操作逻辑在全系统及跨版本中必须保持统一稳定，降低用户的学习认知成本；
   - **具体实现原则**：
     - 统一视觉规范（字体、字号、配色方案、按钮形状与图标语义全系统一致）；
     - 统一输入机制与快捷键映射（如 `Ctrl+S` 统一为保存）；
     - 统一信息展示格式（日期、货币、错误提示信息的显示规范保持相同）。

## 5. 软件体系结构评估核心概念（ATAM / SAAM）

软件体系结构评估旨在系统开发早期，对架构方案是否满足非功能性质量属性需求（如性能、可用性、安全性、可修改性）进行系统化评价。其中最经典的是**架构权衡分析法（ATAM）**。

### 架构评估四大核心概念判定矩阵

| 评估核心概念 | 英文名称 | 概念精确定义与内涵 | 考题判定口诀与特征 | 经典真题实例 |
|---|---|---|---|---|
| **敏感点** | Sensitivity Point | **某一特定质量属性对某个或某几个架构特性/决策极为敏感**（该特性稍有改变，该质量属性即发生显著变化） | “改动它，**只影响某一个单一质量属性**” | • 对通信数据采用特定算法加密，能显著提高系统的**安全性**（加密特性是安全性的敏感点）<br>• 增大主存 Cache 容量能大幅提升系统**响应性能** |
| **权衡点** | Tradeoff Point | **影响多个不同的质量属性，并且在这些质量属性之间产生此消彼长（Trade-off）折中妥协的架构特性** | “改动它，**同时影响两个或多个质量属性，且互有得失**” | • 提高通信数据的加密强度可以提高系统的**安全性**，但由于加解密计算开销增大，会导致系统**响应时间变长（性能下降）**。因此该加密算法是安全性和性能之间的**权衡点**！ |
| **风险点** | Risk | 架构设计中潜在的、**可能导致系统严重违背某一关键质量属性或失败的未决架构决策** | “可能引发严重后果的架构隐患或薄弱环节” | 核心业务数据库未配置任何主从备份，一旦单点故障将导致全系统瘫痪（这是可用性的重大风险点） |
| **非风险点** | Non-risk | 架构设计中经过严格评估验证的、**能够有效满足预期质量要求的良好架构决策** | “积极的、被证明安全可行的设计决策” | 系统关键接口均统一使用成熟的 OAuth 2.0 工业标准协议进行身份鉴权 |

> **架构评估秒杀口诀**：
> “改动它只影响一个指标是敏感点；改动它产生此消彼长矛盾是权衡点；潜在隐患是风险点；稳妥良策是非风险点。”

## 6. 第十二章核心易错陷阱防坑指南与做题检查清单

### 核心易错陷阱防坑指南
1. **敏感点与权衡点混淆**：
   - **陷阱**：题干描述“改变该机制提升了安全性的同时降低了性能”，错选为敏感点；
   - **避坑法宝**：只要涉及**两个或多个质量属性之间的相互折中制约**，必须判定为**权衡点**！只有孤立影响单一质量属性时才是敏感点。
2. **E-R 图结构冲突与属性冲突混淆**：
   - **陷阱**：同一概念在 A 图中是实体，在 B 图中是属性，错判为属性冲突；
   - **避坑法宝**：抽象层级不同（实体 vs 属性）属于**结构冲突**！属性冲突仅局限于同一属性的数据类型、长度或取值范围不一致。
3. **BCE 架构中边界类跨层访问**：
   - **陷阱**：误以为用户界面（边界类）可以直接执行 SQL 读写数据库实体类；
   - **避坑法宝**：BCE 设计准则严禁边界类直接访问实体类，必须经过**控制类（Control Class）**进行业务逻辑调度。

### 第十二章做题自检检查清单
- [ ] 决策表先计算条件取值组合数，再处理每种组合对应的动作；
- [ ] 数据库设计题按“需求分析 → 概念 E-R 模型 → 逻辑关系模式”回溯，不跳过概念结构；
- [ ] UML 图题先锁定图类型：消息时序用序列图，业务流程用活动图，状态变化用状态图；
- [ ] 状态图中方括号是条件，斜杠后的表达式或标注动作是动作；不要将两者混淆；
- [ ] 识别 BCE 架构时，界面表单属于边界类，业务规则控制器属于控制类，数据模型属于实体类；
- [ ] UI 三大黄金准则：“置用户于控制之下、减少用户记忆负担、保持界面一致性”。
