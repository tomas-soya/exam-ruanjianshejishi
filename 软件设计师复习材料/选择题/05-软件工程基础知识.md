# 第五章 软件工程基础知识

## 1. 开发生命周期：先区分“给谁用、何时用”

### 软件生命周期各阶段文档与交付物体系
- **系统规划与系统分析阶段**：用户与系统分析人员交流使用的文档包括：**可行性研究报告、总体规划报告、项目开发计划、软件需求规格说明书（SRS）**，用于确认目标、范围和可行性；
- **设计阶段产物**：软件体系结构图（SC）、数据库表结构、接口规格说明书，描述系统如何组织实现，属于系统设计阶段产物；
- **交付与运维阶段产物**：**用户使用手册**的目标读者是最终用户，主要在软件完成并交付后使用，**绝不是规划、分析阶段用户与分析人员交流的核心文档**。遇到“规划/分析阶段交流文档不包括”时，直接定位排除用户手册。

### 软件需求分类：功能需求 vs 非功能需求
- **功能需求（Functional Requirement）**：描述系统必须完成的**业务功能与具体处理操作**（即“系统必须做什么”）。
  - 例如：“系统应支持员工提交报销单”、“财务人员按部门汇总月度报销金额”、“系统自动计算并扣除个人所得税”等直接体现业务处理逻辑的条款。
- **非功能需求（Non-functional Requirement）**：系统在运行品质、性能与环境约束方面的要求（即“系统做得多好、受什么限制”）：
  - **性能需求**：响应时间（如 < 1 秒）、吞吐量、并发用户数；
  - **安全性与可靠性**：用户身份鉴别、数据传输加密、平均无故障时间（MTBF）；
  - **可用性与易用性**：界面直观友好、操作失误防范；
  - **设计与实现约束**：指定运行平台（如 Linux）、遵循特定会计准则、采用特定开发语言。

## 2. 过程改进与过程模型

### CMMI 连续式表示法

连续式模型的过程域能力等级从 CL0 到 CL5。最容易混淆的是后两级：

| 等级 | 关键含义 |
|---|---|
| CL0 未完成 | 过程未执行或未达到 CL1 目标 |
| CL1 已执行 | 能把输入工作产品转化为可识别的输出工作产品 |
| CL2 已管理 | 过程有计划、资源、监控与评审 |
| CL3 已定义 | 按组织标准过程裁剪并沉淀过程资产 |
| CL4 定量管理 | 用测量和质量目标管理过程 |
| CL5 优化 | 用量化、统计手段持续改变和优化过程，以适应客户变化 |

题干出现“统计学手段”“持续改进”“应对客户要求改变”时，应定位到 CL5，而不是只看到“度量”就选 CL4。

### UP、构件开发与敏捷方法

- 统一过程（UP/RUP）是**用例驱动、以体系结构为核心、迭代和增量式**的软件过程框架。四阶段为起始、精化、构建、移交；需求分析和架构演进、确定稳定架构基础，重点在**精化阶段**。
- 基于构件开发本质上是演进式、迭代式开发，复用预先打包和测试过的构件；它不以“必须采用面向对象技术”为前提。
- Scrum（并列争球法）以短迭代的**冲刺（Sprint）**推进工作，并按需求优先级交付产品增量。
- XP 强调沟通、简单、反馈和勇气。结对编程也是持续代码审查和知识共享的方式；代码所有权属于团队，而非某一名开发者。

### 演化模型的适用点

- **增量模型**把产品拆成多个增量分别设计、实现、集成和测试，可较早交付可用功能，也更容易适应需求变化；前提是有能容纳后续增量的开放式架构。模块划分困难、增量交叉处理不当、过程退化为边做边改，都是风险或缺点，不是优势。
- **螺旋模型**以风险分析为显著特征，综合原型迭代与瀑布式的系统化控制，适合大型、昂贵、风险较高的系统。
- **喷泉模型**面向对象，以用户需求为动力、对象为驱动；迭代且各阶段可重叠，没有瀑布模型那样严格的阶段间隙。

## 3. 系统设计：架构、耦合和内聚要分层判断

### 架构风格

- **经典软件体系结构风格分类**：
  - **数据流风格**：包括批处理序列和**管道—过滤器（Pipe and Filter）**。管道传输数据，过滤器完成独立数据变换；构件高内聚低耦合，但**不适合要求构件之间进行复杂、直接交互的情形**；
  - **仓库风格（Repository）**：包含一个**中心数据结构（数据仓库）**和若干个**独立构件**。独立构件访问并修改中心数据。
    - **典型子风格**：**数据库系统、黑板系统（Blackboard）、超文本系统**；
    - **优点**：便于数据共享与构件扩充、具有可更改性和可维护性、支持多方法求解、有可重用知识源；
    - **缺点**：**测试困难**（因黑板模式系统执行顺序不确定，结果可再现性较差，难以测试）、效率可能受限于中心数据争用；
  - **调用/返回风格**：包括主程序/子程序、面向对象系统、分层体系结构；
  - **独立构件风格**：包括进程通信、事件驱动系统（隐式调用）；
  - **虚拟机风格**：包括解释器（Interpreter）、基于规则的系统。
- **现代与分布式架构**：
  - **微服务架构**：将系统按业务领域拆分为可独立部署、通过轻量 API 通信的小服务，具有高弹性与自治性；
  - **C/S 与 B/S**：客户机/服务器（C/S）具备较强的客户端交互与本地处理能力，但客户端维护升级成本高；浏览器/服务器（B/S）零客户端安装、维护简单；
  - **MVC 体系结构**：Model（模型，负责业务逻辑与数据）、View（视图，负责用户界面展示）、Controller（控制器，负责响应请求与协调）。各部分职责分离，支持多视图共享同一模型。

### 耦合与内聚分类全体系

#### 模块耦合度分类（从低到高，耦合越低越好）
1. **无直接耦合**：两个模块间没有任何直接关系；
2. **数据耦合（最理想）**：模块间仅通过简单的数据参数传递信息；
3. **标记耦合**：模块间传递的是复合数据结构（如传递整个记录/结构体），但接收模块仅需其中部分字段；
4. **控制耦合**：模块间传递的信息中包含控制开关、标志变量，用以直接控制另一模块的内部执行逻辑；
5. **外部耦合**：一组模块均访问相同的外部环境变量、I/O 设备或通信协议；
6. **公共耦合**：多个模块通过共同的全局数据域、全局变量或公共数据区相互作用；
7. **内容耦合（最差，必须避免）**：一个模块直接访问另一模块的内部数据，或非正常转移至另一模块内部。

#### 模块内聚度分类（从高到低，内聚越高越好）
1. **功能内聚（最理想）**：模块内所有元素共同完成一个单一、明确的特定功能；
2. **顺序内聚**：模块内各处理元素紧密相连，前一元素的输出是后一元素的直接输入；
3. **通信内聚**：模块内各处理元素操作同一输入数据集，或产生共同的输出数据集；
4. **过程内聚**：模块内部处理元素按特定的控制流程（顺序、分支、循环）执行；
5. **时间内聚**：模块内各任务必须在同一时间段内执行（如系统初始化、关闭退出）；
6. **逻辑内聚**：模块内执行几个逻辑上相似的功能，由外部传入的参数决定执行哪一个；
7. **偶然/巧合内聚（最差）**：模块内各部分之间没有实质联系，纯粹偶然拼凑在一起。

#### 模块结构设计准则：作用范围与控制范围
- **控制范围**：模块本身及其所有下属模块（直接和间接被其调用的模块）的集合；
- **作用范围**：受模块内某一个判定影响的所有模块的集合；
- **设计准则**：**模块的作用范围应在其控制范围之内**（作用范围 ⊆ 控制范围）；
- **超范围改进策略**：若作用范围超出控制范围，可采用“**上移判定点**”（将判定上移至较高层父模块中），或“**下移受判定影响的模块**”（将其调入控制范围内），绝对不能通过将父模块下移来解决。

### 程序执行效率与系统性能优化原则

- **提升程序运行与执行效率的核心途径**：
  1. **优化算法设计（最根本手段）**：选择时间复杂度更低的高效算法（例如从 O(n²) 优化至 O(n log n)），从渐进数量级上减少基本运算次数；
  2. **组织高效的数据结构**：根据数据的访问特性（随机访问、频繁插入/删除、范围查询等）选择合适的数据结构（如哈希表、平衡二叉树、B+ 树、跳表等），减少查找与搬运开销；
  3. **选用运行效率高的程序设计语言**：底层对执行效率与实时性有极致要求的模块（如系统核心、图形渲染驱动、通信引擎）采用编译型系统级语言（如 C/C++）编写，替代高运行时开销的解释型脚本语言；
  4. **并发与体系结构优化**：利用多线程并行处理、多进程、异步非阻塞 I/O、流水线优化以及合理利用 CPU Cache（保持良好的时间局部性与空间局部性）。
- **极高频做题避坑陷阱**：
  - **“改写代码使其更紧凑”一般不能提高程序的执行效率**！改写紧凑代码（如将多行代码浓缩写在单行、滥用嵌套三元运算符或语法糖缩写）主要改变的是源码排版形式与书写紧凑度，反而会损害程序可读性与可维护性；现代编译器的优化器通常会将紧凑书写与规范书写的等价逻辑编译为相同的机器指令序列，因此**代码紧凑书写绝不属于提高程序执行效率的方法**；
  - “编译优化（编译器生成更优机器码）”可以提高执行效率，但“源代码紧凑”不等于编译优化。

## 4. 系统测试与调试：层次模型、覆盖准则与 McCabe 环路复杂度

### 测试层次与面向对象测试
- **单元测试**：检查最小可测试代码单元（函数/类）。面向对象中类内方法测试对应算法层；
- **集成测试**：重点发现**模块间接口不匹配与交互缺陷**；策略包括自顶向下（需桩模块 Stub 模拟下层）与自底向上（需驱动模块 Driver 模拟上层调用）；
- **系统测试**：在真实运行环境下验证完整系统是否满足需求规格（包括功能、性能、压力、安全等）；
- **验收测试**：由最终用户参与，分为 Alpha 测试（开发者场所，受控环境）与 Beta 测试（用户场所，非受控环境）。

### 白盒测试逻辑覆盖准则（由弱到强）
1. **语句覆盖（最弱）**：设计测试用例，使程序中**每一条可执行语句至少执行一次**；
2. **判定覆盖（分支覆盖）**：使程序中**每个判定的真分支和假分支至少经历一次**；
3. **条件覆盖**：使判定中**每个条件的可能取值（真/假）至少满足一次**；
4. **判定/条件覆盖**：同时满足判定覆盖与条件覆盖；
5. **条件组合覆盖**：使每个判定中**所有条件的各种可能取值组合至少出现一次**；
6. **路径覆盖（最强）**：覆盖程序控制流图中所有可能的执行路径。

### McCabe 环路复杂度计算三大等价方法
控制流图 G 中：
1. **闭环区域法**：V(G) = 平面闭环区域数 + 1（包含外部无界区域）；
2. **边点关系法**：V(G) = E - N + 2（E 为流图中的有向边数，N 为流图中的节点数）；
3. **判定节点法**：V(G) = P + 1（P 为控制流图中出度大于 1 的条件判定节点数）。

### 黑盒测试用例设计：等价类划分、边界值分析与错误推测法
- **黑盒测试基本特征**：不考虑程序内部逻辑结构与编码细节，完全依据软件需求规格说明书，检查程序功能是否符合规格要求。
- **等价类划分法（Equivalence Partitioning）**：
  - **核心思想**：把所有可能的输入数据划分为若干互不相交的等价子集（等价类），从每个子集中选取少数具有代表性的值作为测试用例。每个等价类中的输入数据在检验程序功能时具有相同的检错效力。
  - **主要目的**：**显著减少测试用例数量，同时保证对输入域进行系统、充分的测试覆盖**，在测试成本与测试有效性之间取得最佳平衡。
  - **分类**：
    - **有效等价类**：由符合程序规格说明的合理输入数据构成的集合（检验程序是否实现预定功能）；
    - **无效等价类**：由不符合规格说明的不合理输入数据构成的集合（检验程序的输入校验、异常捕获与容错健壮性）。
- **边界值分析法（Boundary Value Analysis，BVA）**：
  - **核心原理**：大量工程实践表明，软件缺陷极高概率聚集在输入域的**边界值附近**，而不是内部。
  - **用例设计准则**：测试用例应重点选取**刚好等于边界、刚刚大于边界和刚刚小于边界的值**（如 0、最大值、最小值、空串、溢出临界点）。
  - **协同关系**：边界值分析法是等价类划分法的最核心有效补充，通常两者联合使用。
- **错误推测法与因果图法**：
  - **错误推测法**：依靠测试工程师的直觉、工程经验和对常见 Bug 模式的洞察来专门推测容易出错的薄弱环节；
  - **因果图法**：通过因果图表达多个输入条件（原因）与输出（结果）之间的布尔逻辑与制约关系，并转化为判定表设计测试用例。

## 5. 软件运行与维护：四类维护类型与度量指标

### 软件维护的四大类型（按性质划分）
1. **完善性维护（占比最高，50%～55%）**：
   - 为扩充新功能、改善系统性能、优化用户界面或满足业务扩展而进行的修改；
2. **适应性维护（占比次之，18%～25%）**：
   - 为适应外部运行环境（操作系统升级、硬件更替、外部接口或国家法规标准调整）而进行的修改；
3. **改正性维护 / 纠错性维护（17%～21%）**：
   - 识别并排除软件交付上线后在运行过程中暴露出的潜在缺陷、潜伏 Bug 或逻辑错误；
4. **预防性维护（约 4%）**：
   - 为应对未来演化、提高软件可维护性和可靠性，主动重构设计、优化架构或补充文档。

### 可维护性度量模型
- 常用指标：M = 1 / (1 + MTTR)（MTTR 为平均故障修复时间）；
- MTTR 越小，说明修复速度越快，系统的可维护性越高。

## 6. 软件项目管理、质量模型与度量体系

### 项目进度管理：甘特图 vs PERT/CPM 网
- **甘特图（Gantt Chart）**：
  - **优势**：直观反映每个子任务的计划起止时间、持续工期、任务并行关系以及**项目的实际执行进度**；
  - **局限**：**不能清晰反映各子任务之间复杂的先后依赖与衔接关系**，难以直接推断关键路径。
- **PERT / CPM 网络图**：
  - **优势**：清晰表达任务间的先后依赖关系，能够准确计算最早/最迟时间，**识别决定总工期的关键路径**；
  - **局限**：不能直观反映项目当前的实际工期完成百分比。

### 关键路径与工期延误判定通用模型
1. **关键路径（Critical Path）**：项目中从起始节点到终止节点耗时最长的一条（或多条）路径，其总耗时决定了**项目的最短完工时间**；
2. **总时差（Total Float）**：活动在不影响项目总工期的前提下可以推迟开工的最大宽限时间。
   - **标准计算公式**：总时差 = 最迟开工时间 - 最早开工时间（`TF = LS - ES`），或 = 最迟完工时间 - 最早完工时间（`TF = LF - EF`）。
   - **简化特例判断**：对于完全独立的简单并行支路（无复杂的中间分叉或汇合），路径长度差（关键路径总工期 - 该支路总工期）可作为该支路容许总时差的快捷判断。但**这并非通用公式**，复杂网络必须使用最早/最迟时间计算。
3. **延误对项目总工期的影响判定**：
   - 若某活动的延误时间 ≤ 其总时差，则**不会对项目最短总工期造成任何影响**；
   - 若延误时间 > 总时差，则**超出总时差的部分将直接导致项目整体总工期延长**！

### 软件风险管理核心策略
- **风险评估与优先级设定**：
  - **风险识别与评估双维度**：风险评估必须同时考量**风险发生概率（Risk Probability, P）**与**风险产生影响/损失严重度（Risk Impact / Loss, L）**；
  - **风险暴露（Risk Exposure, RE）计算**：RE = P × L（即风险概率与风险影响的乘积），又称**风险量**或**风险曝光度**；
  - **风险优先级设定依据**：在软件工程风险管理中，**风险的优先级通常根据“风险暴露（Risk Exposure）”来设定**，以便项目团队集中资源优先应对综合危害最大的风险；若仅作定性评估，则通过“概率-影响矩阵”综合判定；
  - **做题易错陷阱**：单纯依靠“风险概率”或单纯依靠“风险影响”设定优先级均是片面的，二者结合的综合量度**风险暴露（Risk Exposure）**才是优先级的权威判定依据。
- **四大应对策略（高频做题区分）**：
  1. **风险规避（Risk Avoidance）**：通过彻底修改项目计划或放弃高风险模块/业务来杜绝该风险发生（如砍掉不成熟的新技术特性）；
  2. **风险转移（Risk Transference）**：**将风险的后果和责任转交由第三方承担**。典型手段包括：
     - **购买商业保险**：将潜在财务损失转移给保险公司；
     - **签订固定价格合同（固定总价合同）**：将成本超支或工期延误的经济风险转移给承包商/供应商；
     - **非核心业务外包**：将技术实施风险转移给外部专业团队。
  3. **风险缓解 / 减轻（Risk Mitigation）**：采取主动预防措施降低风险发生的概率或减轻其损失（例如：增加资深测试人员降低缺陷率、开展团队交叉培训、搭建双机热备容灾环境）；
  4. **风险接受（Risk Acceptance）**：不采取主动改变措施，准备应急预案并预留应急储备金（通常适用于发生概率低、影响较小的非关键风险）。

### 软件配置管理（SCM）体系与易错边界
- **配置项（SCI）**：包括程序（源程序、目标代码）、文档（需求分析书、设计方案、测试计划、用户手册）和数据（测试用例、支撑数据）；
- **配置库三层结构**：
  1. **开发库（动态库/工作库）**：供开发人员个人日常编码、调试使用，无需严格受控；
  2. **受控库（受控状态库）**：保存通过单元/集成测试的基线版本，需 CCB 变更控制审批方可签出修改；
  3. **产品库（静态库/发行库）**：保存正式发布并交付用户的最终系统基线产品。
- **四大核心配置管理活动**：
  1. **版本控制（Version Control）**：标识配置项的演变演进，管理分支与标签；
  2. **变更管理（Change Control）**：由变更控制委员会（CCB）负责审批评估所有变更申请，确保受控修改；
  3. **配置状态报告（Configuration Status Accounting）**：记录并报告配置项状态及已批准变更的执行进展；
  4. **配置审计（Configuration Audit）**：包括功能配置审计（FCA，核对是否符合需求文档）与物理配置审计（PCA，核对构建完整性与物料清单）。
- **极高频做题避坑陷阱**：
  - **风险管理**属于软件项目整体管理范畴，**绝不属于软件配置管理活动**！做题若问“不属于配置管理的是”，首选**风险管理**；
  - 基线（Baseline）是软件开发特定阶段的重要里程碑，包括功能基线（需求分析结束）、指派基线（设计阶段结束）、产品基线（测试验收完成）。

### 软件质量模型：ISO/IEC 9126 六大质量特性
1. **功能性**：适合性、准确性、互操作性、依从性、**安全性**（注：安全性属于功能性子特性！）；
2. **可靠性**：成熟性、容错性、易恢复性；
3. **易用性**：易理解性、易学性、易操作性；
4. **效率**：时间特性、资源特性；
5. **可维护性**：易分析性、易改变性、稳定性、易测试性；
6. **可移植性**：适应性、易安装性、共存性、易替换性。

### 软件项目估算模型：COCOMO、COCOMO II 与工作量/成本估算

- **软件估算基本概念与规模度量**：
  - 软件成本与工作量主要由**软件规模**决定，辅以各种成本驱动因子进行校正；
  - 常用的规模度量指标包括：**源代码行数（LOC/SLOC）**、**功能点（Function Points，FP）**与**对象点（Object Points，OP）**。
- **经典 COCOMO 模型（结构化成本模型）**：
  - 属于静态单变量/多变量模型，按项目复杂度分为三类：组织型（Organic，小型熟悉项目）、半独立型（Semidetached，中等规模混合项目）、嵌入型（Embedded，严苛硬件与环境约束的大型复杂项目）；
  - 分为基本 COCOMO（仅基于代码行）、中级 COCOMO（引入 15 个成本驱动因子属性乘数）、详细 COCOMO（按阶段和子系统逐层细化）。
- **现代 COCOMO II 模型（层次化阶段估算模型）**：
  - COCOMO II 针对现代软件开发模式进行了重大升级，包含一套完整的**三阶段层次结构模型**：
    1. **应用组装模型（Application Composition Model）**：用于项目原型构建阶段，处理界面和用户交互，规模估算基于**对象点（Object Points）**；
    2. **早期设计阶段模型（Early Design Model）**：在需求初步明确、探索替代系统架构阶段使用，基于**未调整的功能点（FP）**或粗略代码行进行初步估算；
    3. **体系结构阶段模型（Post-Architecture Model）**：在系统体系结构已经稳定、进入详细设计与编码实现阶段使用。**该模型基于源代码行数（SLOC）或功能点进行估算**，并综合考虑 17 个精确的成本驱动属性与 5 个标度因子，是精确度最高的估算模型。
- **高频做题检查清单**：
  - 考题问“COCOMO II 层次结构中，规模度量选择不包括”：牢记 COCOMO II 的 3 种规模选择是**对象点、功能点、代码行（源代码行）**，不包括“用例数”、“用例点”或“模块数”；
  - 考题问“COCOMO II 中，体系结构阶段模型基于什么进行估算”：直接锁定**源代码的行数（SLOC）**；
  - 考题问“以规模作为成本主要因素，包括应用组装模型、早期设计阶段模型和体系结构阶段模型的方法”：直接锁定 **COCOMO II**。

## 7. 软件容错技术、可靠性浴盆曲线与净室软件工程

### 软件容错技术全景体系
容错技术旨在系统发生软件或硬件故障时，依然能够保持规定功能的正常运行或安全降级。
1. **四类基本冗余手段**：
   - **结构冗余（硬件/软件冗余）**：引入额外的计算部件或程序模块；
   - **信息冗余**：引入额外的校验位或纠错码（如奇偶校验、CRC、海明码）；
   - **时间冗余**：通过重复执行计算（如指令重试、事务回滚重试）以消除瞬态故障；
   - **冗余程序设计**：针对相同规格说明，由不同团队采用不同算法或语言独立开发多个程序模块。
2. **两大多版本冗余架构深度辨析（核心考点）**：

| 容错架构 | 冗余类型 | 核心运行机制与结构 | 错误检测与恢复动作 | 典型应用与做题线索 |
|---|---|---|---|---|
| **N 版本程序设计（N-Version Programming）** | **静态冗余（前向恢复）** | 由 N 个独立团队开发的 N 个版本**并发并行执行**，将其输出送入**表决器（Voter）** | 表决器按**多数一致原则**裁定最终输出，少数出错版本的错误直接被屏蔽掩盖（无需回滚历史状态） | “多版本并发运行 + 表决器选多数”；常用于严苛实时航天、飞行控制系统 |
| **恢复块方法（Recovery Block）** | **动态冗余（后向恢复）** | 包含 1 个**主块（Primary Block）**与多个**后备块（Alternate Blocks）**，平时仅串行执行主块 | 主块执行完毕后进入**验收测试（Acceptance Test）**；若测试通过则输出；若失败则**回退恢复现场状态**，串行切换至第一个后备块重试 | “主块 + 验收测试 + 后备块回退重试”；验收测试至关重要 |

> **极速判定口诀**：
> “N版本是静态冗余，并发执行表决器选多数；恢复块是动态冗余，验收测试不通过回退重试。”

### 软件可靠性工程与浴盆曲线对比
- **硬件浴盆曲线（Bathtub Curve）三大阶段**：
  1. **早期故障期（失效率递减）**：由于制造工艺缺陷、元件筛选不良导致，随老化筛选失效率迅速下降；
  2. **偶然故障期（失效率恒定，有效寿命期）**：系统进入稳定运行期，失效率 λ 保持常数，故障由随机外部环境应力引发；
  3. **耗损故障期（失效率递增）**：元器件因物理磨损、老化、疲劳导致失效率急剧上升。
- **软件失效率曲线的本质差异**：
  - **软件没有物理磨损和老化**！软件不会因为长期运行而产生机械磨损；
  - 软件失效率在经过开发调试与上线初期修复后逐渐降低；
  - 软件在生命周期后期的失效率上升，**完全是因为频繁的功能变更、维护修改引入了新的缺陷与副作用（退化）**导致的，绝非物理老化！

### 净室软件工程（Cleanroom Software Engineering）基本概念
净室软件工程强调在软件开发全过程中**预防缺陷而非测试除错**：
1. **形式化规格说明**：采用严格的数学模型（如函数表示法、状态机、代数规格说明）描述系统需求；
2. **正确性验证**：采用严格的数学证明与团队审查代替传统的单元测试；
3. **统计过程控制**：基于使用模型（Usage Model）进行**基于统计的软件测试**，以科学评估软件的失效率与可靠性指标（MTTF）。

## 8. 第五章核心易错陷阱防坑指南与做题检查清单

### 核心易错陷阱防坑指南
1. **N 版本程序设计 vs 恢复块方法混淆**：
   - **陷阱**：看到“多版本”就错选 N 版本，忽视了题干描述的是“串行执行、验收测试失败后回滚”；
   - **避坑法宝**：抓住标志性机制：有“表决器（Voter）”是 N 版本；有“验收测试（Acceptance Test）与回退”是恢复块。
2. **软件老化误区**：
   - **陷阱**：题干选项断言“软件像硬件一样因磨损而导致失效率上升”；
   - **避坑法宝**：软件是逻辑实体，绝对不发生物理磨损！后期失效率波动完全源于人为维护修改的副作用。
3. **逻辑覆盖准则由弱到强次序颠倒**：
   - **陷阱**：混淆判定覆盖与条件覆盖的强弱包含关系；
   - **避坑法宝**：牢记强度阶梯：`语句覆盖（最弱） < 判定覆盖（分支） < 条件覆盖 < 判定-条件覆盖 < 条件组合覆盖 < 路径覆盖（最强）`。注意：条件覆盖不一定包含判定覆盖，判定覆盖也不一定包含条件覆盖，二者交织但均弱于判定-条件覆盖。
4. **甘特图 vs PERT 图功能辨析**：
   - **陷阱**：试图在甘特图上直接识别关键路径与活动依赖关系；
   - **避坑法宝**：甘特图直观反映任务的**起止时间与并行进度**，但不能清晰展现复杂的任务依赖网络与关键路径；PERT/CPM 网状图专用于展现**任务先后依赖、时差松弛与关键路径计算**。

### 第五章做题自检检查清单
- [ ] 软件生命周期阶段产物：可行性报告（立项）、SRS 软件需求规格说明书（需求分析）、架构与详细设计说明书（设计）；
- [ ] 内聚与耦合等级：功能内聚最高（最好），偶然内聚最低（最差）；无直接耦合最低（最好），内容耦合最高（最差）；
- [ ] McCabe 环路复杂度公式：`V(G) = E - N + 2`，或 `V(G) = 闭合区域数 + 1`，或 `V(G) = 判定节点数 + 1`；
- [ ] 关键路径判定：网络中从源点到汇点**耗时最长**的路径即为关键路径；
- [ ] 维护类型四分类：纠错性（修 Bug）、适应性（适新软硬件环境）、完善性（扩充新功能、提高性能，占比超 50%）、预防性（防患未然重构）。
