# 第九章 数据库技术基础

## 1. 数据库三级模式结构与两级独立性映像

### 三级模式与数据对象的映射关系
| 数据库模式 | 对应视图 | 对应系统实体 | 职责与描述对象 |
|---|---|---|---|
| **外模式 (External Schema)** | **用户模式 / 用户视图** | **视图 (View)** | 针对特定用户或应用程序看到和使用的局部数据逻辑结构 |
| **概念模式 (Schema)** | **概念模式 / 概念视图** | **基本表 (Base Table)** | 数据库中全体数据的全局逻辑结构和特征，独立于物理存储 |
| **内模式 (Internal Schema)** | **存储模式 / 内部视图** | **存储文件、聚簇索引** | 数据在物理存储介质上的存储方式、物理组织与索引结构 |

- **视图机制与数据字典**：视图（View）是从一个或多个基本表（或其他视图）导出的虚拟表，其本身不独立存储数据行。在数据库中创建视图时，**数据字典中保存的是视图定义（即对应的 SQL 查询定义）**，而非所引用的基本表定义或查询结果。针对视图建立聚簇索引改变的是内模式存储。

### 两级映像与两大独立性（核心考点）
1. **外模式 / 模式映像（保证逻辑数据独立性）**：
   - 当数据库全局逻辑结构发生改变（如增加新属性、修改关系结构）时，只需修改该映像，而**外模式和应用程序无需修改**；
2. **模式 / 内模式映像（保证物理数据独立性）**：
   - 当数据的物理存储结构改变（如修改存储路径、重建聚簇索引）时，只需修改该映像，而**全局概念模式和应用程序无需修改**。

### 分布式数据库系统的四大透明性
- **分片透明性（最高级别）**：用户无需关心数据是如何分片的（水平分片、垂直分片、混合分片）；
- **位置透明性**：用户无需关心数据存放在哪个网络节点或站点上；
- **局部映像透明性（逻辑透明）**：用户无需关心局部站点使用的是何种数据模型；
- **复制透明性**：用户无需关心系统内部是否存在多个数据副本及其同步机制。

## 2. 数据库设计全生命周期与 E-R 模型转换

### 数据库设计的 5 大核心阶段
1. **需求分析阶段**：调查业务需求，输出**数据流图 (DFD)**、**数据字典 (DD)** 与需求说明书；
2. **概念结构设计阶段**：
   - 核心步骤：**抽象局部数据 → 形成各分 E-R 图 → 合并分 E-R 图消除冲突（命名冲突、属性冲突、结构冲突） → 优化消除冗余生成全局概念 E-R 图**；
3. **逻辑结构设计阶段**：
   - **依据概念 E-R 图，将其转换为特定 DBMS 支持的关系模式**，并进行范式规范化、确定主键与外键完整性约束；
4. **物理结构设计阶段**：
   - 为关系模式选定物理存储结构、存取路径、聚集方式与索引策略；
5. **数据库实施与运行维护**：加载数据、应用程序调试、监控优化与日常备份恢复。

### E-R 模型转换为关系模式的通用准则
- **实体转换**：每个实体独立转换为一个关系模式，其实体标识符直接作为该关系的主键；
- **1:1 联系**：可在任一端实体关系中加入另一端主键作为外键，或单独建立新关系；
- **1:n 联系**：**将“1”端实体的主键放入“n”端关系中作为外键**，联系属性也放入“n”端；
- **m:n 联系**：**必须独立转换为一个关系模式**，两端实体的主键作为外键共同构成**复合主键**，联系自身属性放入该联系关系中；
- **多元联系（如三元联系）**：必须独立建表，各参与实体的主键共同作为外键构成复合主键（若业务允许在不同时间重复发生，主键必须扩充时间属性）。

## 3. 关系代数与查询优化通用法则

### 核心关系代数运算符速查
- **选择 (σ)**：根据条件在关系的**行（元组）** 方向上进行过滤筛选；
- **投影 (π)**：在关系的**列（属性）** 方向上选择所需的属性列；结果关系按集合语义消除重复的**元组（行）**；
- **笛卡儿积 (×)**：将两表的属性列全部拼接，元组数为两表元组数乘积；
- **自然连接 (⋈)**：在笛卡儿积基础上，选取两表**所有公共同名属性值相等**的元组，并在结果中**合并消除重复属性列**；
- **除运算 (÷)**：常用于求解“查询选修了全部课程的学生”等包含“全部/所有”语义的查询。

### 关系代数查询优化原则（选择下推）
- **先选择、后投影、再连接**：
  - 在可能的情况下**尽量先执行选择 (σ) 操作**（选择下推），使参与后续连接的中间结果集大幅减小；
  - 尽早执行投影 (π) 操作，减少中间元组的字段宽度，大幅降低内存消耗与磁盘 I/O 开销。

## 4. 规范化理论：候选码求解、范式判定与分解准则

### 属性闭包计算与候选码求解通用算法（L/R/N/LR 分类法）
设关系模式 R(U, F)，将属性集 U 中的属性分为四类：
- **L 类**：仅出现在函数依赖左部的属性；
- **R 类**：仅出现在函数依赖右部的属性；
- **N 类**：在函数依赖左右两部均未出现的属性；
- **LR 类**：在函数依赖左右两部均出现过的属性。

#### 求解步骤：
1. **基础核确定**：令核心属性集 X = L ∪ N。**X 中的所有属性必定包含在每一个候选码中**；
2. **计算闭包 X^+**：若 X^+ 包含了 U 中的全部属性，则 **X 即为唯一的候选码**；
3. **组合扩展**：若 X^+ 不能覆盖全部属性，则依次将 LR 类中的属性逐个与 X 组合求闭包，直至能够覆盖全部属性的极小组合即为候选码；
4. **主属性与非主属性**：包含在**任何一个候选码中**的属性称为**主属性**；其他属性称为**非主属性**。

> **典型推导示例**：设关系模式 R(U, F)，属性集 U = {A, B, C, D}，函数依赖集 F = {AB → C, CD → B}。因为属性 D 仅在左部出现（L类），所以每个候选码都必须包含 D。通过计算闭包可知候选码为 ABD 与 ACD。因此所有属性 {A, B, C, D} 均为主属性，非主属性个数为 0。

### 关系数据库四大范式决策树
```text
[1NF: 属性值原子不可分]
   │
   ├── 是否存在非主属性对码的“部分函数依赖”？
   │      ├── 是 ──> 停留在 1NF（有数据冗余、插入/删除异常）
   │      └── 否（消除部分依赖） ──> [2NF]
   │                                     │
   └── 是否存在非主属性对码的“传递函数依赖”？
          ├── 是 ──> 停留在 2NF
          └── 否（消除传递依赖） ──> [3NF]
                                         │
   └── 每个决定因素（左部）是否都包含候选码（超键）？
          ├── 否 ──> 停留在 3NF
          └── 是（消除主属性部分/传递依赖） ──> [BCNF]
```

### 模式分解准则
1. **保持函数依赖性**：分解后各子模式所包含的原函数依赖闭包与原模式等价；
2. **无损连接性**：分解后的关系通过自然连接能够完全无损地还原回原关系（可用 Chase 矩阵法或定理判定：若 R_1 ∩ R_2 → (R_1 - R_2) 或 R_1 ∩ R_2 → (R_2 - R_1)，则二元分解必定无损）。

## 5. 事务管理与并发控制体系

### 事务的 ACID 四大特性
1. **原子性 (Atomicity)**：事务是不可分割的工作单位，要么全做要么全不做（由 **Undo 日志** 保证回滚）；
2. **一致性 (Consistency)**：事务执行前后数据库保持完整性约束状态一致（由其他三个特性共同保证）；
3. **隔离性 (Isolation)**：并发执行的各个事务之间互不干扰（由 **并发锁与 MVCC** 保证）；
4. **持久性 (Durability)**：事务一旦提交，对数据库的修改永久保存在磁盘介质中（由 **Redo 日志** 保证重做）。

### 并发操作导致的三大数据不一致问题
1. **丢失修改**：事务 T_1 和 T_2 读入同一数据并修改，T_2 的提交结果覆盖了 T_1 的结果；
2. **读“脏”数据**：T_1 修改了数据但随后回滚，T_2 读取了 T_1 尚未提交且最终被撤销的数据；
3. **不可重复读**：T_1 读取某数据后，T_2 对其进行了修改并提交，导致 T_1 再次读取时数值发生变化；
4. **幻读**：T_1 按条件查询时，T_2 新增或删除了满足条件的行，导致 T_1 再次按相同条件查询时记录条数改变。

### 事务四大隔离级别（SQL 标准）安全性与并发度对比表

| 隔离级别 | 读“脏”数据 | 不可重复读 | 幻读 | 安全性级别 | 并发执行性能 |
|---|:---:|:---:|:---:|---|---|
| **READ UNCOMMITTED（读未提交）** | 可能发生 | 可能发生 | 可能发生 | 最低 | 最高 |
| **READ COMMITTED（读已提交）** | **避免** | 可能发生 | 可能发生 | 较低 | 较高 |
| **REPEATABLE READ（可重复读）** | **避免** | **避免** | 可能发生 | 较高 | 较低 |
| **SERIALIZABLE（可串行化）** | **避免** | **避免** | **避免** | **最高（安全性最强）** | **最低** |

- **核心考点与做题陷阱**：
  - SQL 标准中，**隔离级别安全性最高的是 SERIALIZABLE（可串行化）**；
  - 它通过范围锁或严格串行调度，彻底杜绝脏读、不可重复读和幻读，但并发吞吐量最低；
  - 安全性从低到高顺序为：`READ UNCOMMITTED` < `READ COMMITTED` < `REPEATABLE READ` < `SERIALIZABLE`。

### 封锁机制与三级封锁协议
- **排他锁（X 锁 / 写锁）**：若事务对数据加上 X 锁，其他任何事务不能再对该数据加任何锁，只允许持有锁的事务读写；
- **共享锁（S 锁 / 读锁）**：若事务对数据加上 S 锁，其他事务只能再对其加 S 锁而不能加 X 锁，允许并发共享读；
- **三级封锁协议**：
  - **一级封锁协议**：修改数据前必须加 X 锁直至事务结束 → **防止丢失修改**；
  - **二级封锁协议**：在一级基础上，读数据前必须加 S 锁，**读完立即释放 S 锁** → **防止读脏数据**；
  - **三级封锁协议**：在一级基础上，读数据前必须加 S 锁，**直到事务结束才释放 S 锁** → **防止不可重复读**；
- **两段锁协议 (2PL)**：所有事务必须分两个阶段对数据加锁和解锁（加锁阶段只能加不能解，解锁阶段只能解不能加）。**遵守两段锁协议是保证并发调度可串行化的充分条件**。

### 数据库安全控制与标准 SQL 授权机制（GRANT / REVOKE）
- **数据控制语言（DCL）核心定位**：用于定义数据库用户的存取权限、控制敏感数据访问安全；
- **标准 SQL 授权语法（GRANT）**：
  ```sql
  GRANT <权限列表> ON [TABLE] <表名/视图名> TO <用户/角色列表> [WITH GRANT OPTION];
  ```
  - **常见权限**：`SELECT`、`INSERT`、`UPDATE(列名)`、`DELETE`、`ALL PRIVILEGES`；
  - **`WITH GRANT OPTION` 关键语义**：获得该权限的用户，**还拥有将该权限进一步授予其他用户的权利**；若省略该子句，则被授权者仅可使用权限，不可转授；
- **标准 SQL 收回权限语法（REVOKE）**：
  ```sql
  REVOKE <权限列表> ON [TABLE] <表名/视图名> FROM <用户/角色列表> [CASCADE | RESTRICT];
  ```
  - **`CASCADE`（级联收回）**：将该用户及其所有转授出去的相应权限一并收回；
  - **`RESTRICT`（受限收回）**：若该用户已将权限转授给他人，则系统拒绝执行收回操作，报错返回。

### 标准 SQL 自定义函数与存储过程基础语法
- **SQL 自定义函数定义语法骨架（SQL/PSM 规范）**：
  ```sql
  CREATE FUNCTION <函数名> ( [参数名 参数类型, ...] )
  RETURNS <返回值类型>
  BEGIN
      DECLARE <局部变量名> <变量类型>;
      SELECT <表达式/聚集函数> INTO <局部变量名>
      FROM <表名>
      WHERE <条件表达式>;
      RETURN <局部变量名/表达式>;
  END;
  ```
- **核心语法要素与做题判定准则**：
  1. **返回值类型声明（`RETURNS`，带 S）**：位于参数列表之后、函数体 `BEGIN` 之前，指明函数返回值的数据类型（如 `returns integer`、`returns varchar(20)`）；
  2. **局部变量声明（`DECLARE`）**：在函数体 `BEGIN ... END` 内部，使用 `DECLARE <变量名> <数据类型>` 显式声明函数内部使用的局部变量（如 `declare d_count integer`）；
  3. **查询赋值语句（`SELECT ... INTO`）**：将单行单列的查询结果（如 `count(*)`）直接赋值存入声明的局部变量中（如 `select count(*) into d_count from ...`）；
  4. **函数返回值语句（`RETURN`，无 S）**：在函数执行结束时，使用 `RETURN <表达式/变量>` 返回计算结果。
- **做题高频易错辨析**：
  - **`RETURNS` vs `RETURN`**：函数签名中声明返回类型必须用复数形式 **`RETURNS`**；函数体中返回执行结果必须用动词原形 **`RETURN`**，切勿混淆两者的 S；
  - **局部变量关键字**：在 SQL 函数内部声明局部变量必须使用关键字 **`DECLARE`**，不能在函数体中重复使用 `RETURNS`。

### 数据库访问接口与中间件连接技术（ODBC / JDBC）
- **ODBC（Open Database Connectivity，开放数据库互连）**：微软主导制定的跨平台数据库通用访问 API 规范。基于 C 语言函数库接口，应用程序通过调用统一的 ODBC API，再由各数据库厂商提供的底层 ODBC 驱动程序与具体数据库通信，屏蔽底层不同数据库的实现差异；
- **JDBC（Java Database Connectivity，Java 数据库连接）**：Java 平台访问关系数据库的标准 Java API（中间件技术）。在基于 Web 的 Java 企业级应用与电子商务系统开发中，应用程序通过 JDBC 驱动程序与后台数据库建立连接、执行 SQL 语句，并实现对持久化存储在数据库中的业务对象（如用户账户、商品订单）的高效存取与访问；
- **做题典型选项辨析**：
  - **JDBC**：Java Web 与电子商务应用中访问数据库持久化业务对象的常用标准方式；
  - **XML（可扩展标记语言）**：用于跨平台数据交换、文档格式化和配置文件描述，本身不是数据库连接机制；
  - **CGI（通用网关接口）**：早期 Web 服务器调用外部可执行程序处理 HTTP 请求的接口规范；
  - **COM（组件对象模型）**：微软提出的二进制软件构件组件互操作标准。

## 6. 函数依赖严格数学模型与范式判定深化

### 函数依赖三大基本类型数学定义
设 R(U) 是属性集 U 上的关系模式，X、Y 是 U 的子集：
1. **完全函数依赖（Full Functional Dependency，写作 X → f Y）**：
   - 若 `X → Y`，并且对于 X 的**任何一个真子集 X'`，都有 `X' 不决定 Y`，则称 Y 完全函数依赖于 X；
   - 只有当决定因素 X 是由多个属性组成的复合属性集时，才可能出现部分函数依赖；若 X 仅为单属性，则只要有函数依赖，必定是完全函数依赖。
2. **部分函数依赖（Partial Functional Dependency，写作 X → p Y）**：
   - 若 `X → Y`，但存在 X 的某个真子集 X' 使得 `X' → Y` 成立，则称 Y 部分函数依赖于 X；
   - *例*：在选课关系 (学号, 课程号) 中，`(学号, 课程号) → 姓名`，但由于 `学号 → 姓名` 独立成立，故“姓名”部分函数依赖于主键 `(学号, 课程号)`。
3. **传递函数依赖（Transitive Functional Dependency）**：
   - 若 `X → Y`（`Y ⊈ X`，且 `Y 不决定 X`），并且 `Y → Z`（`Z ⊈ Y`），则称 Z 传递函数依赖于 X；
   - *例*：`学号 → 系名`，`系名 → 系主任`，且系名不能反向决定学号，故“系主任”传递依赖于“学号”。

### 范式判定定理与 BCNF 深度反例解析
- **1NF**：属性值具有原子性，不可再分；
- **2NF**：在 1NF 基础上，**消除非主属性对候选码的部分函数依赖**；
- **3NF**：在 2NF 基础上，**消除非主属性对候选码的传递函数依赖**；
- **BCNF（巴斯-科德范式）**：在 3NF 基础上，**消除主属性对候选码的部分和传递函数依赖**。
  - **BCNF 充要条件**：关系模式 R 中的**每一个非平凡函数依赖 X → Y，其决定因素 X 都必须包含一个候选码（即 X 必须是超键）**！
  - **经典经典 BCNF 反例模型**：
    > 设关系模式 `STJ(S, T, J)`，其中 S 代表学生，T 代表教师，J 代表课程。
    > 每位教师只教一门课，每门课可有多位教师，但每个学生选修某门课只能跟一位特定教师。
    > 函数依赖集：`F = { (S, J) → T, (S, T) → J, T → J }`。
    > **范式分析**：
    > 1. 候选码有两个：`(S, J)` 与 `(S, T)`；
    > 2. 主属性为所有包含在候选码中的属性：S, T, J 全部是主属性，**非主属性个数为 0**；
    > 3. 因为不存在非主属性，所以**直接满足 3NF**；
    > 4. 但是，函数依赖 `T → J` 的决定因素是 `T`，而 `T` 本身不包含候选码（不是超键），存在主属性 J 对候选码 (S, T) 的部分函数依赖！
    > 5. **结论**：`STJ` 属于 3NF，但**绝不属于 BCNF**！

### 模式分解无损连接与保持函数依赖判定
1. **二元分解无损连接充要定理**：
   若关系模式 R 被分解为两个子模式 `R₁` 与 `R₂`，函数依赖集为 F。则分解具有无损连接性的**充要条件**是：
   `(R₁ ∩ R₂) → (R₁ - R₂) ∈ F⁺`  或  `(R₁ ∩ R₂) → (R₂ - R₁) ∈ F⁺`
   （即两子模式的公共属性交集，必须能够函数决定其中某一个子模式的独有属性差集）。
2. **Chase 矩阵测试法**：
   针对多元分解（分解为 3 个及以上子模式），构建属性表矩阵，根据函数依赖逐行合并字母符号，若最终出现至少一行全为 `a` 标记，则该分解为无损连接。

## 7. 封锁相容矩阵与 SQL 高级分组过滤深度辨析

### 共享锁 (S) 与排他锁 (X) 相容矩阵

| 当前已加锁状态 \ 申请锁类型 | **申请共享锁 (S 锁 / 读锁)** | **申请排他锁 (X 锁 / 写锁)** |
|---|:---:|:---:|
| **无锁 (None)** | **允许 (兼容)** | **允许 (兼容)** |
| **已加共享锁 (S 锁)** | **允许 (兼容，并发读)** | **拒绝 (冲突互斥，等待)** |
| **已加排他锁 (X 锁)** | **拒绝 (冲突互斥，等待)** | **拒绝 (冲突互斥，等待)** |

- **封锁死锁解决**：并发事务由于争夺锁资源可能发生死锁（如 T1 持有 A 申请 B，T2 持有 B 申请 A）。解决死锁的常见方法是**超时法**（事务等待超过阈值自动回滚）与**等待图法**（死锁检测算法检测等待环路，选择代价最小的事务强制回滚释放锁）。

### SQL 中 WHERE 与 HAVING 的本质区别与 NULL 值三值逻辑
1. **`WHERE` vs `HAVING` 对比**：
   - **执行时机**：`WHERE` 子句在**数据分组（GROUP BY）之前**执行，针对磁盘基本表中的单行记录逐行进行条件过滤；`HAVING` 子句在**数据分组之后**执行，针对分组聚合统计后的中间结果集进行条件过滤；
   - **能否使用聚合函数**：`WHERE` 子句中**绝对不能使用聚合函数**（如 `WHERE count(*) > 5` 是语法错误！）；`HAVING` 子句中**可以直接使用聚合函数**（如 `HAVING count(*) >= 3`）；
   - **优化准则**：凡是能用 `WHERE` 过滤掉的行，应尽早用 `WHERE` 过滤（减少进入分组的记录数），无法用 `WHERE` 表达的分组统计指标才使用 `HAVING`。
2. **SQL 三值逻辑（Three-Valued Logic）与 NULL 值处理**：
   - SQL 中任何数据与 `NULL` 进行比较（如 `val = NULL` 或 `val != NULL`），其逻辑结果均既非 True 也非 False，而是 **`UNKNOWN`（未知）**；
   - 过滤条件只有在判定结果为严格的 **`TRUE`** 时，该行才会被查询结果保留；
   - 判断某个字段是否为空，必须使用标准谓词：**`IS NULL`** 或 **`IS NOT NULL`**，绝对不能写成 `= NULL`！

## 8. 第九章核心易错陷阱防坑指南与做题检查清单

### 核心易错陷阱防坑指南
1. **BCNF 误判为 3NF**：
   - **陷阱**：看到所有属性都是主属性，就断定达到了最高范式 BCNF；
   - **避坑法宝**：3NF 只约束非主属性不传递依赖；而 BCNF 要求**所有决定因素都必须包含候选码**。若存在 `主属性 → 主属性` 且左侧不是候选码，则只能止步于 3NF。
2. **二元分解无损连接公式方向**：
   - **陷阱**：误以为公共属性要决定全部属性；
   - **避坑法宝**：公共属性交集只需函数决定子模式的**差集**：`R₁ ∩ R₂ → R₁ - R₂` 或 `R₁ ∩ R₂ → R₂ - R₁`。
3. **WHERE 中错用聚合函数**：
   - **陷阱**：在 WHERE 中写 `WHERE AVG(score) > 60`；
   - **避坑法宝**：WHERE 过滤单行不能用聚合，分组统计过滤必须在 GROUP BY 之后使用 `HAVING AVG(score) > 60`。
4. **两段锁协议 (2PL) 误判**：
   - **陷阱**：认为遵守两段锁协议的事务调度一定不会死锁；
   - **避坑法宝**：遵守两段锁协议是保证**并发调度可串行化（正确性）的充分条件**，但**它不能预防死锁**！两段锁协议执行过程中仍然可能发生死锁。

### 第九章做题自检检查清单
- [ ] 见到视图、基本表、文件、索引，先写出外模式、模式、内模式的对应关系，再选答案；
- [ ] 关系代数先问自己“删行还是删列”：条件筛选用 `σ`，字段保留用 `π`；多表题先定位每个条件的所属关系；
- [ ] SQL/关系代数中的字符串必须加单引号；投影序号要以笛卡儿积后的列次序计算；
- [ ] 规范化题先求闭包和候选码，再判断部分依赖、传递依赖或多值依赖，不能直接从范式名称猜选项；
- [ ] 事务隔离级别与封锁协议紧密对应，串行化是最高安全性级别，两段锁协议是保证并发调度可串行化的充分条件；
- [ ] SQL 判空必用 `IS NULL`，分组聚合条件过滤必用 `HAVING`。
