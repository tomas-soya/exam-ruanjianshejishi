# UML 用例图与活动图案例

> 本专题专为软考下午试题三（UML 面向对象分析与设计之“用例图与活动图建模”，15 分必答题）定制。考生拿到用例图或活动图题目后，可直接对照小问设问类型，定位到对应作答卡快速解题。

---

## 1. 用例图与活动图题型识别与通用破题流程

### 1.1 试题识别与题面结构
- **试题位置**：下午试题三（必答题，满分 15 分，高频考查用例图与类图组合）。
- **题面两件套**：
  1. **系统业务角色与流程说明**：详述系统使用者的身份（如作者、审稿人、管理员、银行后端网络），以及用户能够通过系统完成的完整业务目标与可选操作；
  2. **用例图 / 活动图框架**：
     - **用例图**：小人图标（参与者 `A1～An`）、椭圆框（用例 `U1～Un`），以及带箭头的连线（实线关联、带 `<<include>>`/`<<extend>>` 构造型的虚线箭头）；
     - **活动图**：初态实心黑圆、圆角矩形动作节点、分支判断菱形、合并线条及终态同心圆。

### 1.2 考场四步快速解题流水线
```text
第 1 步：找系统边界，定参与者 → 圈出边界外的人、外部系统与硬件设备，理清“是一种”角色泛化
  ↓
第 2 步：按业务目标，定用例名 → 将“用户可以进行某项完整操作”提炼为动宾短语（U1～Un）
  ↓
第 3 步：分必经与条件，断关系 → 每次必经选 <<include>>，条件插入选 <<extend>> 并提取触发条件
  ↓
第 4 步：顺时序流程，补活动图 → 动作节点填动作，分支用菱形标注 [互斥条件]，检查回路与终点
```

## 2. 用例图与活动图核心作答卡

### 作答卡 UML-UC-01：识别系统参与者（外部边界与角色排他法）

- **【题型识别】**：常见设问：“根据说明中的描述，给出图中的参与者 A1～An 的名称。”（通常 3～6 分）。
- **【目标产出】**：参与者名称列表（如 `A1: 作者 (Author); A2: 审稿人 (Reviewer); A3: 银行清算系统 (BankSystem)`）。
- **【题干取证】**：
  - 阅读题干首段与用户权限说明段落，圈出所有在**系统边界之外**与系统交互的角色；
  - 重点关注两类参与者：
    1. **自然人参与者**：如客户、医生、管理员、读者、仓库主管；
    2. **外部系统 / 硬件参与者**：如银行支付网关、短信平台、车载传感器、第三方清算主机。
- **【推理步骤（外部边界排他三步法）】**：
  1. **第一步：系统边界划定（坚决排除系统内部实体）**：
     - **排除内部程序**：系统自身的后台守护进程、自动计费批处理、定时轮询任务**绝不是参与者**（它们是系统内部实现）；
     - **排除内部数据**：数据库管理系统、内部历史档案表**绝不是参与者**；
     - **外部硬件条件**：硬件设备（如扫码枪、IC卡读卡器）仅当其主动向系统输入信号或接收系统控制且脱离系统边界存在时才算参与者；
  2. **第二步：对应小人连线图元**：
     - 观察小人图标 `A1～An` 与各用例椭圆的连线，核对题干中谁有权限发起该项操作；
  3. **第三步：识别参与者泛化层次**：
     - 若小人 `A1` 与 `A2` 之间有一条带空心三角箭头的连线指向 `A3`，说明 `A1` 和 `A2` 是 `A3` 的特殊角色（例如：`VIP客户 ──▷ 客户`，`委员会主席 ──▷ 审稿人`）。
- **【答案形态】**：规范英文名词或中文角色名（如 `Reviewer`, `审稿人`）。
- **【知识依赖】**：[参与者先找边界外角色再画泛化](#51-参与者识别与外部系统建模)。
- **【易错与自检】**：
  - *陷阱*：将系统内部的 Controller、Service 或数据存储表误填为参与者；
  - *自检*：该参与者是否位于系统外部？外部系统（如第三方支付）是否作为参与者被遗漏？

### 作答卡 UML-UC-02：识别与命名用例（动宾短语提炼法）

- **【题型识别】**：常见设问：“根据说明中的描述，给出图中的用例 U1～Un 的名称。”（通常 4～8 分）。
- **【目标产出】**：用例名称列表（如 `U1: 查询余额; U2: 提交论文; U3: 结算订单`）。
- **【题干取证】**：题干中关于各参与者“可以执行哪些操作、达到什么目标”的描述语句。
- **【推理步骤】**：
  1. **主谓宾结构提炼**：将业务句提炼为标准动宾短语：`【参与者】能够【业务动词 + 宾语】`；
  2. **动宾命名硬性规则**：
     - **必须是动宾短语**：如“查询体检记录”、“打印发票”、“提交申报材料”；
     - **严禁纯名词**：写成“体检报告”、“发票”直接判错或扣分；
  3. **用例粒度适中原则**：
     - 用例必须是一个对外部参与者具有独立、完整业务价值的操作目标（如“网购下单”）；
     - 极细的交互碎片（如“输入账号”、“点击确定”、“连接数据库”）不能作为独立用例。
- **【答案形态】**：动宾短语（如 `浏览已提交稿件`、`分配审稿任务`、`打印成绩单`）。
- **【知识依赖】**：[用例由目标确定](#52-用例由谁发起什么目标确定)。
- **【易错与自检】**：
  - *陷阱*：命名写成纯名词；粒度过细将单步界面动作误当用例；
  - *自检*：用例名称是否以动词开头并带宾语？

### 作答卡 UML-UC-03：判定用例间关系与触发条件

- **【题型识别】**：常见设问：“指出用例之间的关系类型（包含/扩展/泛化）” / “简述 <<extend>> 关系的含义及该用例的触发条件。”（通常 4～6 分）。
- **【目标产出】**：关系构造型（`<<include>>`, `<<extend>>`）、箭头方向，以及扩展用例的触发前置条件说明。
- **【题干取证】**：找出描述“必经步骤” vs “在特定异常/分支条件下才发生”的语句。
- **【推理步骤（包含 vs 扩展 vs 泛化三问法）】**：
  1. **第一问：是不是主流程中每次必然调用的公共行为？**
     - 是 → **包含关系（`<<include>>`）**；
     - 箭头方向：**基础用例 ───<<include>>──▶ 被包含的子用例**（虚线箭头指向子用例）；
  2. **第二问：是不是只在满足特定条件、异常或用户主动可选时才插入？**
     - 是 → **扩展关系（`<<extend>>`）**；
     - 箭头方向：**扩展用例 ───<<extend>>──▶ 被扩展的基础用例**（虚线箭头指向基础用例！）；
     - 提取触发条件：从题干中找出触发该动作的前提（如“当收货地址为空时”、“当账户余额不足时”）；
  3. **第三问：是不是同一抽象业务在不同渠道/实现手段上的具体特殊化？**
     - 是（如“支付费用”细化为“微信支付”与“银行卡支付”） → **泛化关系（Generalization）**；
     - 箭头方向：**具体用例 ───▷ 抽象父用例**（实线空心三角指向父用例）。
- **【答案形态】**：
  ```text
  关系类型: <<extend>> (扩展关系)
  箭头方向: 从“添加新地址”指向“选择收货地址”
  扩展执行条件: 用户的常用地址信息为空或用户选择使用新地址。
  ```
- **【知识依赖】**：[包含与扩展判定模型](#53-include-与-extend看触发条件和必经行为)、[用例三关系与类六关系速查](#54-用例关系与类间关系对比速查)。
- **【易错与自检】**：
  - *陷阱*：**`<<extend>>` 的箭头方向极易画反**（必须指向被扩展的基础用例！）；
  - *自检*：包含用例指向子用例（主调子），扩展用例指向父用例（插回主）。

### 作答卡 UML-UC-04：包含 vs 扩展关系快速判定与箭头防反动作卡

- **【题型识别】**：用例连线类型判定与箭头指向专项必得分考点。
- **【秒杀口诀】**：**“无则不完整必是包含，有则更丰富必是扩展；包含主指子，扩展插回主。”**
- **【两大关系深度对照秒杀表】**：

| 对比维度 | 包含关系 (`<<include>>`) | 扩展关系 (`<<extend>>`) |
|---|---|---|
| **核心语义** | 基础用例**不可或缺的组成部分**，每次执行基础用例时**必然调用** | 基础用例本身功能完整，扩展用例仅在**特定条件/异常**下插入 |
| **存在依赖** | 缺少被包含用例，基础用例**无法独立完成**（如“存款”必包含“验密”） | 即使没有扩展用例，基础用例也能独立成功结束（如“结账”可选“领优惠券”） |
| **箭头图元** | 带 `<<include>>` 的虚线箭头：`基础用例 ───▶ 被包含用例` | 带 `<<extend>>` 的虚线箭头：`扩展用例 ───▶ 基础用例`（箭头指向基础！） |
| **触发机制** | 无论何种分支均强制触发 | 必须满足特定的扩展点（Extension Point）或条件判定 |
| **典型真题场景** | 借书、还书、挂失均 `<<include>>` 身份认证 | 网上购书 `<<extend>>` 缺货登记；预订车票 `<<extend>>` 购买保险 |

- **【考场箭头防反自检动作】**：
  - 画完 `<<extend>>` 连线后，问自己一句：“箭头是不是指着原来的大主流程？”如果是，答题正确！若指着附加的旁支动作，立即反转！

### 作答卡 UML-ACT-01：活动图工作流与分支判定

- **【题型识别】**：常见设问：“补充活动图中的活动节点 A1～An” / “给出决策分支上的守卫条件”。
- **【目标产出】**：圆角矩形内的动作短语、菱形引出分支的守卫条件 `[Guard]`。
- **【题干取证】**：题干中对业务操作步骤先后次序、分支判定逻辑（“如果...则...否则...”）及循环回路的叙述。
- **【推理步骤】**：
  1. 按照主成功路径顺序列出动作：`开始 → 动作1 → 动作2 → 决策判断`；
  2. 遇到判定点画菱形，从菱形引出的分支**必须互斥且带有方括号守卫条件**（如 `[信息有效]` 和 `[信息缺失]`）；
  3. 若题干说明“若信息有误，则返回重新填写”，必须从决策菱形引出**回路箭线**指向前序的填写动作节点；
  4. 检查是否有并发泳道或分叉/汇合线条（粗水平黑线），确保并发流程最终汇总到终态。
- **【答案形态】**：动作短语，条件用 `[ ]`（如 `[库存充足]`）。
- **【知识依赖】**：[活动图建模要素](#55-活动图建模核心要素)。
- **【易错与自检】**：
  - *陷阱*：动作节点写成了名词或角色名；分支条件遗漏方括号 `[ ]`；
  - *自检*：活动图是否有明确的结束节点（同心圆）？循环回路是否正确回溯？

## 3. 典型真题全链路演练与真题锚点

以已验收真题 2021 年下半年试题三（吃金币游戏用例与类图建模）（请在历年真题页面查看） 为例，演示从题面到标准答案的全流程：

### 3.1 题面关键信息提炼
- **业务背景**：某游戏公司开发一款吃金币游戏：
  - 游戏背景为回廊式迷宫（Maze），不同位置设置有墙；
  - 迷宫中有两种机器人（Robos）：小精灵（PacMan）和幽灵（Ghost），小精灵吞吃路径金币且躲避幽灵，幽灵游走并吃掉小精灵；
  - 机器人上有前向传感器（FrontSensor，探测左/右/前方是否有墙）与近距离传感器（ProxiSensor，探测视线内是否有金币或幽灵）；
  - 每个机器人设置有一个计时器（Timer），支持执行预先定义好的定时事件；
  - 建立迷宫：用户可以使用编辑器（Editor）编写迷宫文件，建立自定义迷宫；也可以将迷宫文件导入游戏系统建立自定义迷宫。
- **图示结构**：图 3-1 给出用例图（包含用例 U1～U3 及与“建立迷宫”、“操作机器人”的关系连线）；图 3-2 给出初始类图（包含待填类 C1～C4）。

### 3.2 逐小问推导演练
- **问题 1（识别与命名用例 U1～U3）**：
  - **取证**：说明最后一段指出“用户可以使用编辑器（Editor）编写迷宫文件，建立用户自定义的迷宫。将迷宫文件导入游戏系统建立用户自定义的迷宫”；关于机器人操作，说明指出“每个机器人都设置有一个计时器（Timer），用于支持执行预先定义好的定时事件”。
  - **推理**：
    - 针对建立迷宫目标，细分子用例为“编写迷宫文件”与“导入迷宫文件”，分别对应 U1 与 U2；
    - 针对机器人操作，计时器支持的定时操作对应 U3 为“设置计时器”。
  - **答案**：`U1: 编写迷宫文件; U2: 导入迷宫文件（U1 与 U2 可互换）; U3: 设置计时器`（套用 [作答卡 UML-UC-02](#作答卡-uml-uc-02识别与命名用例)）。
- **问题 2（判定用例间关系：泛化与包含）**：
  - **取证与推理**：
    - **U1、U2 与“建立迷宫”**：建立迷宫可通过“编写迷宫文件”或“导入迷宫文件”两种具体途径实现，两者是建立迷宫的具体特化方式，图示为实线三角箭头指向“建立迷宫”，属于**泛化（Generalization）关系**；
    - **U3 与“操作机器人”**：每个机器人执行定时事件依赖于计时器，操作机器人必然包含设置计时器以支持定时事件，属于主用例执行过程中的必经子用例，图示为虚线带 `<<include>>` 构造型箭头，属于**包含（Include）关系**。
  - **答案**：
    - `U1、U2 与“建立迷宫”用例的关系：泛化（Generalization）关系。`
    - `U3 与“操作机器人”用例的关系：包含（Include）关系。`（套用 [作答卡 UML-UC-03](#作答卡-uml-uc-03判定用例间关系与触发条件)）。
- **问题 3（根据系统对象补全类名 C1～C4）**：
  - **取证与推理**：
    - C1 是整个机器人的泛化基类，聚合了传感器与计时器 C2（Timer），故 C1 为 `Robos（机器人）`，C2 为 `Timer（计时器）`；
    - C3 与 C4 继承自 C1（Robos），由题干知两种机器人分别为小精灵与幽灵，故 C3 为 `PacMan（小精灵）`，C4 为 `Ghost（幽灵）`。
  - **答案**：`C1: 机器人（Robos）; C2: 计时器（Timer）; C3: 小精灵（PacMan）; C4: 幽灵（Ghost）`。

## 4. 易错陷阱与交卷自检清单

交卷前花 2 分钟逐项对照以下清单自检：

- [ ] **箭头方向防反**：检查所有的 `<<extend>>` 箭头，是否从**扩展用例指向被扩展的基础用例**？
- [ ] **包含关系必经性**：检查所有的 `<<include>>` 箭头，是否从**基础用例指向被包含的公共子用例**？
- [ ] **扩展条件提取**：题目若问 extend 的触发条件，是否忠实从题干提取了前提（如“未登录”、“信息为空”）？
- [ ] **参与者排除内部类**：参与者是否全都是系统边界外的外部用户或外部接口？
- [ ] **活动图回路与守卫**：活动图的判断菱形引出的分支，是否都带有方括号 `[ ]` 的互斥条件？错误分支是否形成了回到前置状态的闭合回路？

## 5. 支撑知识详解（下钻专区）

### 5.1 参与者识别与外部系统建模
- **自然人参与者**：系统直接使用者（如学生、教务人员、店员）；
- **外部系统参与者**：当本系统与外部主机、银行清算网关、第三方物流或外部数据库交互时，外部系统是独立的参与者（如 ATM 系统中的 `Bank` 银行网络主机）；
- **角色泛化（Generalization）**：子参与者继承父参与者的所有用例权限，子参与者还可以拥有自身特有的用例。

### 5.2 用例由“谁发起什么目标”确定
- 用例表示一个完整系统服务，必须由参与者发起并产生可观察的结果；
- 用例命名严禁写成软件开发内部术语（如“建立数据库连接”、“解析JSON”不是用例）；
- 必须使用人类业务维度的动宾短语（如“在线挂号”、“提交退款申请”、“下载电子发票”）。

### 5.3 `<<include>>` 与 `<<extend>>`：看触发条件和必经行为
| 比较维度 | 包含关系 (`<<include>>`) | 扩展关系 (`<<extend>>`) |
|---|---|---|
| **执行必然性** | **必然执行**：基础用例每次运行必须调用被包含用例 | **条件执行**：仅在特定触发条件成立时才插入执行 |
| **基础用例完整性** | 缺少被包含用例，基础用例逻辑不完整、无法结束 | 基础用例本身完整自洽，即使不扩展也能正常运行 |
| **箭头指向** | **基础用例 ───<<include>>──▶ 子用例**（主调子） | **扩展用例 ───<<extend>>──▶ 基础用例**（插回主） |
| **典型考场案例** | 结账必经“支付费用”；存款必经“验证密码” | 结账时若无地址触发“新增地址”；修改资料时可选“上传头像” |

### 5.4 用例关系与类间关系对比速查
#### 1. 用例之间的 3 种关系
1. **包含（`<<include>>`）**：提取复用，必经调用；
2. **扩展（`<<extend>>`）**：特定条件分支插入，增强行为；
3. **泛化（Generalization）**：空心三角实线，抽象业务的多种具体实现形式。

#### 2. 类之间的 6 种关系（耦合度由弱到强）
`依赖 (Dependency) < 关联 (Association) < 聚合 (Aggregation) < 组合 (Composition) < 泛化/继承 (Generalization) / 实现 (Realization)`
- **聚合（空心菱形）**：弱“整体-部分”，部分可以脱离整体独立存在（如学校与学生）；
- **组合（实心菱形）**：强“整体-部分”，同生同灭，部分不可脱离整体独立存在（如公司与部门）。

### 5.5 活动图建模核心要素
1. **初态与终态**：实心黑圆表示起点，带外环的同心实心圆表示终点；
2. **动作节点（Action State）**：圆角矩形，填动作短语（如“校验身份”、“发送通知”）；
3. **分支与合并（Decision & Merge）**：菱形，引出互斥带 `[Guard]` 的分支；
4. **分叉与汇合（Fork & Join）**：粗横黑线，表示并发并行处理分支；
5. **泳道（Swimlanes）**：纵向或横向分区，明确区分各个业务参与部门/系统对不同动作的归属职责。
