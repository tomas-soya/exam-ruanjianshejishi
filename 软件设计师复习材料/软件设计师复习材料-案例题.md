# 1. 案例分析 45 分极速通关应试攻略（田忌赛马·风险预算版）

> [!TIP] **先把“保底分”改成“风险预算”**
> 1. **目标仍是 45 分**：应用技术满分 75 分，全国一般合格标准按满分 60% 执行时即为 45 分。冲刺阶段不需要追求满分，但模拟训练应争取稳定达到 **48～52 分**，给临场波动留出安全垫。
> 2. **2026 年时间规则已变化**：初、中级资格的“基础知识 + 应用技术”两科连考，总作答时长 240 分钟；基础知识最短 90 分钟、最长 120 分钟，节余时长可用于应用技术。因此应用技术实际可用时间是 **120～150 分钟**，不是固定 150 分钟。选择题已有把握时，可在不牺牲正确率的前提下争取约 90～100 分钟完成第一科。
> 3. **分数区间不是统计学保证**：本仓库 2024 年两场为题库精选组卷，2016～2023 年材料也标注为平台试题集合、统考身份待逐项核验。下表用于制定训练优先级，不代表真实考试中“必拿”或“保底”分。
> 4. **考场顺序按题型和个人强弱动态决定**：不要死记“1→3→5→2→4”。进入应用技术后先快速浏览题面，优先做自己最稳定的高收益题，把算法等容易超时的题放到后段并设置止损线。
>
> 2026 年连考规则参考：[南京市工业和信息化局《2026 年下半年计算机软件资格考试南京考区考试安排》](https://gxj.nanjing.gov.cn/njsjjhxxhwyh/202609/t20260924_5916907.html)。

## 1. 案例五大题型性价比与“田忌赛马”得分蓝图

| 题型 | 历年材料中的主要拿分点 | 冲刺定位 | 建议训练目标 | 熟练后上限 |
|---|---|---|:---:|:---:|
| **DFD** | 实体/存储识别、缺失数据流、父子平衡、数据流组成 | **固定主粮仓**：题型结构最稳定，优先练到低失误 | **10～13 分** | 15 分 |
| **Java 设计模式** | 类图角色、接口/继承、成员声明、构造/实例化、委托调用 | **固定主粮仓**：模板化程度高，但空位数量并非固定为 5 | **9～12 分** | 15 分 |
| **UML** | 用例/类名、多重度、属性方法、关系与模式识别 | **候选第三粮仓**：与数据库做真题测速后择强 | **8～12 分** | 15 分 |
| **数据库** | E-R 联系、关系模式、主外键、范式与需求扩展 | **候选第三粮仓**：按给分点取舍，不按“小问编号”机械截断 | **8～11 分** | 15 分 |
| **算法** | 算法思想/复杂度/稳定性/结果推演、代码浅层空位 | **限时扫分区**：先拿非代码分，再尝试明显代码空 | **2～5 分 + 奖金分** | 15 分 |

> **风险预算的正确用法**
> - 不再使用“DFD 13 + UML 12 + Java 11 = 36，所以数据库再拿 10 就稳过”的乐观叠加。
> - 一个更保守的起点可以是：DFD 11 + Java 10 + UML/数据库强项 10 + 另一门 8 + 算法 3 = **42 分**。
> - 因此模拟训练不能只追求“算出来刚好 45”，而应把可重复成绩推到 **48～52 分**；这 3～7 分才是真正的安全垫。
> - UML 与数据库谁是第三粮仓，不由题号决定：连续做 2～3 套限时真题，谁单位时间得分更高、波动更小，就优先谁。

## 2. 三大极速攻坚战术（风险预算版）

### 战术一：先锁定两个固定主粮仓——DFD + Java 设计模式

1. **DFD：目标 10～13，熟练后冲 15**
   - 优先拿实体/存储识别与缺失数据流，这些小问最适合通过“题干—图形对账”训练稳定性。
   - 父子平衡、加工逻辑、数据流组成等最后一问并不总是送分，不能把接近满分写入“保底预算”。
   - 训练时必须写完整三元组“数据流名称、起点、终点”，并核对实体—加工—存储之间的合法连接。
   - 对应：[结构化分析与设计](#结构化分析与设计案例数据流图dfd)。

2. **Java 设计模式：目标 9～12，熟练后冲 15**
   - “五大空位法”应理解为 **五类常见空位**，不是“每卷固定五个空”。仓库材料中已经存在 6 个空的题目。
   - 优先掌握：接口/继承声明、多态成员声明、构造与初始化、对象创建、委托调用；再用类图角色关系校验类型和方法名。
   - 训练目标不是“背完 23 种模式”，而是看到类图后能迅速确定角色关系，并能从上下文还原常见 Java 语句。
   - 对应：[面向对象设计模式与 Java/C++ 实现](#面向对象设计模式与-javac-实现案例)。

### 战术二：UML / 数据库真题测速，选出第三粮仓

- 用 2～3 套历年材料分别限时做 UML 与数据库，记录“得分 / 分钟”和错误类型。
- **UML 若更强**：重点练用例/类名映射、多重度、include/extend、属性方法和模式识别。
- **数据库若更强**：重点练 E-R 联系、多重度、关系模式、主外键和常见范式。
- 数据库尤其不要执行“只做前两问”的机械策略：历年材料中前两问合计分值并不稳定，有的只有 7～9 分。正确做法是 **先扫全题，再按给分点难度取舍**；第三问中若有简单主外键、局部扩展或范式判断，仍应继续拿分。
- 对应：[UML 类图与面向对象分析](#uml-类图与面向对象分析案例)、[数据库设计与关系模式](#数据库设计与关系模式案例)。

### 战术三：算法题先扫非代码分，再设 15～20 分钟止损线

1. **先扫非代码小问**：算法思想、时间/空间复杂度、稳定性、给定实例的结果等，能直接判断的先写。
2. **再扫代码浅层空位**：循环初值/边界、数组下标、明显状态转移、返回值等；看得出就填。
3. **不要预记“4～6 分”**：历年材料并非每套都有“算法策略 + 复杂度”两项固定送分，有的卷子复杂度只有 2 分，甚至没有独立的策略名称得分点。
4. **硬止损**：算法累计投入 15～20 分钟后，如果继续阅读代码不能明显增加得分，就标记未完成处并撤出，把时间留给前三/四个更稳定模块的补漏与检查。
5. 对应：[算法设计与分析](#算法设计与分析案例)。

## 3. 考场实战顺序与弹性时间管理

**第一原则：应用技术时间 T = 240 - 基础知识实际用时，因此 T 在 120～150 分钟之间。** 不再按固定 150 分钟硬套时间表。

推荐的题型顺序是：

~~~text
先快速浏览全卷（约 3～4 分钟）
→ DFD（通常优先）
→ Java / UML / 数据库三者按个人模拟成绩从强到弱
→ 算法放后段，15～20 分钟止损
→ 回到所有标记题与格式检查
~~~

> 如果模拟结果显示 DFD 并非你的稳定强项，也不要为了“题号传统”硬守顺序；原则始终是 **单位时间得分 + 波动最小**。

**当应用技术有约 150 分钟时：**

| 阶段 | 建议预算 |
|---|---:|
| 快速浏览、标记强弱题 | 4 分钟 |
| DFD | 24 分钟 |
| Java/UML/数据库最强项 | 24 分钟 |
| 第二强项 | 22 分钟 |
| 第三项 | 23 分钟 |
| 算法 | 最多 18 分钟 |
| 回防、补空、格式与交卷检查 | **35 分钟** |

**当应用技术只有约 120 分钟时：**

| 阶段 | 建议预算 |
|---|---:|
| 快速浏览、标记强弱题 | 3 分钟 |
| DFD | 20 分钟 |
| Java/UML/数据库最强项 | 20 分钟 |
| 第二强项 | 18 分钟 |
| 第三项 | 18 分钟 |
| 算法 | 最多 14 分钟 |
| 回防、补空、格式与交卷检查 | **27 分钟** |

这些数字是“上限预算”而不是强制铃声：某题提前完成，就把时间转移给标记题或检查；某题超过预算仍没有明显新增得分，就立即撤出。

## 4. 考前极速冲刺执行法（3～5 天）

- **Day 1：诊断 + 选第三粮仓**  
  选 2 套材料，分别限时做 DFD、Java、UML、数据库、算法的关键小问。记录实际得分、耗时和错误类型；当天结束前确定“DFD + Java + UML/数据库较强者”的 **2+1 主攻结构**。

- **Day 2：固定粮仓提稳定性**  
  专攻 DFD + Java。DFD 重点把实体/存储/补流做到低失误；Java 用类图角色还原代码，覆盖至少 3 种不同设计模式。目标不是刷数量，而是让同类错误不重复出现。

- **Day 3：第三粮仓 + 弱项最低可用能力**  
  主攻 UML/数据库中的强项；弱项只保留高性价比基本功。算法只练“先扫非代码分 + 明显代码空 + 15～20 分钟撤退”。

- **Day 4（有 4～5 天时）：第一次完整模拟**  
  按真实连考思路控制时间。如果基础知识已经较稳，可按 90～100 分钟完成第一科、给应用技术留下约 140～150 分钟的节奏模拟。应用技术不按题号，按“浏览 → 强项优先 → 算法止损 → 回防”执行。

- **Day 5（有 5 天时）：错因回炉 + 第二次模拟**  
  只修第一次模拟中真正丢分的动作：漏看限定词、图文对账错误、多重度方向错、主外键遗漏、Java 类型/方法名错、算法超时等。第二次完整模拟的目标是 **稳定达到 48～52 分，而不是偶然碰到 45 分**。

# 结构化分析与设计案例：数据流图（DFD）

> 本专题专为软考下午试题一（数据流图 DFD，15 分必答题）定制。考生拿到试题后，可依据具体小问设问类型，直接定位对应的作答卡快速展开作答。

---

## 1. DFD 题型识别与考场通用破题流程

### 1.1 试题识别与题面结构
- **试题位置**：下午试题一（必答题，满分 15 分）。
- **题面三件套**：
  1. **系统业务说明**：按段落陈述系统的外部参与者、核心功能处理逻辑、持久化记录要求及数据流转过程；
  2. **图 1 顶层 DFD（环境图）**：将整个系统视为单一加工（编号通常为 0），呈现系统与外部实体之间的宏观输入与输出；
  3. **图 2 细化 0 层 DFD（或局部 1 层/2 层图）**：将系统分解为若干具体子加工（P1~Pn）、数据存储（D1~Dn）及内部数据流。

### 1.2 考场四步快速解题流水线
```text
第 1 步：扫视说明，划定边界 → 圈出系统外角色（外部实体）与系统内静态文件（数据存储）
  ↓
第 2 步：父子对照，平衡检查 → 比对顶层图与 0 层图边界数据流，锁定缺失或名称不一致的数据流
  ↓
第 3 步：紧扣动词，推演内部 → 依据业务说明中“查询/保存/通知”动词，为内部加工补齐输入与输出
  ↓
第 4 步：闭环核对，规避陷阱 → 检查连线合法性（严禁非法直连），复核是否有黑洞/奇迹/灰洞
```

## 2. DFD 核心作答卡

---

### 作答卡 DFD-01：识别外部实体

- **【题型识别】**：常见设问：“使用说明中的词语，给出图中的实体 E1～En 的名称。”（通常 3～5 分）。
- **【目标产出】**：实体编号对应的名称列表（如 `E1: 客户; E2: 采购部门; E3: 库房`）。
- **【题干取证】**：
  - 重点阅读业务说明的前两段及各功能描述句的主语/宾语；
  - 寻找位于系统边界之外、与系统发生信息交互的**人（如经理、客户、会员）**、**外部机构/部门（如供应商、库房、财务部）**或**外部系统/第三方平台（如证券交易中心、银行接口、天气预报服务）**。
- **【推理步骤】**：
  1. 查看图 1 顶层图中各矩形框 `E1～En` 连接的数据流流向；
  2. 若某实体向系统发送“订单/请求/申请”，或系统向其输出“报表/通知/确认信息”，在题干中定位该输入输出句的发送者或接收者；
  3. 核对实体个数与题干角色一一对应，排除系统内部的子模块或管理人员。
- **【答案形态】**：严格忠实于题干原词，写名词短语（如“证券交易中心”、“居民”）。
- **【知识依赖】**：[四类元素识别与系统边界](#51-从题干拆出数据流图的四类元素)。
- **【易错与自检】**：
  - *陷阱*：误将系统内部的加工（如“订单管理员”）或内部数据表当作外部实体；
  - *自检*：该实体是否脱离本系统而独立存在？若是系统内功能，绝不能填为外部实体。

---

### 作答卡 DFD-02：识别数据存储

- **【题型识别】**：常见设问：“使用说明中的词语，给出图中的数据存储 D1～Dn 的名称。”（通常 3～5 分）。
- **【目标产出】**：存储编号对应的名称列表（如 `D1: 订单记录; D2: 库存表`）。
- **【题干取证】**：
  - 在题干说明中圈出带“**记录、文件、表、档案、库、清单**”等体现持久化保存的名词短语；
  - 观察 0 层图中连接数据存储 `D1～Dn` 的数据流（流入该存储表示“保存/写入”，流出表示“读取/查询”）。
- **【推理步骤】**：
  1. 顺着指向 `Di` 的输入数据流反查：是哪个加工在“记录/更新/保存”什么信息？
  2. 顺着从 `Di` 引出的输出数据流反查：是哪个加工在“查询/对照/统计”什么信息？
  3. 结合两端数据流的语义，匹配题干中最贴切的持久化文件名词。
- **【答案形态】**：严格采用名词短语，绝不使用动宾短语。
- **【知识依赖】**：[数据存储命名原则](#52-数据存储命名与读写规则)。
- **【易错与自检】**：
  - *陷阱*：将加工名称填在数据存储位置（如误填为“进货处理”、“库存统计”）；
  - *自检*：该项是否能被保存并供后续加工反复查询？若包含动词操作，立即修正为对应名词。

---

### 作答卡 DFD-03：补充缺失数据流

- **【题型识别】**：常见设问：“根据说明和图中的术语，补充图 1-2 中缺失的数据流及其起点和终点。”（通常 4～6 分）。
- **【目标产出】**：三元组形式：`数据流名称 | 起点 | 终点`。
- **【题干取证】**：
  - 取证点 A（父子平衡）：顶层图对外的数据流列表 vs 0 层图边界对外数据流列表；
  - 取证点 B（加工守恒）：题干中明确说明“加工 A 将 X 发送给加工 B / 写入存储 D”，但图中无此连线；
  - 取证点 C（动词方向）：题干中“读取、查询、生成、发送、打印”对应的源和宿。
- **【推理步骤】**：
  1. **先做父子图平衡检查**：对比顶层图与 0 层图，若顶层图有流 `E1 → 系统` 名为“申请单”，而 0 层图 `E1` 到任何加工均无“申请单”流，立即补出 `起点: E1, 终点: 加工Px`；
  2. **再做加工内部数据守恒核查**：排查 0 层图中的每个加工：
     - 若某加工只有输入没有输出（黑洞），或者只有输出没有输入（奇迹），必有漏流；
     - 结合题干描述，该加工根据什么数据生成输出？找出从外部实体或存储到该加工的缺失输入流；
  3. **依据动词确定箭头方向**：
     - 查询/读取：`数据存储 → 加工`；
     - 写入/更新：`加工 → 数据存储`；
     - 提交/请求：`外部实体 → 加工`；
     - 通知/结果：`加工 → 外部实体`。
- **【答案形态】**：建议按清晰表格或分行罗列，必须写清**名称、起点、终点**：
  ```text
  数据流名称: 交易结果通知, 起点: 加工P3(证券交易), 终点: E1(客户)
  数据流名称: 库存查询, 起点: D1(库存记录), 终点: 加工P2(缺货统计)
  ```
- **【知识依赖】**：[顶层图与 0 层图平衡](#53-顶层图与-0-层图必须平衡)、[动词与连线方向对照表](#54-用题干动词校验方向)。
- **【易错与自检】**：
  - *陷阱*：只写了数据流名称，漏写起点或终点；箭头方向颠倒；
  - *自检*：所补数据流的两端中，**是否至少有一端是“加工”**？如果两端都是实体或存储，必错！

---

### 作答卡 DFD-04：加工分解与子图细化规范（含错误流修正）

- **【题型识别】**：常见设问：“给出加工 Pn 细化分解后的子加工 Pn.1～Pn.k 的名称及其输入输出数据流” / “指出图中的错误数据流并说明理由，给出纠正后的数据流。”（通常 3～6 分）。
- **【目标产出】**：
  1. 细化子加工编号、动宾短语名称、局部数据存储与内部数据流；
  2. 错误数据流识别、违背规则理由阐述及纠正方案（删错线、经过加工中介补正线）。
- **【题干取证】**：
  - 定位题干中对某特定复杂业务步骤（如“结算处理”、“核保审核”）的具体子步骤描述；
  - 检查图中所有图元间的直连连线是否违背加工中介铁律；
  - 检查数据流方向是否违背“申请进、通知出、日志存”的业务常理。
- **【推理步骤（加工细化与纠错流水线）】**：
  1. **第一步：子加工编号与动宾命名**：
     - 若父加工为 `P3`，其细化子加工统一编号为 `P3.1`、`P3.2`、`P3.3`；
     - 每个子加工必须使用“动词 + 宾语”命名（如 `P3.1: 校验支付凭据; P3.2: 扣减用户积分; P3.3: 生成对账凭证`），严禁纯名词；
  2. **第二步：父图端点穿透与局部守恒**：
     - 父加工 `P3` 拥有的外部输入流（如“支付凭据”），在子图中必须精确连入承担该起始职责的具体子加工（如 `P3.1`）；
     - 父加工 `P3` 拥有的外部输出流（如“对账单”），在子图中必须由产生该结果的末端子加工（如 `P3.3`）引出；
     - 子加工之间流动的数据流为**内部数据流**，仅在子图内部流转，不穿透到父图；
  3. **第三步：排查“三大非法直连”**：
     - 坚决查杀：`外部实体 ↔ 外部实体` 直连（系统无法感知外部实体之间的私下交互）；
     - 坚决查杀：`外部实体 ↔ 数据存储` 直连（外部实体绝不能越过加工直接读写数据库）；
     - 坚决查杀：`数据存储 ↔ 数据存储` 直连（数据表之间不会凭空自拷贝，必须通过加工搬运）；
  4. **第四步：排查“加工数据守恒黑洞/奇迹”**：
     - **黑洞**：某子加工只有输入流，没有输出流（数据被吞噬）；
     - **奇迹**：某子加工只有输出流，没有输入流（凭空产生数据）；
     - **灰洞**：输入数据不足以产生输出数据（如输入仅有“学号”，输出却包含了“家庭住址与考试成绩”）。
- **【答案形态】**：
  ```text
  【加工细化示例】
  子加工名称: P2.1 验证资格, P2.2 扣除费用, P2.3 打印凭证
  内部数据流: 合格通知 (P2.1 -> P2.2), 扣费凭条 (P2.2 -> P2.3)
  
  【错误数据流纠错示例】
  错误数据流: 规则文件（起点: 外部实体E2，终点: 数据存储D1）
  理由: 外部实体与数据存储之间不能直接相连，数据流两端必须至少有一端是加工。
  纠正方案: 删除该数据流，增加数据流“提交规则”（E2 -> 加工P1）和数据流“写入规则”（加工P1 -> D1）。
  ```
- **【知识依赖】**：[DFD 连线合法性铁律](#55-dfd-连线合法性处理是必要中介)、[加工数据守恒与动宾短语命名](#56-加工数据守恒与动宾短语命名)。
- **【易错与自检】**：
  - *陷阱*：子图细化时自己虚构了外部输入流，导致与父图不平衡；
  - *自检*：子图中所有连向图外的流，其名称和数量是否与父图完全一致？

---

### 作答卡 DFD-05：父子图平衡与数据守恒快速核查卡

- **【题型识别】**：常见设问：“解释图 X（顶层图）和图 Y（0层图）是否保持平衡，若不平衡请说明原因 / 如何保持平衡？”（通常 3～5 分）。
- **【目标产出】**：明确结论（平衡 / 不平衡）+ 差异数据流清单（缺失流/多余流及其端点）+ 保持平衡规范概念。
- **【题干取证】**：对比父图（顶层 DFD）中对应加工（通常为系统加工 0）的所有外接数据流，与子图（0 层 DFD）中与外部实体之间的全部数据流。
- **【推理步骤（父子平衡核对矩阵法）】**：
  1. **构建输入流对账集**：
     - 列出父图中从各外部实体指向系统的输入流集合：`In_parent = { 流名1 (E1 -> 系统), 流名2 (E2 -> 系统), ... }`；
     - 列出子图中从各外部实体指向各子加工的输入流集合：`In_child = { 流名1 (E1 -> P1), 流名2 (E2 -> P2), ... }`；
  2. **构建输出流对账集**：
     - 列出父图中从系统指向各外部实体的输出流集合：`Out_parent = { 流名3 (系统 -> E1), ... }`；
     - 列出子图中从各子加工指向各外部实体的输出流集合：`Out_child = { 流名3 (P3 -> E1), ... }`；
  3. **比对核查与异常分类**：
     - **完全平衡**：`In_parent == In_child` 且 `Out_parent == Out_child`；
     - **子图缺流**：父图有的流子图漏画（最常见，如子图缺少 `E1 -> P1` 的“挂号请求”）；
     - **子图多流**：子图凭空多出连接外部实体的连线；
     - **数据流打包与拆解**：若父图为宏观数据流（如“报销申请包”），子图拆为“发票明细”和“审批单”，若题干明确说明包含关系则视为平衡，否则指出命名不一致。
  4. **给出标准平衡定义阐述**：
     - “分层数据流图中的父图与子图平衡是指，父图中某个加工的输入输出数据流必须与该加工分解后子图的总输入输出数据流在数量、名称和方向上保持完全一致。”
- **【答案形态】**：
  ```text
  判定: 图 1 与 图 2 不平衡。
  原因: 
  1. 顶层图 1 中存在从外部实体 E1 到系统的输入数据流“挂号申请”，但在 0 层图 2 中缺失该输入数据流；
  2. 0 层图 2 中存在从加工 P3 到外部实体 E2 的输出数据流“处方单”，但在顶层图 1 中缺失该输出数据流。
  如何保持平衡: 父图中某个加工的输入输出数据流必须与该加工分解后子图的总输入输出数据流完全一致。应在图 2 中为加工 P1 补充从外部实体 E1 输入的“挂号申请”数据流，并在图 1 中补充从系统到外部实体 E2 的“处方单”数据流。
  ```
- **【知识依赖】**：[顶层图与 0 层图必须平衡](#53-顶层图与-0-层图必须平衡)。

以已验收真题 2024 年下半年试题一（证券交易平台 DFD）（请在历年真题页面查看） 为例，演示从题面到标准答案的全流程：

### 3.1 题面关键信息提炼
- **系统功能说明**：
  1. **开户**：根据客户服务助理提交的开户信息，进行开户，并将客户信息存入客户记录中，账户信息（余额等）存入账户记录中；

  3. **取款**：客户可以从其账户中取款，根据取款金额修改账户余额；

    3. `交易信息（或写入交易记录） | 证券交易（或加工 4） | D3（或交易记录）`（套用 [作答卡 DFD-03](#作答卡-dfd-03补充缺失数据流)）。

## 5. 支撑知识详解（下钻专区）

### 5.1 从题干拆出数据流图的四类元素
| 元素 | 图形符号 | 识别线索 | 考场作用 |
|---|---|---|---|
| **外部实体 (Entity)** | 矩形框 | 客户、供应商、经理、银行系统、库房 | 系统边界外的数据源或宿 |
| **加工 (Process)** | 圆形 / 圆角矩形 | 审核、统计、计算、生成、处理（动宾短语） | 执行数据逻辑变换 |
| **数据存储 (Data Store)** | 双平形线 / 开口矩形 | 订单表、库存文件、档案记录、日志库（名词） | 静态持有持久化数据 |
| **数据流 (Data Flow)** | 命名带箭头的实线 | 订单单据、报表、通知、查询结果、认证数据 | 传递中的数据内容 |

### 5.2 数据存储命名与读写规则
- 必须使用业务名词短语（如“库存记录”、“委托记录”），切忌写成加工名；
- 同一存储可被多个加工反复读写，不因被两个加工访问就画两个独立存储。

### 5.3 顶层图与 0 层图必须平衡
- **平衡原理**：父图中的某个加工分解为子图后，该加工对外的所有输入流与输出流，在子图边界上必须完全保留，不能凭空增删对外数据流。子图内部可以增设仅在子图流转的加工、数据存储及内部数据流。

### 5.4 用题干动词校验方向
| 题干常见动词 | 数据流标准流向 |
|---|---|
| 接收、受理、读取、输入、提取、根据…比对 | `外部实体 / 数据存储 → 加工` |
| 保存、记录、存入、更新、写入、修改 | `加工 → 数据存储` |
| 发送、打印、开具、通知、反馈、呈现、输出 | `加工 → 外部实体` |
| 提交、录入、申报、发起申请 | `外部实体 → 加工` |

### 5.5 DFD 连线合法性：处理是必要中介
- **连线铁律**：数据流的两端中，**至少有一端必须是“加工”**！
- 绝对非法的四类连线：
  1. `外部实体 ──▶ 外部实体`（系统无法感知外部交互）；
  2. `外部实体 ──▶ 数据存储`（实体不能越权读写数据库）；
  3. `数据存储 ──▶ 外部实体`（数据库不会主动向外部输出）；
  4. `数据存储 ──▶ 数据存储`（数据存储之间没有自发的复制能力）。

### 5.6 加工数据守恒与动宾短语命名
- **黑洞（Black Hole）**：加工只有输入流，没有输出流（数据吞噬）；
- **奇迹（Miracle）**：加工只有输出流，没有输入流（凭空产生）；
- **灰洞（Gray Hole）**：输入流的数据项不足以支撑计算出输出流所需的内容；
- 加工必须命名为**动宾短语**（动词+名词，如“验证用户身份”、“生成结算月报”）。

### 5.7 数据字典（Data Dictionary）核心描述符号速查
| 符号 | 语法含义 | 典型案例 |
|:---:|---|---|
| `=` | 被定义为 | `开票信息 = 客户名称 + 税号 + 金额` |
| `+` | 与（顺序连接） | 必选的连续数据项相接 |
| `[ \| ]` | 或（多选一） | `付款方式 = [ 微信 \| 支付宝 \| 现金 ]` |
| `{ }` | 重复（0次至多次） | `{ 选购商品 }` 或 `1{ 选购商品 }50` |
| `( )` | 可选（0次或1次） | `( 附加备注说明 )` |
| `" "` 或 `..` | 基本字符常量 / 范围 | `1..100` 或 `"男" \| "女"` |

### 5.8 结构化分析五大核心工具
1. **数据流图（DFD）**：建模系统功能与数据流转视图；
2. **数据字典（DD）**：对 DFD 中所有图元数据项给出精确规范定义；
3. **结构化语言**：采用受限控制结构（顺序、选择、循环）表达加工算法；
4. **判定表（Decision Table）**：在条件复杂组合时，清晰表达条件与动作对应关系；
5. **判定树（Decision Tree）**：图形化展示多条件多分支决策逻辑。

### 5.9 外部实体辨析矩阵（内部人员 vs 外部实体）

软考案例试题一中，外部实体识别最容易在“人员角色与系统内部模块”之间产生混淆。下表梳理了高频考查的典型边界辨析：

| 实体分类 | 典型角色 / 示例 | 是否为外部实体 | 判定规则与采分依据 |
|---|---|:---:|---|
| **外部人员** | 客户、读者、患者、考生、会员、供应商销售代表 | **是** | 位于系统之外，通过人机界面向系统提交请求或接收系统产出结果 |
| **系统操作员** | 挂号收费员、图书管理员、仓库管理员、调度员 | **是** | 虽为组织内部员工，但从软件系统边界来看，属于软件的人机交互操作者，向系统录入数据 |
| **外部系统/平台** | 银行支付网关、社保结算系统、短信服务平台、气象数据接口 | **是** | 独立于本系统之外运行的第三方系统，通过接口进行网络数据交换 |
| **外部物理设备** | IC卡读卡器、温湿度传感器、条码扫描枪、打印机 | **是** | 硬件接口设备，作为数据的物理输入源或输出目的地 |
| **内部功能模块** | 权限验证模块、报表生成器、自动结算程序 | **否（是加工）** | 系统内部的数据处理逻辑单元，属于 DFD 中的圆圈加工，绝不能当成外部实体 |
| **内部数据表/库** | 用户信息表、订单主表、日志文件、配置档案 | **否（是存储）** | 静态持有持久化数据的容器，属于 DFD 中的数据存储，绝不能当成外部实体 |

### 5.10 16 卷真题高频业务场景语境与动词-宾语数据流命名规范

### 作答卡 DP-01：识别设计模式

- **【题型识别】**：常见设问：“代码中采用了 (n) 设计模式” / “类图展现了哪种经典设计模式？”（通常 2～3 分）。
- **【目标产出】**：GoF 经典设计模式标准中英文名称（如“桥接模式 (Bridge)”、“策略模式 (Strategy)”）。
- **【题干取证】**：
  - 阅读题干开篇的“设计意图说明”；
  - 观察类图中的继承与组合结构。
- **【推理步骤（模式识别三问法）】**：
  1. **第一问：系统面临的核心变化点是什么？**
     - 两个独立变化的维度（如操作系统平台 × 图像格式） → **桥接模式 (Bridge)**；
     - 算法规则需频繁切换与扩展（如打折、计费、排序） → **策略模式 (Strategy)**；
     - 对象的行为随生命周期状态演进而动态变身 → **状态模式 (State)**；
     - 一对多状态变动联动通知（如数据更新多屏同步） → **观察者模式 (Observer)**；
     - 部分与整体的树形层次，叶子与容器一致对待 → **组合模式 (Composite)**；
  2. **第二问：哪个对象集中协调交互，还是对外提供统一高层门面？**
     - 多个平级同事对象互相调用、关系混乱，需要集中协同 → **中介者模式 (Mediator)**；
     - 封装子系统复杂接口，对外提供单一前台接待入口 → **外观模式 (Facade)**；
  3. **第三问：如何创建对象或增强对象？**
     - 成套产品族切换（如换数据库引擎、换UI主题） → **抽象工厂模式 (Abstract Factory)**；
     - 复杂对象分步装配（服务员调度厨师组装套餐） → **生成器模式 (Builder)**；
     - 通过既有对象快速深浅克隆复制新对象 → **原型模式 (Prototype)**；
     - 动态透明地给对象增添额外职责（加头加尾发票） → **装饰模式 (Decorator)**；
     - 已有接口不兼容但需复用老组件 → **适配器模式 (Adapter)**；
     - 撤销与历史状态快照保存 → **备忘录模式 (Memento)**。
- **【答案形态】**：标准中英文名称（如 `桥接模式` 或 `Bridge 模式`）。
- **【知识依赖】**：[16 种设计模式考场速记表](#51-16-种经典设计模式考场速查总表)。

### 作答卡 DP-03：面向对象继承与接口语法填空

- **【题型识别】**：空位位于类声明头部、方法重写头部或纯虚函数声明处。
- **【目标产出】**：继承/实现关键字与父类/接口名称。
- **【推理步骤】**：
  1. **Java 语言规范**：
     - 继承父类：`extends BaseClass`（Java 严格单继承，只能继承一个类）；
     - 实现接口：`implements InterfaceA, InterfaceB`（可同时实现多个接口）；
     - 抽象方法：`public abstract void doAction();`；
  2. **C++ 语言规范**：
     - 公有继承：`: public BaseClass`；
     - 纯虚函数声明：`virtual void doAction() = 0;`；
     - 虚析构函数：`virtual ~BaseClass() {}`。
- **【答案形态】**：
  - Java: `extends MenuComponent`，`implements Cloneable`；
  - C++: `: public Item`，`virtual void print() = 0`。
- **【知识依赖】**：[双语语法静态检查规范](#53-双语语法静态检查六步自检法则)。
- **【易错与自检】**：
  - *陷阱*：Java 错写 `extends A, B`；C++ 继承漏写 `public` 导致变成私有继承。

### 作答卡 DP-04：面向对象多态委托与方法调用代码填空动作卡

- **【题型识别】**：空位位于业务执行方法体内部、状态/策略转换处或容器批量分派点，要求将业务请求委托给聚合持有的成员对象（通常 2.5～3 分/空）。
- **【目标产出】**：精准的方法调用表达式（含被调对象、方法名、传递参数）。
- **【题干取证】**：
  - 查看类图中的聚合/组合实线箭头，锁定当前类持有的**被委托成员变量名**（如 `protected Strategy strategy;` 或 `private State state;`）；
  - 查看被委托接口/抽象类中声明的**多态方法名**及形参列表；
  - 检查当前上下文是否需要将自身传递过去（如 `this`）。
- **【推理步骤（5 大经典空位类型推导流水线）】**：
  1. **类型 1：基类与接口继承/实现空位**：
     - 若后跟普通类/抽象类：Java 填 `extends BaseClass`；C++ 填 `: public BaseClass`；
     - 若后跟接口：Java 填 `implements InterfaceName`；C++ 仍为 `: public InterfaceName`；
  2. **类型 2：抽象方法与虚函数声明空位**：
     - 位于接口或抽象基类中：Java 填 `public abstract 返回类型 方法名(形参);`；C++ 填 `virtual 返回类型 方法名(形参) = 0;`；
  3. **类型 3：构造依赖注入与父类初始化空位**：
     - Java 子类构造首行调用父类构造：`super(参数);` 或保存依赖 `this.strategy = strategy;`；
     - C++ 子类构造必须通过初始化列表传递基类参数：`: BaseClass(参数), member(参数)`；
  4. **类型 4：状态/策略动态切换与环境注入空位**：
     - 状态模式中子状态类触发环境状态流转：`context.setState(new ConcreteState());` 或 `context.setState(this);`；
     - 策略/桥接中装配具体实现算法：`context.setStrategy(strategy);`；
  5. **类型 5：多态集合遍历与批量分派调用空位**：
     - 组合模式与观察者模式中向所有子节点/观察者广播事件：
       - Java: `for (Observer o : observers) { o.update(state); }` 或 `for (Component c : children) { c.operation(); }`；
       - C++: `for (auto it = observers.begin(); it != observers.end(); ++it) { (*it)->update(state); }`。
- **【答案形态】**：
  ```text
  Java 典型答案: strategy.algorithmInterface(data);
  C++ 典型答案: strategy->algorithmInterface(data);
  双向传递示例: visitor.visit(this); 或 imp->doPaint(m);
  ```
- **【知识依赖】**：[16 种设计模式标准双语实现库](#52-16-种设计模式标准双语实现库)。
- **【易错与自检】**：
  - *陷阱*：Java 与 C++ 的解引用符号搞混（Java 均用点号 `.`；C++ 指针变量必须用箭头 `->`）；
  - *自检*：调用的方法名是否与类图中该接口定义的方法名拼写、大小写完全一致？

### 作答卡 DP-05：C++ 与 Java 双语核心填空语法对照速查卡

- **【题型识别】**：面向试题五（Java）与试题六（C++）共用同一套模式语义时的语言级代码填空转换。
- **【目标产出】**：严格遵循对应语言编译规范的代码片段。
- **【双语核心语法对应大表】**：

| 面向对象语言机制 | Java 代码填空标准写法 | C++ 代码填空标准写法 | 考场易错陷阱与自检 |
|---|---|---|---|
| **类继承** | `class B extends A` | `class B : public A` | C++ 漏写 `public` 将变成私有继承无法多态 |
| **接口实现** | `class B implements Inter` | `class B : public Inter` | Java 接口用 `implements`，C++ 无单独 interface 关键字 |
| **纯虚/抽象方法声明**| `abstract void action();` | `virtual void action() = 0;` | C++ 纯虚函数尾部必带 `= 0;`，Java 带 `abstract` |
| **子类调用父类构造**| `super(name);`（函数首行） | `: Base(name)`（位于函数头初始化列表）| Java 必须在构造函数第一行，C++ 必须在冒号后 |
| **动态对象创建** | `new ConcreteProduct()` | `new ConcreteProduct()` | C++ `new` 返回指针类型（如 `Product* p = new ...`） |
| **当前对象传参** | `visitor.visit(this);` | `visitor->visit(this);` | 访问者/备忘录模式中常将当前实例指针 `this` 传出 |
| **成员指针/引用调用**| `member.operation();` | `member->operation();` | C++ 只要是指针类型，方法调用必用箭头 `->` |
| **集合容器添加元素**| `children.add(component);` | `children.push_back(component);` | Java 用 `add`，C++ `vector`/`list` 用 `push_back` |
| **集合多态广播遍历**| `for (Item item : list) { item.op(); }` | `for (auto it : list) { it->op(); }` | C++ 迭代器指针注意解引用 |
| **常量与空指针** | `null` | `NULL` 或 `nullptr` | 大小写差异 |

- **【知识依赖】**：[双语语法静态检查六步自检法则](#53-双语语法静态检查六步自检法则)。

### 作答卡 DP-06：双语语法静态检查六步自检

- **【题型识别】**：完成填空后的最终交卷自检动作。
- **【静态检查六步检查表】**：
  1. **单/多继承检查**：Java `extends` 后面是否只有一个类名？
  2. **可见性与签名一致性**：重写的方法名、返回类型与参数列表是否与父类完全一致？访问权限没有被缩小？
  3. **构造链传递**：父类缺少无参构造函数时，子类是否显式调用了 `super(...)`？
  4. **指针箭头与点号**：C++ 指针变量是否严格使用了 `->` 而非 `.`？

  6. **类型强制转换**：Java 的 `clone()` 或容器返回 `Object` 时，是否执行了 `(TargetType)` 强制转换？

## 3. 典型真题全链路演练与真题锚点

以已验收真题 2024 年下半年试题二（桥接模式 Java 实现）（请在历年真题页面查看） 为例，演示从题面到标准答案的全流程：

### 3.1 题面关键信息提炼
- **业务背景**：图像预览程序要求查看 BMP、JPEG 和 GIF 三种格式的文件，且能够在 Windows 和 Linux 两种操作系统上运行。为支持扩展并减少子类数目，系统采用**桥接（Bridge）模式**进行设计。
- **类图与代码骨架**：
  - 左侧为图像抽象化角色 `abstract class Image`（持有 `protected Implementor imp;`，提供 `setImp(Implementor imp)` 与抽象方法 `parseFile(String fileName)`），其子类为 `BMPImage`、`GIFImage` 和 `JPEGImage`；
  - 右侧为实现化角色 `abstract class Implementor`，其子类为操作系统具体绘制实现 `WinImp` 与 `LinuxImp`（均实现 `public void doPaint(Matrix m)`）；
  - `Image` 内部聚合了 `Implementor` 引用。

### 3.2 逐小问推导演练
- **空 (1)：抽象实现基类中的行为声明**：
  - **取证**：类 `Implementor` 是操作系统实现抽象基类，其派生子类 `WinImp` 和 `LinuxImp` 均实现了 `public void doPaint(Matrix m)` 方法；空 (1) 位于 `abstract class Implementor` 内部声明处，注释标注“显示像素矩阵 m”。
  - **推理**：作为抽象基类，必须声明公共绘制方法供多态调用。在 Java 中抽象类声明抽象方法需带 `abstract` 修饰符，且方法签名与参数类型必须与子类实现保持一致。
  - **答案**：`abstract void doPaint(Matrix m)`（套用 [作答卡 DP-03](#作答卡-dp-03面向对象继承与接口语法填空)）。
- **空 (2)：多态委托底层平台绘制像素矩阵**：
  - **取证**：在具体图像类 `GIFImage` 的 `parseFile(String fileName)` 方法中，已解析获得像素矩阵对象 `m`，后接注释“显示像素矩阵 m”。
  - **推理**：父类 `Image` 持有实现化角色引用 `protected Implementor imp`。根据桥接模式思想，具体格式类不直接调用平台 API，而是委托持有的桥接接口进行绘制。
  - **答案**：`imp.doPaint(m)`（套用 [作答卡 DP-05](#作答卡-dp-05委托调用与多态分派代码填空)）。
- **空 (3) 与空 (4)：根据客户端需求实例化具体图像与平台实现对象**：
  - **取证**：`main` 方法注释明确指定“在 Linux 操作系统上查看 demo.gif 图像文件”。
  - **推理**：
    - 图像格式为 GIF，对应抽象子类实例化：空 (3) 填 `new GIFImage()`；
    - 操作系统为 Linux，对应具体实现子类实例化：空 (4) 填 `new LinuxImp()`。
  - **答案**：
    - (3) `new GIFImage()`
    - (4) `new LinuxImp()`（套用 [作答卡 DP-04](#作答卡-dp-04构造链与实例创建代码填空)）。
- **空 (5)：依赖注入装配桥接关系**：
  - **取证**：已创建图像对象 `image` 与平台实现对象 `imageImp`，随后执行 `image.parseFile("demo.gif");`。
  - **推理**：调用解析与绘制前，必须将具体操作系统实现注入到图像抽象对象中。基类 `Image` 提供了 Setter 注入方法 `public void setImp(Implementor imp)`。
  - **答案**：`image.setImp(imageImp)`（套用 [作答卡 DP-05](#作答卡-dp-05委托调用与多态分派代码填空)）。

## 4. 易错陷阱与交卷自检清单

交卷前花 2 分钟逐项对照以下清单自检：

- [ ] **分号遗漏排查**：检查所填代码行末尾是否缺少了必需的分号 `;`？
- [ ] **指针符号核对**：C++ 指针调用是否均写成了箭头 `->`？纯虚函数是否写成了 `= 0;`？
- [ ] **构造函数名称**：构造函数名是否与类名拼写完全一致且没有返回值类型？
- [ ] **克隆类型强转**：Java 调用 `clone()` 后，是否加了具体类型的括号向下强转？
- [ ] **角色颠倒自检**：委托调用时，是委托给持有的依赖对象，而不是将上下文反向操控外部对象？

## 5. 支撑知识详解（16 种设计模式标准双语实现库）

### 5.1 16 种经典设计模式考场速查总表
| 模式名称 | 分类 | 核心解题识别信号 | 典型考场场景 |
|---|---|---|---|
| **桥接模式 (Bridge)** | 结构型 | 抽象与实现分离，两个独立变化的维度 | 跨平台图像渲染（格式 × 操作系统） |
| **组合模式 (Composite)** | 结构型 | 部分—整体树形层次，叶子与容器一致对待 | 多级菜单树、组织架构树、文件目录 |
| **适配器模式 (Adapter)** | 结构型 | 已有类接口不兼容但需复用，包装转换 | 新系统对接老地址库/老支付接口 |
| **装饰模式 (Decorator)** | 结构型 | 动态透明增加职责，用组合替代继承 | 发票加头加尾、数据流多层加密压缩 |
| **外观模式 (Facade)** | 结构型 | 为复杂子系统提供统一的高层接待门面 | 医院前台接待（挂号/门诊/划价一站式） |
| **享元模式 (Flyweight)** | 结构型 | 大量细粒度对象共享，区分内部与外部状态 | 网络围棋黑白棋子（共享颜色，坐标外传） |
| **策略模式 (Strategy)** | 行为型 | 封装一系列可相互替换的算法族，独立变化 | 促销收银打折、不同图书借阅计费规则 |
| **状态模式 (State)** | 行为型 | 行为随生命周期状态改变而改变，消除庞大分支 | 自动售货机流转、航空会员里程升级 |
| **观察者模式 (Observer)** | 行为型 | 一对多依赖，一个对象状态变动自动广播通知 | 实验室环境监控（温度变化多块仪表更新） |
| **中介者模式 (Mediator)** | 行为型 | 平级对象复杂网状依赖解耦为星状中介协同 | 多平台电商支付中介、飞机航行调度塔台 |
| **备忘录模式 (Memento)** | 行为型 | 不破坏封装捕获内部状态，支持撤销/恢复 | 编辑器 Undo/Redo、历史快照恢复 |
| **命令模式 (Command)** | 行为型 | 请求发送者与接收者解耦，支持队列/宏命令 | 股票交易委托代理、遥控器按钮宏命令 |
| **模板方法 (Template Method)** | 行为型 | 父类定义算法骨架，子类重写可变步骤 | 应用程序框架（openDocument 固定 5 步） |
| **访问者模式 (Visitor)** | 行为型 | 元素结构稳定，操作随需求不断新增（双分派） | 超市收银员访问不同商品结算（accept/visit） |
| **生成器模式 (Builder)** | 创建型 | 复杂对象分步构建与表现分离，指挥者编排 | 餐厅套餐制作（指挥者服务员调度建造者） |
| **原型模式 (Prototype)** | 创建型 | 通过拷贝/克隆原型创建新对象，避免昂贵初始化 | 大对象高效复制（Java Cloneable / C++ 拷贝构造） |

### 5.2 16 种设计模式标准双语实现库

#### 1. 中介者模式 (Mediator)
- **依赖方向**：同事 → 中介者 → 相关同事，同事之间互不相识。
- **Java 核心实现**：
  ```java
  interface Mediator { void send(String msg, Colleague c); }
  class ConcreteMediator implements Mediator {
      private ConcreteColleague1 c1;
      private ConcreteColleague2 c2;
      public void send(String msg, Colleague c) {
          if (c == c1) c2.notify(msg); else c1.notify(msg);
      }
  }
  ```

#### 2. 模板方法模式 (Template Method)
- **核心骨架（Application / Document 模型）**：
  ```cpp
  void Application::openDocument(const string& name) {
      if (!canOpenDocument(name)) return;
      Document* doc = doCreateDocument(); // 工厂方法延迟到子类
      doc->open(name);
      doc->read(name);
      addDocument(doc);
  }
  ```

#### 3. 访问者模式 (Visitor)
- **双分派机制**：`item.accept(visitor)` ──内部调用──▶ `visitor.visit(this);`。
- **Java 核心实现**：
  ```java
  interface Item { void accept(Visitor v); }
  class Book implements Item {
      public void accept(Visitor v) { v.visit(this); }
  }
  class Cashier implements Visitor {
      public void visit(Book b) { /* 结算图书 */ }
  }
  ```

#### 4. 抽象工厂模式 (Abstract Factory)
- **创建产品族**：
  ```cpp
  class IFactory {
  public:
      virtual IUser* CreateUser() = 0;
      virtual IDepartment* CreateDepartment() = 0;
  };
  ```

#### 5. 观察者模式 (Observer)
- **广播通知机制**：
  ```java
  class EnvironmentData implements Subject {
      private List<Observer> observers = new ArrayList<>();
      public void notifyObservers() {
          for (Observer o : observers) { o.update(temperature, humidity); }
      }
  }
  ```

#### 6. 备忘录模式 (Memento)
- **三角色协作**：
  ```java
  // Originator
  public Memento saveState() { return new Memento(state); }
  public void restoreState(Memento m) { this.state = m.getState(); }
  // Caretaker 管理历史列表
  caretaker.add(originator.saveState());
  originator.restoreState(caretaker.get(index));
  ```

#### 7. 命令模式 (Command)
- **参数化与解耦**：
  ```java
  class ConcreteCommand implements Command {
      private Receiver receiver;
      public ConcreteCommand(Receiver r) { this.receiver = r; }
      public void execute() { receiver.action(); }
  }
  ```

#### 8. 策略模式 (Strategy)
- **算法族可替换**：
  ```java
  class Duck {
      protected FlyBehavior flyBehavior;
      public void performFly() { flyBehavior.fly(); } // 委托调用
  }
  ```

#### 9. 状态模式 (State)
- **状态驱动上下文流转**：
  ```java
  class StartState implements State {
      public void doAction(Context context) {
          context.setState(this); // 驱动环境状态切换
      }
  }
  ```

#### 10. 享元模式 (Flyweight)
- **内外状态分离**：颜色为内部共享状态（存放在享元池），坐标 `(x, y)` 为外部状态由调用端传入。

#### 11. 适配器模式 (Adapter)
- **接口转换**：
  ```cpp
  class Adapter : public Target {
  private:
      Adaptee* adaptee;
  public:
      virtual void request() { adaptee->specificRequest(); }
  };
  ```

#### 12. 生成器模式 (Builder)
- **指挥者调度建造者**：
  ```java
  public void constructMeal(MealBuilder builder) {
      builder.buildBurger();
      builder.buildDrink();
  }
  ```

#### 13. 装饰模式 (Decorator)
- **组合包装增强**：
  ```cpp
  void Decorator::print() {
      component->print(); // 基础调用
      printFooter();      // 装饰增强
  }
  ```

#### 14. 组合模式 (Composite)
- **树形递归多态调用**：
  ```java
  public void print() {
      for (Component c : components) { c.print(); }
  }
  ```

#### 15. 外观模式 (Facade)
- **子系统统一门面**：
  ```java
  public void dispose() {
      registration.handle();
      outpatient.handle();
      pharmacy.handle();
  }
  ```

#### 16. 桥接模式 (Bridge)
- **双维度聚合解耦**：
  ```java
  abstract class Image {
      protected ImageImp imp; // 组合实现接口
      public abstract void parseFile(String name);
  }
  ```

#### 17. 原型模式 (Prototype)
- **克隆机制**：Java 实现 `Cloneable` 接口并调用 `super.clone()`；C++ 提供纯虚 `virtual Prototype* Clone() = 0;` 并调用拷贝构造函数 `return new ConcretePrototype(*this);`。

### 5.3 双语语法静态检查六步自检法则

| 检查项 | Java 关键检查点 | C++ 关键检查点 |
|---|---|---|
| **1. 继承与实现** | 严格单继承 `extends`，多接口 `implements A, B` | `: public BaseClass`（切勿遗漏 `public`） |
| **2. 抽象方法声明** | `public abstract void action();` | `virtual void action() = 0;`（纯虚函数） |
| **3. 析构函数** | 垃圾回收器自动回收，无需析构 | 基类必须声明虚析构：`virtual ~Base() {}` |
| **4. 构造链调用** | 子类首行调用：`super(args);` | 初始化列表传参：`Derived(...) : Base(args)` |
| **5. 指针与引用** | 引用变量一律使用点号 `.` | 指针变量一律使用箭头 `->`，对象使用 `.` |
| **6. 容器遍历** | `for (Component c : list)` 或迭代器强转 | `vector<Item*>::iterator it` 解引用 `(*it)->action()` |

| **责任链模式 (Chain of Resp.)** | 处理者持有下一后继者 `successor` | 无法处理时后继传递 | `if(successor != null) successor.handle(request);` |

## 1. 类图题型识别与考场通用破题流程

### 1.1 试题识别与题面结构
- **试题位置**：下午试题三（必答题，满分 15 分，常考类图、用例图、序列图或状态图）。
- **题面三件套**：

  2. **类图框架（半成品）**：已给出大部分类的矩形框（分三栏：类名、属性、方法），通常在类名 `C1～Cn`、属性方法空缺或多重度连线处留空；
  3. **设问小问**：通常包括“识别类名”、“补充属性与方法”、“判定多重度”、“指出类图所使用的设计模式”以及“SOLID 原则简答”。

### 1.2 考场四步快速解题流水线
```text
第 1 步：划定 BCE 模型，识别类名 → 区分边界界面类、业务控制类与实体数据类，匹配 C1～Cn

  ↓
第 3 步：双向独立，标定关联多重度 → 正向看一次、反向看一次，下界关注“0”还是“1”
  ↓
第 4 步：信息专家，分配方法与关联类 → 谁持有数据谁拥有操作，带有时间/成绩的关联提取为关联类
```

## 2. UML 类图核心作答卡

---

### 作答卡 UML-CD-01：识别与补充类名（名词短语排他推导法）

- **【题型识别】**：常见设问：“根据说明中的描述，给出图中的类 C1～Cn 所对应的类名。”（通常 6～9 分）。
- **【目标产出】**：类编号对应的类名列表（如 `C1: Book; C2: Reader; C3: BorrowRecord`）。
- **【题干取证】**：
  - 在题干中圈出核心业务名词，对照 **BCE（边界-控制-实体）模型**：
    - **边界类（Boundary）**：面向交互的窗体、界面、输入框（如 `LoginForm`, `MainWindow`）；
    - **控制类（Control）**：负责编排用例流程的控制器、管理器（如 `BorrowController`, `OrderManager`）；
    - **实体类（Entity）**：映射数据库或核心持久化业务对象的名词（如 `Book`, `User`, `Account`）。
- **【推理步骤（名词短语排他推导四步法）】**：
  1. **第 1 步：提取业务名词候选池**：通读需求说明，圈出所有表示实体角色、凭证单据、物理设备或管理对象的名词短语（如“借阅人”、“图书”、“押金账单”、“借还书管理器”）；
  2. **第 2 步：排他过滤已知类名**：对比类图中已经给出明确类名的类框，将已出现的类名从候选池中坚决划掉，缩小搜索范围；
  3. **第 3 步：继承层次与架构职责定位**：
     - 若 `Ci` 处于继承树的顶端且有多个派生类，必为概括性父类（如 `Member` 派生出 `VIPMember` 和 `RegularMember`）；
     - 若 `Ci` 处于叶子节点且属性特化，匹配具体子类；
     - 若 `Ci` 包含 `create...()`, `process...()` 等协调方法，通常匹配控制类；
  4. **第 4 步：属性反推与大小写规范**：核对类框内已给出的属性或方法，匹配该名词是否拥有这些特征；若题干给出英文，答案必须严格大驼峰拼写。
- **【答案形态】**：大驼峰英文或中文原词（如 `BorrowRecord`、`借阅记录`）。
- **【知识依赖】**：[BCE 模型与架构划分](#51-面向对象分析-bce-模型边界-控制-实体与架构划分)。
- **【易错与自检】**：
  - *陷阱*：将具体对象实例（如某人的名字）或基本类型属性名误填为类名；
  - *自检*：该类是否具有独立的一组属性和行为？是否未与图中已给出的类名发生重复？

---

### 作答卡 UML-CD-02：提取类属性与方法

- **【题型识别】**：常见设问：“给出类 C 的主要属性和方法” / “给出类 C1～C4 的属性”。
- **【目标产出】**：某类的属性列表（含类型）与方法/操作列表（含参数）。
- **【题干取证】**：题干中对特定业务实体的描述句子，圈出状态描述（属性）与行为动词（方法）。
- **【推理步骤】**：
  1. **共同属性上提原则**：
     - 若多个子类都拥有某个属性（如姓名、身份证号、联系电话），**必须上提到它们的直接共同父类**中；
     - 子类只保留自己独有的属性（如学生类的 `学号`、教师类的 `职称`、VIP会员的 `折扣率`）；
  2. **信息专家原则（方法分配）**：
     - **谁拥有数据，谁提供操作该数据的方法**：计算订单总金额的方法 `calculateTotal()` 应属于 `Order` 类（因为订单持有各明细项的价格与数量）；
     - 集合管理操作（如 `addBook()`, `findBook()`）归属于控制器或目录类，不放在单本图书类中；
  3. **关联非属性铁律**：如果一个类持有对另一个独立业务实体的引用，在 UML 类图中应当画**关联连线**，绝不能作为基本数据类型属性写在属性列表框里。
- **【答案形态】**：
  ```text
  类 AddressBook 的主要属性: 无（通过关联持有 PersonAddress 集合）
  类 AddressBook 的主要方法: addContact(), findContact(), deleteContact()
  类 PersonAddress 的主要属性: name, address, telephone, email
  ```
- **【知识依赖】**：[属性提取与共同属性上提原则](#52-属性提取与继承设计共同属性上提原则)、[信息专家原则](#53-类方法分配原则信息专家与职责驱动设计)。
- **【易错与自检】**：
  - *陷阱*：把特有属性错误上提到父类；把持有其他类的对象引用当成普通属性填入框内；
  - *自检*：检查父类的属性是不是所有子类都确实需要？子类是否没有重复声明父类的已有属性？

---

### 作答卡 UML-CD-03：多重度（Multiplicity）双向推导四步流水线卡

- **【题型识别】**：常见设问：“给出图中关联连线 (1)～(n) 处的多重度标记”。
- **【目标产出】**：标准多重度数值范围（`1`, `0..1`, `1..*`, `0..*`, `*`）。
- **【题干取证】**：在业务说明中寻找修饰两类实体关系的量词（“每个/每位”、“至少一个”、“最多一个”、“可以没有”、“零个或多个”）。
- **【推理步骤（双向独立四步流水线）】**：
  1. **第 1 步：由 A 视角审视 B（定 B 端数值）**：
     - 提问：“一个 A 类的实例，最少和最多可以同时关联多少个 B 类的实例？”
     - 若可无下界为 0，若必须有下界为 1；最多若为 1 则上界为 1，若为多个则上界为 `*`；
  2. **第 2 步：将 A 视角结论标在 B 端**：
     - **切记**：A 视角得出的多重度，**必须严格标注在 B 类的旁边**（被观察对象的端点）；
  3. **第 3 步：由 B 视角审视 A（定 A 端数值）**：
     - 提问：“一个 B 类的实例，最少和最多可以属于或关联多少个 A 类的实例？”
     - 确定 A 端的下界（0 或 1）与上界（1 或 `*`）；
  4. **第 4 步：将 B 视角结论标在 A 端**：
     - **切记**：B 视角得出的多重度，**必须严格标注在 A 类的旁边**。
- **【标准符号规范速查】**：
  - `1`（或 `1..1`）：必须且仅能有 1 个（例如一名员工必须属于且仅属于一个主部门）；
  - `0..1`：至多 1 个，也可以没有（例如一位客户可以没有专属顾问，若有最多 1 位）；
  - `1..*`：至少 1 个，可以有多个（例如一个订单必须包含至少 1 项明细商品，上不封顶）；
  - `0..*`（或 `*`）：可以没有，也可以有任意多个（例如一个部门可以有 0 到多名员工）。
- **【知识依赖】**：[关联多重度判定与业务对照表](#54-关联多重度判定双向独立读法)。
- **【易错与自检】**：
  - *陷阱*：将 A 端看到的结果误写在 A 端自己身上（导致两端数字正好互换反向！）；
  - *自检*：把“一个部门可以有多个员工”的结果写在员工端了吗？把“一名员工必须属于一个部门”的结果写在部门端了吗？

### 作答卡 UML-CD-04：类图中识别设计模式

- **【题型识别】**：常见设问：“图示类图中包含了哪种设计模式？实现的是该系统的哪个功能？ / 请解释选择该模式的原因（不超过 50 字）。”（通常 2～3 分）。
- **【目标产出】**：设计模式标准中英文名称 + 对应功能说明 + 解耦原因。
- **【题干取证】**：观察类图中的骨架特征，以及题干中“需要支持多维度独立变化”、“统一接口屏蔽底层差异”等语句。
- **【推理步骤】**：
  1. **双维度独立变化（解耦抽象与实现）**：类图呈现两个平行的继承层次，中间通过实线聚合/组合桥接 → **桥接模式（Bridge）**；
  2. **整体与部分树形层次（统一叶子与容器）**：类既继承抽象构件，内部又聚合抽象构件集合 → **组合模式（Composite）**；
  3. **算法可自由替换**：环境类持有一个抽象算法接口引用，并在运行时多态调用 → **策略模式（Strategy）**；
  4. **一对多联动通知**：目标类持有观察者列表并在状态变动时遍历通知 → **观察者模式（Observer）**；
  5. **接口转换复用**：适配器类继承或组合老接口，实现新接口 → **适配器模式（Adapter）**。
- **【答案形态】**：
  ```text
  设计模式: 桥接模式 (Bridge)
  实现功能: 实现不同操作系统（Windows/Linux）下多种图像格式（BMP/GIF）的独立渲染。
  选型原因: 将抽象部分与实现部分分离，使两个维度都可以独立扩展，避免类爆炸。
  ```
- **【知识依赖】**：[桥接模式等设计模式在类图中的应用](#55-结构型与行为型模式在类图中的典型应用以桥接模式为例)。

### 作答卡 UML-CD-05：关联类识别与属性提取

- **【题型识别】**：常见设问：“指出图中的关联类及其核心属性” / “为何使用虚线挂在关联线上？”。
- **【目标产出】**：关联类名称、该类持有的动态时效属性。
- **【题干取证】**：找出修饰两两实体关联过程的动态属性（如起止时间、评分、佣金比例、选课成绩）。
- **【推理步骤】**：
  1. 识别两实体间的多对多关联；
  2. 判断某些属性是否“既不单属于 A，也不单属于 B，而是两者关联发生时的产物”；
  3. 将此类属性封装进独立的类中，用**一条虚线连接到关联实线上**。
- **【答案形态】**：
  ```text
  关联类名称: 代销记录 (AgentList)
  核心属性: 起始时间 (startTime), 终止时间 (endTime), 佣金比例 (commissionRate)
  ```

### 作答卡 UML-QA-01：面向对象设计原则与架构简答

- **【题型识别】**：设问：“该设计遵循/违背了面向对象的什么原则？请结合题干说明理由。”
- **【目标产出】**：SOLID 原则全称与针对性理由阐述。
- **【快速诊断表】**：
  - 一个类包揽了过多互不相干的职责 → 违背 **单一职责原则（SRP）**；
  - 增加新业务需要大规模修改已有类的 `switch-case` 代码 → 违背 **开放-封闭原则（OCP）**；
  - 子类重写父类方法后破坏了程序原有的正确性 → 违背 **里氏替换原则（LSP）**；
  - 高层业务类直接 `new` 具体实现类而非依赖接口 → 违背 **依赖倒置原则（DIP）**；
  - 接口定义过于臃肿，迫使实现类写大量空方法 → 违背 **接口隔离原则（ISP）**。
- **【知识依赖】**：[SOLID 原则体系](#57-面向对象设计的核心原则solid-体系)。

## 3. 典型真题全链路演练与真题锚点

以已验收真题 2024 年上半年试题一（数字图书馆系统 UML 类图）（请在历年真题页面查看） 为例，演示从题干到标答的标准作答路径：

### 3.1 题面关键信息提炼
- **业务背景**：某大学拟开发用于管理学术出版物（Publication）的数字图书馆系统，用户可查询或下载已发表的学术出版物。
- **系统核心功能说明**：
  1. **登录系统**：用户（User）仅限于该大学的学生（Student）、教师（Faculty）和其他工作人员（Staff），需账户密码登录；
  2. **查询某位作者（Author）的所有出版物**：保存会议文章（ConfPaper）、期刊文章（JournalArticle）和校内技术报告（TechReport），共性信息包括题目、作者、出版年份；特有信息包括：
     - 会议文章：会议名称、召开时间、召开地点；
     - 期刊文章：期刊名称、出版月份、期号、主办单位；
     - 校内技术报告：学校分配的唯一 ID；
  3. **查询指定会议集（Proceedings）或期刊期次（Edition）的文章**；
  4. **下载出版物**：记录每个出版物被下载的次数；
  5. **查询引用通知**：用户为某出版物注册引用通知，若有新出版物引用则发邮件通知。
- **类图框架**：包含类名待填项 C1～C9，展现人员继承树与出版物继承树，顶部包含 `Subject` 与 `Observer` 依赖结构。

### 3.2 逐小问推导演练
- **问题 1（识别与补充类名 C1～C9）**：
  - **取证与推理**：
    - **人员泛化体系**：外部作者（Author）与内部用户（User，C2）拥有共同基类，抽象为 `Person`（C1）；内部用户（User，C2）进一步派生出学生 `Student`（C3）、教师 `Faculty`（C4）和其他工作人员 `Staff`（C5）；
    - **出版物泛化体系**：C6 为学术出版物根基类 `Publication`，与 Author 存在 `written by` 关联；Publication 进一步派生出三种具体出版物：聚合论文集 Proceedings 的会议文章 `ConfPaper`（C7）、聚合期刊期次 Edition 的期刊文章 `JournalArticle`（C8）、以及具备校内唯一 ID 的校内技术报告 `TechReport`（C9）。
  - **答案**：
    - `C1: Person（或 人）`
    - `C2: User`
    - `C3: Student; C4: Faculty; C5: Staff`（C3、C4、C5 次序可互换）
    - `C6: Publication`
    - `C7: ConfPaper; C8: JournalArticle; C9: TechReport`（套用 [作答卡 UML-CD-01](#作答卡-uml-cd-01识别与补充类名)）。
- **问题 2（提取类属性与共同属性上提）**：
  - **取证与推理**：
    - 说明 2 指出题目、作者、出版年份为所有出版物的共有信息，说明 4 要求记录下载次数；依据共同属性上提原则，这些共性属性全部上提到基类 `Publication（C6）`；
    - 会议文章特有属性：会议名称、召开时间、召开地点，保留在子类 `ConfPaper（C7）`；
    - 期刊文章特有属性：期刊名称、出版月份、期号、主办单位，保留在子类 `JournalArticle（C8）`；
    - 校内技术报告特有属性：ID（或 校内ID），保留在子类 `TechReport（C9）`。
  - **答案**：
    - `C6（Publication）: 题目、作者、出版年份、下载次数`
    - `C7（ConfPaper）: 会议名称、召开时间、召开地点`
    - `C8（JournalArticle）: 期刊名称、出版月份、期号、主办单位`
    - `C9（TechReport）: ID（或 校内ID）`（套用 [作答卡 UML-CD-02](#作答卡-uml-cd-02提取类属性与方法)）。
- **问题 3（类图中识别设计模式与实现功能）**：
  - **取证与推理**：类图顶部明确给出 `Subject` 与 `Observer` 依赖结构，C6（Publication）继承 `Subject`；说明 5 要求“若有新的出版物引用了该出版物，系统将发送电子邮件通知注册该出版物通知的用户”，属于典型的松耦合一对多事件通知机制。
  - **答案**：
    - 设计模式：**观察者模式（Observer）**；
    - 实现功能：**引用通知功能**（若有新的出版物引用了该出版物，系统将发送电子邮件通知注册该出版物通知的用户）（套用 [作答卡 UML-CD-04](#作答卡-uml-cd-04类图中识别设计模式)）。

## 4. 易错陷阱与交卷自检清单

交卷前花 2 分钟逐项对照以下清单自检：

- [ ] **属性上提核对**：父类属性框里的属性，是否确保为所有子类所完全共有？独有属性（如学号、折扣率）是否严格保留在子类中？
- [ ] **关联连线检查**：如果类 A 持有类 B 的引用，是否画成了关联连线？（绝对不能把 `List<B>` 当作基础类型属性写进属性框）。
- [ ] **多重度对端位置**：多重度数值是否标注在了被观察的**对端**？（A 看 B 标在 B 端，B 看 A 标在 A 端）。
- [ ] **下界 0 还是 1**：题目如果说“可以没有借阅记录”、“可以暂时不选课”，多重度下界必须写 `0`（写成 `0..*` 或 `0..1`）。
- [ ] **关联类虚线**：若存在关联类，连线必须是从关联实线上引出的**虚线**，框内包含起止时间或成绩等关联属性。

## 5. 支撑知识详解（下钻专区）

### 5.1 面向对象分析 BCE 模型（边界-控制-实体）与架构划分
1. **实体类（Entity Class）**：
   - 映射现实世界的业务对象，承载持久化数据，生命周期长（如 `User`, `Book`, `Order`）。
2. **控制类（Control Class）**：
   - 协调与控制用例的业务执行流，处理复杂事务编排与逻辑流转（如 `BorrowController`, `SettlementControl`）。
3. **边界类（Boundary Class）**：
   - 负责系统与外部角色（人、外部系统、设备）之间的交互边界，封装报文与界面交互（如 `LoginForm`, `PaymentGateway`）。

### 5.2 属性提取与继承设计：共同属性上提原则
- **上提规则**：两个或多个子类具有相同业务语义且类型一致的属性，必须上提到两者的**直接共同父类**中，消除重复定义；
- **特有下沉规则**：只属于某一个子类角色的特有属性，必须保留在子类中，严禁为了所谓“方便”把特有属性塞给父类；
- **重写保护**：子类继承父类属性后，不要在子类中再次声明同名属性（避免属性遮蔽）。

### 5.3 类方法分配原则：信息专家与职责驱动设计
- **信息专家（Information Expert）**：把职责分配给拥有完成该职责所需全部信息的类；
- 如果计算价格需要读取明细中的单价与数量，那么该计算方法理应分配给持有明细集合的 `Order` 类；
- 避免设计出只含属性没有方法的“贫血模型”，以及包揽所有操作的“上帝控制类”。

### 5.4 关联多重度判定：双向独立读法
| 业务语义描述 | 考场标准多重度写法 |
|---|---|
| 必须且仅有一个（强制单一） | `1`（或 `1..1`） |
| 可有可无，至多一个（可选单一） | `0..1` |
| 至少一个，上不封顶（强制多值） | `1..*`（或 `1..n`） |
| 任意多个，可为空（可选多值） | `0..*`（或 `*`、`0..n`） |
| 固定离散范围（如 1 到 5 项） | `1..5` |

### 5.5 结构型与行为型模式在类图中的典型应用：以桥接模式为例
- **核心定义**：将抽象部分与它的实现部分分离，使它们都可以独立地变化；
- **应用信号**：一个系统存在两个或两个以上独立变化的维度时（如：图形格式维度 vs 操作系统平台维度；图表类型维度 vs 渲染引擎维度）；
- **类图结构**：左侧为抽象类继承体系，右侧为实现接口继承体系，左侧抽象基类持有一个指向右侧实现接口的**聚合关联指针**。

### 5.6 关联类（Association Class）的图形规范与实战模型
- **定义**：当多对多关联本身包含特定属性和行为时，该关联升级为关联类；
- **图形表示**：在连接类 A 与类 B 的实线上，引出一条**虚线**连接一个独立的类矩形框；
- **三大经典模型**：
  1. **房产代销模型**：`房产` ──(实线关联)── `房产经纪`，虚线引出 `代销记录(起始时间, 终止时间, 佣金比例)`；
  2. **学生选课模型**：`学生` ──(实线关联)── `课程`，虚线引出 `选课记录(平时成绩, 期末成绩, 选课学期)`；
  3. **员工项目模型**：`员工` ──(实线关联)── `项目`，虚线引出 `项目任务分配(担任角色, 入组日期, 工时占比)`。

### 5.7 面向对象设计的核心原则（SOLID 体系）
1. **单一职责原则 (SRP)**：一个类应该只有一个引起它变化的原因；
2. **开放-封闭原则 (OCP)**：软件实体应当对扩展开放，对修改关闭；
3. **里氏替换原则 (LSP)**：子类型必须能够替换掉它们的基类型；
4. **依赖倒置原则 (DIP)**：高层模块不应依赖于低层模块，二者都应依赖其抽象；
5. **接口隔离原则 (ISP)**：客户端不应该被迫依赖于它们不使用的接口。

### 5.8 类间 6 大关系图元符号及代码对应速查表

在下午面向对象试题三类图中，类与类之间的连线类型决定了类的角色职责与成员变量定义。耦合度由弱到强依次如下：

| 关系名称 | UML 图元符号标准 | 语义定义与生命周期关系 | 代码实现典型模式 (Java / C++) |
|---|---|---|---|
| **依赖 (Dependency)** | `───▶`（带箭头的虚线） | 弱使用关系，A 的方法以参数、局部变量或返回值使用 B | `void process(B b)` |
| **关联 (Association)** | `─────`（实线，可带单向箭头）| 结构化持有关系，A 长期持有 B 的引用作为成员变量 | `private B b;` |
| **聚合 (Aggregation)** | `◇────`（空心菱形 + 实线） | 整体与部分关系，“部分”可以脱离“整体”独立存在（弱拥有）| `class Team { List<Player> p; }`（成员可脱离团队存在） |
| **组合 (Composition)** | `◆────`（实心菱形 + 实线） | 强整体与部分关系，“部分”的生命周期依附于“整体”（同生共死）| `class Window { Menu menu; }`（窗口销毁菜单同销毁） |
| **泛化 (Generalization)**| `───▷`（带空心三角箭头的实线）| 类继承关系，子类继承父类的属性和方法 | `class Sub extends Super` / `class Sub : public Super` |
| **实现 (Realization)** | `┄┄┄▷`（带空心三角箭头的虚线）| 接口实现关系，具体类实现接口中声明的契约方法 | `class Sub implements Inter` |

## 1. 数据库案例题型识别与通用破题流程

### 1.1 试题识别与题面结构
- **试题位置**：下午试题二（必答题，满分 15 分）。
- **题面三件套**：
  1. **业务场景与实体规则说明**：详细叙述企业业务领域（如汽车销售、医院接种、社区物业、图书租赁），明确各实体的属性、交互业务量词（“一个”、“多个”、“每项”）；
  2. **实体联系图（E-R 图）半成品**：已给出大部分实体矩形、属性椭圆，通常缺少部分联系菱形框、联系基数（1:1、1:n、m:n）或弱实体标注；
  3. **逻辑结构设计（关系模式列表）**：给出从 E-R 图转换后的关系模式框架，通常在属性列表末尾留有 `(a)～(n)` 空缺待补齐，并要求标注主键与外键。

### 1.2 考场四步快速解题流水线
```text
第 1 步：圈数量词，定联系基数 → 通读业务句，双向独立推导 1:1、1:n、m:n 或三元联系
  ↓
第 2 步：对应模式，依规则放外键 → 1:n 在多端加外键，m:n 独立建表加双方主键，弱实体加父键
  ↓
第 3 步：反推事实，定主键与时间 → 问“这一行表达什么事实”，出现多次发生时时间必入复合主键
  ↓
第 4 步：查依赖集，判范式与分解 → 找部分依赖（判2NF）、传递依赖（判3NF），无损建立新表
```

### 作答卡 DB-01：补充 E-R 联系与基数

- **【题型识别】**：常见设问：“根据描述，补充图中的实体联系图（联系名及联系类型）” / “给出联系 (1)～(5) 处的多重度类型”。
- **【目标产出】**：E-R 图补全连线、菱形框，并在两端标清 `1` 或 `m`、`n`（或直接填入基数）。
- **【题干取证】**：
  - 重点阅读描述两两实体交互的句子，圈出“**一个、多名、至少一个、每一台、多次**”等数量约束词；
  - 特别注意涉及三个实体的动词（如“某委托书中由某维修工完成某项目”，同时涉及三方，为**三元联系**）。
- **【推理步骤】**：
  1. **双向独立提问法**：
     - 正向：一个 A 实体最多对应多少个 B 实体？（记在 B 端，如“多”）；
     - 反向：一个 B 实体最多对应多少个 A 实体？（记在 A 端，如“1”）；
     - 组合得到两端基数：`1:n`；
  2. **多元联系辨析**：若一项业务必须由三个实体同时参与且有联系属性（如“派工”有工时），不能画成两个二元联系，必须由一个菱形框同时连向三个实体；
  3. **弱实体与从属联系**：若某实体（如“订单明细”、“邮件附件”）离开父实体无独立意义，画**双边框矩形**，连接两者的菱形画**双边框**。
- **【答案形态】**：联系名写在菱形框内，两端清晰标注 `1`、`n` 或 `m`、`n`。
- **【知识依赖】**：[先由业务数量词确定 E-R 联系](#51-先由业务数量词确定-e-r-联系)、[三元联系判定](#52-三元联系的复合主键与外键判定通用规则)。
- **【易错与自检】**：
  - *陷阱*：连线两端忘记写 `1`、`n`，仅画连线；
  - *自检*：是否漏掉了联系自身特有的属性？（如“购买”联系的“购买日期、数量”）。

### 作答卡 DB-02：补全关系模式属性与外键

- **【题型识别】**：常见设问：“补充下列关系模式中 (a)～(n) 处缺失的属性，并指明外键。”（通常 4～8 分）。
- **【目标产出】**：填空处缺失的属性名称列表，以及明确的外键标注。
- **【题干取证】**：对照 E-R 图中该实体自身自带的属性椭圆，以及通过连线连接的其他实体主键。
- **【推理步骤】**：
  1. **先查实体自身属性**：核对题图上该实体连着的所有椭圆属性，若未在关系模式中列出，优先填入；
  2. **再按 E-R 转换规则安放外键**：
     - **`1:1` 联系**：可在任意一端加入另一端的主键作外键（通常放在有管理/归属职责的多端）；
     - **`1:n` 联系**：**必须在“n”（多）端关系模式中加入“1”端的主键作为外键**；
     - **`m:n` 或三元联系**：必须建立独立联系关系模式，**引入参与各方的主键共同作为外键**，并加入联系自身的特有属性；
     - **弱实体关系模式**：**必须引入强实体（父实体）的主键作为外键**。
- **【答案形态】**：
  ```text
  (a) 处缺失属性: 维修工编号, 维修项目编号, 工时
  外键: 维修工编号 引用 员工(员工编号); 维修项目编号 引用 维修项目(维修项目编号)
  ```
- **【知识依赖】**：[E-R 图转关系模式四大放置规则](#53-e-r-图转关系模式四大放置规则)。
- **【易错与自检】**：
  - *陷阱*：`1:n` 联系把外键错放在了 `1` 端；
  - *自检*：补充完外键后，该关系模式是否能顺利与对端实体表完成 JOIN 连接？

### 作答卡 DB-03：主键与复合主键判定

- **【题型识别】**：常见设问：“指明各关系模式的主键 / 复合主键。”（通常 2～4 分）。
- **【目标产出】**：下划线标明主键，或明确写出主键属性（组）。
- **【题干取证】**：查阅题干中是否有“同一实体在不同时间/日期可反复参与”、“每项记录均有唯一流水号”等描述。
- **【推理步骤】**：
  1. 思考“**这一张表里的一行代表什么客观事实？**”；
  2. 单一实体表通常以其唯一业务标识符（如 `用户ID`、`商品编号`）为主键；
  3. **联系关系表（多对多或多元联系）**：
     - 若实体 A 与 B 之间一生仅关联一次，主键为 `(主键A, 主键B)`；
     - 若实体 A 与 B 在不同时间可反复发生业务（如多次采购、多次接种、多次借阅），**必须将“时间/日期”或“流水序号”并入复合主键**：`(主键A, 主键B, 业务日期)`；
  4. **弱实体表**：复合主键为 `(父实体主键, 弱实体序号)`。
- **【答案形态】**：
  - 文字说明：`派工单的主键为: (委托书编号, 维修工编号, 维修项目编号)`；
  - 下划线标注：`派工单(<u>委托书编号</u>, <u>维修工编号</u>, <u>维修项目编号</u>, 工时)`。
- **【知识依赖】**：[主键从“唯一标识一行事实”反推](#54-主键从唯一标识一行事实反推)。
- **【易错与自检】**：
  - *陷阱*：只选了其中一个外键作为主键；或可多次发生的业务漏掉了时间属性；
  - *自检*：按你选的主键，会不会出现两条记录的主键完全相同？如果会，主键属性必须扩展！

### 作答卡 DB-04：关系模式规范化范式级别判定与无损分解作答卡

- **【题型识别】**：常见设问：“给出关系模式 R 的候选键与函数依赖集” / “判定 R 最高属于第几范式，并详细说明理由” / “将 R 无损分解为满足 3NF 的一组关系模式”。（通常 4～6 分）。
- **【目标产出】**：候选键、范式等级结论（1NF/2NF/3NF/BCNF）、官方采分标准理由句式、无损分解后的关系模式清单及其主外键。
- **【题干取证】**：找出业务描述中决定与被决定的语义规则（如“每位员工拥有唯一姓名，每个部门有唯一经理，部门经理负责审批该部门所有项目”）。
- **【推理步骤（范式判定与分解标准流水线）】**：
  1. **第一步：求候选键**：
     - 利用属性闭包算法，找出能决定全模式属性的最小属性集；
     - 若入度为 0（从未出现在函数依赖右侧），该属性必在候选键中；
  2. **第二步：判定 1NF**：属性值均为不可分割的基本原子项，满足 1NF；
  3. **第三步：判定 2NF（检查是否存在“部分函数依赖”）**：
     - **若候选码为单属性**：绝不可能存在非主属性对码的部分函数依赖，**直接跨过 2NF 检查，自动满足 2NF**；
     - **若候选码为复合属性 `(A, B)`**：检查是否有非主属性只被其中某一个属性决定（如 `A → C`）；若存在，**不满足 2NF，最高属于 1NF**；
  4. **第四步：判定 3NF（检查是否存在“传递函数依赖”）**：
     - 检查是否存在非主属性决定另一个非主属性（即 `候选码 → X → Y`，且 `X` 不包含候选码）；若存在，**不满足 3NF，最高属于 2NF**；若不存在，则满足 3NF；
  5. **第五步：无损分解操作步骤**：
     - **消除部分依赖**：将引起部分依赖的决定因素及被决定的非主属性单独建表（主键为该决定因素）；原复合主键表保留完整依赖的属性；
     - **消除传递依赖**：将传递决定的属性及决定者单独建表（决定者作为主键）；原表中保留该决定者作为外键。
- **【官方规范采分点答题模板】**：
  ```text
  【范式判定理由标准模板】
  结论: 最高属于第 1 范式（1NF）。
  理由: 该关系模式的主键（候选键）为 (人员编号, 小区编号)，非主属性“人员姓名”仅依赖于“人员编号”（存在非主属性对候选键的部分函数依赖，函数依赖为 人员编号 -> 人员姓名），因此不满足 2NF。
  
  结论: 最高属于第 2 范式（2NF）。
  理由: 该关系模式的主键为 房屋编号，非主属性“物业经理”依赖于非主属性“小区编号”（存在非主属性对候选键的传递函数依赖，函数依赖链为 房屋编号 -> 小区编号 -> 物业经理），因此不满足 3NF。
  ```
- **【知识依赖】**：[函数依赖、范式判定与模式规范化分解](#55-函数依赖范式判定与模式规范化分解)。
- **【易错与自检】**：
  - *陷阱*：理由只写“因为不符合2NF定义”，未写出具体的属性名和函数依赖式，导致零分；
  - *自检*：写出的理由中是否明确列出了“候选键是什么、哪一个非主属性对哪一个主键属性构成了部分依赖或传递依赖”？

### 作答卡 DB-05：E-R 联系向关系模式转换规则与外键定位卡

- **【题型识别】**：常见设问：“根据 E-R 图，补充关系模式中的属性并指明外键” / “将 E-R 图中的实体与联系转换为关系模式”。
- **【目标产出】**：关系模式的补全属性清单、外键字段以及被引用的主表和主键。
- **【五大类型联系转换与外键放置标准规则】**：

| E-R 联系类型 | 关系模式转换策略 | 主键 (Primary Key) 设定 | 外键 (Foreign Key) 安放规则 |
|---|---|---|---|
| **1:1 联系** | 可并入任意一方实体模式（通常并入拥有更多关联属性的一方），亦可独立建表 | 若并入则为该实体的主键；若独立建表则任选一方主键为主键 | 并入的一方加入另一端实体的主键作为外键 |
| **1:n 联系** | **必须合并入“n”（多）端实体对应的关系模式**，切勿独立建表 | 多端实体自身原有的主键 | **在“n”（多）端模式中加入“1”端实体的主键作为外键** |
| **m:n 联系** | **必须建立独立的关系模式**，不能并入任何一方实体 | **参与双方实体的主键组合构成复合主键** `(主键A, 主键B)` | 双方主键分别作为外键，引用各自对应的实体表 |
| **多元三元联系** | **必须建立独立的关系模式**，纳入三方主键及联系自身属性 | 三方主键组合构成的复合主键（若有时间可进一步加入业务日期）| 三方实体主键分别作为外键，引用各自实体表 |
| **弱实体联系** | 弱实体必须建立独立模式，其存在完全依赖于强实体 | **`(强实体主键, 弱实体局部序号)` 构成复合主键** | 强实体主键作为外键引用强实体表 |

- **【外键答题规范写法】**：
  ```text
  外键: 
  关系模式 销售记录 中的 客户编号 引用 客户(客户编号);
  关系模式 销售记录 中的 车辆编号 引用 车辆(车辆编号);
  关系模式 员工明细 中的 部门编号 引用 部门(部门编号)。
  ```
- **【知识依赖】**：[E-R 图转关系模式四大放置规则](#53-e-r-图转关系模式四大放置规则)。

### 作答卡 DB-06：新增业务需求模式扩展

- **【题型识别】**：常见设问：“系统现新增如下业务需求...，对原有设计进行修改以实现该需求：给出新增/修改的关系模式及主外键。”（通常 5～7 分）。
- **【目标产出】**：新增的实体模式、新增的联系关系模式，标注完整的主键与外键约束。
- **【推理步骤（扩展三步法）】**：
  1. **第 1 步：提取新增独立实体**：若引入全新业务对象（如“被检测者”、“门店”），先建实体表并设单一主键；
  2. **第 2 步：提取新增业务联系并独立建表**：
     - 若新增业务是多个实体间的动态活动（如“销售”、“检测”、“授课”），**坚决新建独立的联系表**，切勿在旧表追加多值字段；
     - 将各参与方主键作为外键拉入该联系表；
  3. **第 3 步：时间属性扩充复合主键**：
     - 检查同一对象是否可重复参与该业务（如同一客户多次检测、同一车型在多天销售）；若可重复，**必须将“日期/时间”并入复合主键**。
- **【答案形态】**：
  ```text
  新增实体模式: 被检测者(身份证号, 姓名, 性别, 电话), 主键: 身份证号
  新增联系模式: 核酸检测记录(身份证号, 医院编号, 检测日期, 检测结果),
               主键: (身份证号, 医院编号, 检测日期),
               外键: 身份证号 引用 被检测者(身份证号), 医院编号 引用 医院(医院编号)
  ```
- **【知识依赖】**：[业务需求扩展三步法](#56-业务需求扩展与新增关系模式设计三步法)。

### 作答卡 DB-07：弱实体与 ISA 特化联系

- **【题型识别】**：常见设问：“指出图中的弱实体” / “指出特化联系并转换为关系模式”。

### 作答卡 DB-08：分布式数据库特性简答

## 3. 典型真题全链路演练与真题锚点

以已验收真题 2023 年上半年试题二（汽车零件采购系统 E-R 与关系模式）（请在历年真题页面查看） 为例，演示从题干到标答的标准作答路径：

### 3.1 题面关键信息提炼
- **业务背景与需求**：某新能源汽车公司开发汽车零件采购系统：
  1. 记录供应商信息（名称、地址、电话）；
  2. 记录零件信息（编码、名称、价格）；
  3. 记录车型信息（编号、名称、规格）；
  4. 记录零件采购信息：某个车型的某种零件可以从多家供应商采购，某种零件也可以被多个车型采用，某家供应商也可以供应多种零件；还包括采购数量和采购日期。
- **概念与逻辑结构**：
  - 图 1 实体联系图展示供应商、零件、车型三个实体；
  - 关系模式给出：供应商（<u>名称</u>，地址，电话）、零件（<u>编码</u>，名称，价格）、车型（<u>编号</u>，名称，规格）以及待补全的采购（<u>车型编号，供应商名称，(a)</u>，(b)，<u>采购日期</u>）。

### 3.2 逐小问推导演练
- **问题 1（补充 E-R 实体联系图）**：
  - **取证**：需求 4 明确说明“某个车型的某种零件可以从多家供应商采购，某种零件也可以被多个车型采用，某家供应商也可以供应多种零件”，属于典型的三元多对多联系；采购包含联系属性“采购数量”和“采购日期”。
  - **推理**：在车型、零件、供应商三者之间建立多元（三元）联系“采购”，各端的多重度标注均为多（`* : * : *` 或 `n : m : p`），并连接其自身的联系属性。
  - **答案**：在车型、零件、供应商之间补充三元联系“采购”，多重度为 `* : * : *`（或 `n : m : p`），“采购”联系包含属性“采购数量”和“采购日期”（套用 [作答卡 DB-01](#作答卡-db-01补充-e-r-联系与基数)）。
- **问题 2（补充逻辑结构模式空缺并标主外键）**：
  - **取证与推理**：
    - 三元联系转换成关系模式时，属性应包含参与各实体的码及联系本身属性。已给出车型编号、供应商名称与采购日期，对照需求，空缺 (a) 为“零件编码”，空缺 (b) 为联系属性“采购数量”；
    - 同一车型、同一零件可由同一供应商在不同日期多次采购，因此复合主键必须联合“采购日期”；
    - 各实体主键在采购关系中作为外键存在。
  - **答案**：
    - `(a)`：零件编码
    - `(b)`：采购数量（注：(a) 与 (b) 顺序可互换）
    - **主键**：`(车型编号, 供应商名称, 零件编码, 采购日期)`
    - **外键**：`车型编号`（参照车型关系的主键）、`供应商名称`（参照供应商关系的主键）、`零件编码`（参照零件关系的主键）（套用 [作答卡 DB-02](#作答卡-db-02补全关系模式属性与外键)、[作答卡 DB-03](#作答卡-db-03主键与复合主键判定)）。
- **问题 3（新增全国门店车型销售扩展）**：
  - **取证与推理**：
    - 新增独立实体“门店”（属性：编号、地址、电话），主键为编号；
    - 门店与车型之间为多对多联系“销售”（多重度 `* : *`），拥有联系属性“销售数量”、“销售日期”；
    - 独立建立“销售”关系模式：同一门店在不同日期可重复销售同一车型，复合主键必须包含“销售日期”，外键分别引用门店与车型。
  - **答案**：
    1. **实体与联系图补充**：增加实体“门店”（属性：编号、地址、电话）；在“门店”与“车型”之间增加多对多联系“销售”（多重度 `* : *`），联系属性为“销售数量”、“销售日期”。
    2. **新增加的关系模式**：
       - **门店**（<u>编号</u>，地址，电话），**主键**：编号，**外键**：无
       - **销售**（<u>门店编号，车型编号，销售日期</u>，销售数量），**主键**：`(门店编号, 车型编号, 销售日期)`，**外键**：`门店编号`（参照门店关系主键）、`车型编号`（参照车型关系主键）（套用 [作答卡 DB-06](#作答卡-db-06新增业务需求模式扩展)）。

## 5. 支撑知识详解（下钻专区）

### 5.1 先由业务数量词确定 E-R 联系
| 业务描述关键词 | 联系性质 | 两端标注示例 |
|---|---|---|
| 一个 A 对应一个 B；一个 B 对应一个 A | 1:1（一对一） | `A 1 ── 菱形 ── 1 B` |
| 一个 A 拥有多个 B；一个 B 仅属于一个 A | 1:n（一对多） | `A 1 ── 菱形 ── n B` |
| 一个 A 对应多个 B；一个 B 也对应多个 A | m:n（多对多） | `A m ── 菱形 ── n B` |
| 三个实体共同决定某项业务（如供应商-零件-项目） | 三元联系 | 三条线汇聚到一个菱形框 |

### 5.2 三元联系的复合主键与外键判定通用规则
- 当 A、B、C 三个实体共同构成多元联系时：
  - 关系模式结构必须同时包含三个实体的主键及联系特有属性：`联系表(主键A, 主键B, 主键C, 联系属性...)`；
  - 主键A、主键B、主键C 分别作为外键引用对应表；
  - 若在不同时间可重复发生，复合主键扩充为：`(主键A, 主键B, 主键C, 业务日期)`。

### 5.3 E-R 图转关系模式四大放置规则
1. **实体转换**：每个独立实体转换成一个关系模式，其实体标识符直接作为主键；
2. **`1:1` 联系转换**：可在任一端实体模式中加入另一端主键作为外键；
3. **`1:n` 联系转换**：**在“n”端关系模式中加入“1”端的主键作为外键**；
4. **`m:n` 联系转换**：**必须建立独立联系关系模式**，引入双方主键作为外键，两者共同组成复合主键（若需区分重复发生则加入时间属性）。

### 5.4 主键从“唯一标识一行事实”反推
| 关系模式类型 | 这一行事实代表什么 | 主键构成 |
|---|---|---|
| 实体表（如客户、员工） | 一个独立对象 | 单一业务标识符（如 `客户编号`） |
| 单次多对多联系 | 两个实体的一次固定绑定 | 双方主键复合 `(主键A, 主键B)` |
| 周期/时效多对多联系 | 某时间发生的业务事务 | `(主键A, 主键B, 业务日期/流水号)` |
| 弱实体表（从属表） | 某父对象内部的一个子项 | `(父实体主键, 弱实体序号)` |

### 5.5 函数依赖、范式判定与模式规范化分解
- **函数依赖（Functional Dependency）**：若对于关系 R 中的任意两行，当其在属性集 X 上的值相等时，在属性集 Y 上的值也必定相等，则称 X 函数决定 Y，记作 `X → Y`。
- **1NF（第一范式）**：关系中每个属性都是不可分割的原子数据项；
- **2NF（第二范式）**：在 1NF 基础上，**消除非主属性对候选码的部分函数依赖**（所有非主属性完全依赖于候选码）；
  - *判据*：若候选码为单属性，天然是 2NF；若候选码为复合属性，必须检查是否有非主属性只依赖复合码的一部分；
- **3NF（第三范式）**：在 2NF 基础上，**消除非主属性对候选码的传递函数依赖**；
  - *判据*：不存在 `候选码 → X → Y`（其中 X 不能决定候选码，Y 为非主属性）；
- **BCNF（巴斯-科德范式）**：在 3NF 基础上，**消除主属性对候选码的部分和传递依赖**（所有决定因素中都包含候选码）。

### 5.6 业务需求扩展与新增关系模式设计三步法
1. **提取新实体**：独立建实体表，定义单一主键；
2. **提取新联系**：若为多对多业务，建独立联系表，外键引入关联各方主键；
3. **时间复合主键**：可重复业务必须将时间/日期字段并入主键。

### 5.7 弱实体与 ISA 特化联系设计规范
- **弱实体（Weak Entity）**：
  - E-R 图：双边框矩形表示实体，双边框菱形表示标识联系；
  - 模式转换：主键为 `(父实体主键, 弱实体内部序号)`，其中父实体主键同时为外键。
- **特化/泛化联系（ISA）**：
  - 超类与子类用带圆圈折线或“ISA”三角形相连；
  - 子类继承超类所有属性，子类主键直接采用超类主键且作为外键。

### 5.8 分布式数据库核心特性与透明性
- **四大核心特性**：
  1. **共享性**：各网络节点数据在全网透明共享；
  2. **自治性**：各节点数据库由局部 DBMS 自主管理与控制；
  3. **可用性**：多副本容灾，单点崩溃不影响全局；
  4. **分布透明性**：屏蔽底层物理存储与网络细节。
- **三种分布透明性**：
  1. **分片透明**：用户无需了解数据被水平还是垂直切片；
  2. **位置透明**：用户无需了解数据存储在哪个具体网络节点的物理机器上；
  3. **局部映像透明（逻辑透明）**：用户无需了解各局部数据模式与物理组织细节。

### 作答卡 UML-UC-01：识别系统参与者（外部边界与角色排他法）

- **【题型识别】**：常见设问：“根据说明中的描述，给出图中的参与者 A1～An 的名称。”（通常 3～6 分）。
- **【目标产出】**：参与者名称列表（如 `A1: 作者 (Author); A2: 审稿人 (Reviewer); A3: 银行清算系统 (BankSystem)`）。
- **【题干取证】**：
  - 阅读题干首段与用户权限说明段落，圈出所有在**系统边界之外**与系统交互的角色；
  - 重点关注两类参与者：
    1. **自然人参与者**：如客户、医生、管理员、读者、仓库主管；
    2. **外部系统 / 硬件参与者**：如银行支付网关、短信平台、车载传感器、第三方清算主机。
- **【推理步骤（外部边界排他三步法）】**：
  1. **第一步：系统边界划定（坚决排除系统内部实体）**：
     - **排除内部程序**：系统自身的后台守护进程、自动计费批处理、定时轮询任务**绝不是参与者**（它们是系统内部实现）；
     - **排除内部数据**：数据库管理系统、内部历史档案表**绝不是参与者**；
     - **外部硬件条件**：硬件设备（如扫码枪、IC卡读卡器）仅当其主动向系统输入信号或接收系统控制且脱离系统边界存在时才算参与者；
  2. **第二步：对应小人连线图元**：
     - 观察小人图标 `A1～An` 与各用例椭圆的连线，核对题干中谁有权限发起该项操作；
  3. **第三步：识别参与者泛化层次**：
     - 若小人 `A1` 与 `A2` 之间有一条带空心三角箭头的连线指向 `A3`，说明 `A1` 和 `A2` 是 `A3` 的特殊角色（例如：`VIP客户 ──▷ 客户`，`委员会主席 ──▷ 审稿人`）。
- **【答案形态】**：规范英文名词或中文角色名（如 `Reviewer`, `审稿人`）。
- **【知识依赖】**：[参与者先找边界外角色再画泛化](#51-参与者识别与外部系统建模)。
- **【易错与自检】**：
  - *陷阱*：将系统内部的 Controller、Service 或数据存储表误填为参与者；
  - *自检*：该参与者是否位于系统外部？外部系统（如第三方支付）是否作为参与者被遗漏？

### 作答卡 UML-UC-02：识别与命名用例（动宾短语提炼法）

- **【题型识别】**：常见设问：“根据说明中的描述，给出图中的用例 U1～Un 的名称。”（通常 4～8 分）。
- **【目标产出】**：用例名称列表（如 `U1: 查询余额; U2: 提交论文; U3: 结算订单`）。
- **【题干取证】**：题干中关于各参与者“可以执行哪些操作、达到什么目标”的描述语句。
- **【推理步骤】**：
  1. **主谓宾结构提炼**：将业务句提炼为标准动宾短语：`【参与者】能够【业务动词 + 宾语】`；
  2. **动宾命名硬性规则**：
     - **必须是动宾短语**：如“查询体检记录”、“打印发票”、“提交申报材料”；
     - **严禁纯名词**：写成“体检报告”、“发票”直接判错或扣分；
  3. **用例粒度适中原则**：
     - 用例必须是一个对外部参与者具有独立、完整业务价值的操作目标（如“网购下单”）；
     - 极细的交互碎片（如“输入账号”、“点击确定”、“连接数据库”）不能作为独立用例。
- **【答案形态】**：动宾短语（如 `浏览已提交稿件`、`分配审稿任务`、`打印成绩单`）。
- **【知识依赖】**：[用例由目标确定](#52-用例由谁发起什么目标确定)。
- **【易错与自检】**：
  - *陷阱*：命名写成纯名词；粒度过细将单步界面动作误当用例；
  - *自检*：用例名称是否以动词开头并带宾语？

---

### 作答卡 UML-UC-03：判定用例间关系与触发条件

- **【题型识别】**：常见设问：“指出用例之间的关系类型（包含/扩展/泛化）” / “简述 <<extend>> 关系的含义及该用例的触发条件。”（通常 4～6 分）。
- **【目标产出】**：关系构造型（`<<include>>`, `<<extend>>`）、箭头方向，以及扩展用例的触发前置条件说明。
- **【题干取证】**：找出描述“必经步骤” vs “在特定异常/分支条件下才发生”的语句。
- **【推理步骤（包含 vs 扩展 vs 泛化三问法）】**：
  1. **第一问：是不是主流程中每次必然调用的公共行为？**
     - 是 → **包含关系（`<<include>>`）**；
     - 箭头方向：**基础用例 ───<<include>>──▶ 被包含的子用例**（虚线箭头指向子用例）；
  2. **第二问：是不是只在满足特定条件、异常或用户主动可选时才插入？**
     - 是 → **扩展关系（`<<extend>>`）**；
     - 箭头方向：**扩展用例 ───<<extend>>──▶ 被扩展的基础用例**（虚线箭头指向基础用例！）；
     - 提取触发条件：从题干中找出触发该动作的前提（如“当收货地址为空时”、“当账户余额不足时”）；
  3. **第三问：是不是同一抽象业务在不同渠道/实现手段上的具体特殊化？**
     - 是（如“支付费用”细化为“微信支付”与“银行卡支付”） → **泛化关系（Generalization）**；
     - 箭头方向：**具体用例 ───▷ 抽象父用例**（实线空心三角指向父用例）。
- **【答案形态】**：
  ```text
  关系类型: <<extend>> (扩展关系)
  箭头方向: 从“添加新地址”指向“选择收货地址”
  扩展执行条件: 用户的常用地址信息为空或用户选择使用新地址。
  ```
- **【知识依赖】**：[包含与扩展判定模型](#53-include-与-extend看触发条件和必经行为)、[用例三关系与类六关系速查](#54-用例关系与类间关系对比速查)。
- **【易错与自检】**：
  - *陷阱*：**`<<extend>>` 的箭头方向极易画反**（必须指向被扩展的基础用例！）；
  - *自检*：包含用例指向子用例（主调子），扩展用例指向父用例（插回主）。

---

### 作答卡 UML-UC-04：包含 vs 扩展关系快速判定与箭头防反动作卡

- **【题型识别】**：用例连线类型判定与箭头指向专项必得分考点。
- **【秒杀口诀】**：**“无则不完整必是包含，有则更丰富必是扩展；包含主指子，扩展插回主。”**
- **【两大关系深度对照秒杀表】**：

| 对比维度 | 包含关系 (`<<include>>`) | 扩展关系 (`<<extend>>`) |
|---|---|---|
| **核心语义** | 基础用例**不可或缺的组成部分**，每次执行基础用例时**必然调用** | 基础用例本身功能完整，扩展用例仅在**特定条件/异常**下插入 |
| **存在依赖** | 缺少被包含用例，基础用例**无法独立完成**（如“存款”必包含“验密”） | 即使没有扩展用例，基础用例也能独立成功结束（如“结账”可选“领优惠券”） |
| **箭头图元** | 带 `<<include>>` 的虚线箭头：`基础用例 ───▶ 被包含用例` | 带 `<<extend>>` 的虚线箭头：`扩展用例 ───▶ 基础用例`（箭头指向基础！） |
| **触发机制** | 无论何种分支均强制触发 | 必须满足特定的扩展点（Extension Point）或条件判定 |
| **典型真题场景** | 借书、还书、挂失均 `<<include>>` 身份认证 | 网上购书 `<<extend>>` 缺货登记；预订车票 `<<extend>>` 购买保险 |

- **【考场箭头防反自检动作】**：
  - 画完 `<<extend>>` 连线后，问自己一句：“箭头是不是指着原来的大主流程？”如果是，答题正确！若指着附加的旁支动作，立即反转！

---

### 作答卡 UML-ACT-01：活动图工作流与分支判定

- **【题型识别】**：常见设问：“补充活动图中的活动节点 A1～An” / “给出决策分支上的守卫条件”。
- **【目标产出】**：圆角矩形内的动作短语、菱形引出分支的守卫条件 `[Guard]`。
- **【题干取证】**：题干中对业务操作步骤先后次序、分支判定逻辑（“如果...则...否则...”）及循环回路的叙述。
- **【推理步骤】**：
  1. 按照主成功路径顺序列出动作：`开始 → 动作1 → 动作2 → 决策判断`；
  2. 遇到判定点画菱形，从菱形引出的分支**必须互斥且带有方括号守卫条件**（如 `[信息有效]` 和 `[信息缺失]`）；
  3. 若题干说明“若信息有误，则返回重新填写”，必须从决策菱形引出**回路箭线**指向前序的填写动作节点；
  4. 检查是否有并发泳道或分叉/汇合线条（粗水平黑线），确保并发流程最终汇总到终态。
- **【答案形态】**：动作短语，条件用 `[ ]`（如 `[库存充足]`）。
- **【知识依赖】**：[活动图建模要素](#55-活动图建模核心要素)。
- **【易错与自检】**：
  - *陷阱*：动作节点写成了名词或角色名；分支条件遗漏方括号 `[ ]`；
  - *自检*：活动图是否有明确的结束节点（同心圆）？循环回路是否正确回溯？

## 3. 典型真题全链路演练与真题锚点

以已验收真题 2021 年下半年试题三（吃金币游戏用例与类图建模）（请在历年真题页面查看） 为例，演示从题面到标准答案的全流程：

### 3.1 题面关键信息提炼
- **业务背景**：某游戏公司开发一款吃金币游戏：
  - 游戏背景为回廊式迷宫（Maze），不同位置设置有墙；
  - 迷宫中有两种机器人（Robos）：小精灵（PacMan）和幽灵（Ghost），小精灵吞吃路径金币且躲避幽灵，幽灵游走并吃掉小精灵；
  - 机器人上有前向传感器（FrontSensor，探测左/右/前方是否有墙）与近距离传感器（ProxiSensor，探测视线内是否有金币或幽灵）；
  - 每个机器人设置有一个计时器（Timer），支持执行预先定义好的定时事件；
  - 建立迷宫：用户可以使用编辑器（Editor）编写迷宫文件，建立自定义迷宫；也可以将迷宫文件导入游戏系统建立自定义迷宫。
- **图示结构**：图 3-1 给出用例图（包含用例 U1～U3 及与“建立迷宫”、“操作机器人”的关系连线）；图 3-2 给出初始类图（包含待填类 C1～C4）。

### 3.2 逐小问推导演练
- **问题 1（识别与命名用例 U1～U3）**：
  - **取证**：说明最后一段指出“用户可以使用编辑器（Editor）编写迷宫文件，建立用户自定义的迷宫。将迷宫文件导入游戏系统建立用户自定义的迷宫”；关于机器人操作，说明指出“每个机器人都设置有一个计时器（Timer），用于支持执行预先定义好的定时事件”。
  - **推理**：
    - 针对建立迷宫目标，细分子用例为“编写迷宫文件”与“导入迷宫文件”，分别对应 U1 与 U2；
    - 针对机器人操作，计时器支持的定时操作对应 U3 为“设置计时器”。
  - **答案**：`U1: 编写迷宫文件; U2: 导入迷宫文件（U1 与 U2 可互换）; U3: 设置计时器`（套用 [作答卡 UML-UC-02](#作答卡-uml-uc-02识别与命名用例)）。
- **问题 2（判定用例间关系：泛化与包含）**：
  - **取证与推理**：
    - **U1、U2 与“建立迷宫”**：建立迷宫可通过“编写迷宫文件”或“导入迷宫文件”两种具体途径实现，两者是建立迷宫的具体特化方式，图示为实线三角箭头指向“建立迷宫”，属于**泛化（Generalization）关系**；
    - **U3 与“操作机器人”**：每个机器人执行定时事件依赖于计时器，操作机器人必然包含设置计时器以支持定时事件，属于主用例执行过程中的必经子用例，图示为虚线带 `<<include>>` 构造型箭头，属于**包含（Include）关系**。
  - **答案**：
    - `U1、U2 与“建立迷宫”用例的关系：泛化（Generalization）关系。`
    - `U3 与“操作机器人”用例的关系：包含（Include）关系。`（套用 [作答卡 UML-UC-03](#作答卡-uml-uc-03判定用例间关系与触发条件)）。
- **问题 3（根据系统对象补全类名 C1～C4）**：
  - **取证与推理**：
    - C1 是整个机器人的泛化基类，聚合了传感器与计时器 C2（Timer），故 C1 为 `Robos（机器人）`，C2 为 `Timer（计时器）`；
    - C3 与 C4 继承自 C1（Robos），由题干知两种机器人分别为小精灵与幽灵，故 C3 为 `PacMan（小精灵）`，C4 为 `Ghost（幽灵）`。
  - **答案**：`C1: 机器人（Robos）; C2: 计时器（Timer）; C3: 小精灵（PacMan）; C4: 幽灵（Ghost）`。

## 5. 支撑知识详解（下钻专区）

### 5.1 参与者识别与外部系统建模
- **自然人参与者**：系统直接使用者（如学生、教务人员、店员）；
- **外部系统参与者**：当本系统与外部主机、银行清算网关、第三方物流或外部数据库交互时，外部系统是独立的参与者（如 ATM 系统中的 `Bank` 银行网络主机）；
- **角色泛化（Generalization）**：子参与者继承父参与者的所有用例权限，子参与者还可以拥有自身特有的用例。

### 5.2 用例由“谁发起什么目标”确定
- 用例表示一个完整系统服务，必须由参与者发起并产生可观察的结果；
- 用例命名严禁写成软件开发内部术语（如“建立数据库连接”、“解析JSON”不是用例）；
- 必须使用人类业务维度的动宾短语（如“在线挂号”、“提交退款申请”、“下载电子发票”）。

### 5.3 `<<include>>` 与 `<<extend>>`：看触发条件和必经行为
| 比较维度 | 包含关系 (`<<include>>`) | 扩展关系 (`<<extend>>`) |
|---|---|---|
| **执行必然性** | **必然执行**：基础用例每次运行必须调用被包含用例 | **条件执行**：仅在特定触发条件成立时才插入执行 |
| **基础用例完整性** | 缺少被包含用例，基础用例逻辑不完整、无法结束 | 基础用例本身完整自洽，即使不扩展也能正常运行 |
| **箭头指向** | **基础用例 ───<<include>>──▶ 子用例**（主调子） | **扩展用例 ───<<extend>>──▶ 基础用例**（插回主） |
| **典型考场案例** | 结账必经“支付费用”；存款必经“验证密码” | 结账时若无地址触发“新增地址”；修改资料时可选“上传头像” |

### 5.4 用例关系与类间关系对比速查
#### 1. 用例之间的 3 种关系
1. **包含（`<<include>>`）**：提取复用，必经调用；
2. **扩展（`<<extend>>`）**：特定条件分支插入，增强行为；
3. **泛化（Generalization）**：空心三角实线，抽象业务的多种具体实现形式。

#### 2. 类之间的 6 种关系（耦合度由弱到强）
`依赖 (Dependency) < 关联 (Association) < 聚合 (Aggregation) < 组合 (Composition) < 泛化/继承 (Generalization) / 实现 (Realization)`
- **聚合（空心菱形）**：弱“整体-部分”，部分可以脱离整体独立存在（如学校与学生）；
- **组合（实心菱形）**：强“整体-部分”，同生同灭，部分不可脱离整体独立存在（如公司与部门）。

### 5.5 活动图建模核心要素
1. **初态与终态**：实心黑圆表示起点，带外环的同心实心圆表示终点；
2. **动作节点（Action State）**：圆角矩形，填动作短语（如“校验身份”、“发送通知”）；
3. **分支与合并（Decision & Merge）**：菱形，引出互斥带 `[Guard]` 的分支；
4. **分叉与汇合（Fork & Join）**：粗横黑线，表示并发并行处理分支；
5. **泳道（Swimlanes）**：纵向或横向分区，明确区分各个业务参与部门/系统对不同动作的归属职责。

## 1. 序列图题型识别与通用破题流程

### 1.1 试题识别与题面结构
- **试题位置**：下午试题三（必答题，满分 15 分，考查动态交互时序）。
- **题面两件套**：
  1. **对象协同业务描述**：叙述参与者发起请求后，系统内部多个对象之间按时间先后发生的调用、数据传递与返回流程；
  2. **序列图（时序图）框架**：
     - 顶部矩形框（对象生命线，如 `obj:Class`）；
     - 向下垂直延伸的虚线（生命线）；
     - 生命线上的细长矩形框（激活期 / 控制焦点）；
     - 水平消息箭头（同步实心、异步线形、返回虚线、自调用）；
     - 包含守卫条件的组合片段框（`alt`, `opt`, `loop`, `par`）。

### 1.2 考场四步快速解题流水线
```text
第 1 步：查生命线，定位角色 → 明确顶部对象实例与管理类，确认对象创建点（<<create>>）
  ↓
第 2 步：顺垂直时序，自上而下 → 严格按照时间从上往下流逝，绝不跨时序填写方法调用
  ↓
第 3 步：辨箭头类型，规范书写 → 等待结果用实心三角箭头，单向通知用普通箭头，返回用虚线
  ↓
第 4 步：核对片段，自检生命周期 → 互斥分支填 alt，单可选填 opt；复核聚合（空心）与组合（实心）
```

## 2. 序列图核心作答卡

---

### 作答卡 UML-SEQ-01：序列图消息与时序推导

- **【题型识别】**：常见设问：“根据说明中的描述，给出序列图中的消息 (1)～(n) 的名称（或方法调用）。”（通常 4～8 分）。
- **【目标产出】**：按时序排列的方法调用字符串（如 `validateUser(id)`, `queryPrice(itemId)`）。
- **【题干取证】**：
  - 在题干中圈出按步骤发生的交互动词短语（“步骤 1：用户点击提交... 步骤 2：系统查询... 步骤 3：返回确认信息...”）；
  - 关注调用的**发送者生命线**与**接收者生命线**。
- **【推理步骤】**：
  1. 顺着时间线从上到下推进：
     - 找到当前箭头的发送端对象（调用发起者）与接收端对象（调用承载者）；
  2. **方法归属判定**：消息名称必定是**接收端对象所属的类所具备的方法**（如指向 `OrderManager` 的消息应是 `createOrder()`，指向 `PaymentService` 的消息应是 `pay()`）；
  3. **参数传递检查**：前序调用的返回值，常常作为当前调用的实参传入（如根据第 1 步返回的 `userId` 传入 `queryUser(userId)`）；
  4. **四类箭头类型匹配**：
     - **同步调用（阻塞等待）**：**实线 + 实心三角箭头（`──▶`）**；
     - **异步调用（无需等待）**：**实线 + 普通线形箭头（`──>`）**；
     - **返回消息**：**虚线 + 普通线形箭头（`◀--`）**；
     - **自身调用**：折回自身生命线的箭头。
- **【答案形态】**：方法调用表达式（如 `checkStock(productId, count)`、`returnResult()`）。
- **【知识依赖】**：[序列图核心语法要素与时序分析](#51-序列图sequence-diagram核心建模要素与时序分析)。
- **【易错与自检】**：
  - *陷阱*：方法名字填错接收对象；跨越时间垂直顺序颠倒消息；
  - *自检*：调用该方法时，接收对象是否已经被创建（即处于生命线的 `<<create>>` 之后）？

---

### 作答卡 UML-SEQ-02：序列图生命线与组合片段

- **【题型识别】**：常见设问：“给出图中组合片段 (1)～(n) 的操作符名称及守卫条件。”（通常 2～4 分）。
- **【目标产出】**：组合片段关键字（`alt`, `opt`, `loop`, `par`）及方括号内的条件表达式。
- **【题干取证】**：题干中关于条件分支、循环或并发的业务语句。
- **【推理步骤】**：
  1. **互斥双分支 / 多分支（`if-else` 或 `switch`）**：
     - 特征：大框内部被一条水平虚线分割为多个操作区域，各区域带有互斥守卫条件；
     - 填入操作符：**`alt`**；
  2. **单一可选分支（单 `if`，无 `else`）**：
     - 特征：只有一个操作区域，条件满足才执行，不满足直接跳过；
     - 填入操作符：**`opt`**；
  3. **循环重复执行（`while` / `for`）**：
     - 特征：带有循环次数或重复守卫条件；
     - 填入操作符：**`loop`**；
  4. **并发并行执行**：
     - 特征：多个子区域由水平虚线隔开且同时并发执行；
     - 填入操作符：**`par`**。
- **【答案形态】**：操作符名称（如 `alt`、`loop`），守卫条件用中括号包裹（如 `[密码正确]`、`[重试次数 < 3]`）。
- **【知识依赖】**：[常用组合片段操作符速查](#52-常用组合片段操作符combined-fragments速查)。
- **【易错与自检】**：
  - *陷阱*：混淆 `alt` 与 `opt`（`alt` 是多选一互斥，`opt` 是单分支可选）；
### 作答卡 UML-SEQ-03：序列图消息与类操作接口互通作答卡

- **【题型识别】**：常见设问：“根据序列图中的交互时序，指出类 C 中应补充的方法名称” / “对照类图中的类方法，补全序列图中的消息 (1)～(n)”。（通常 3～6 分）。
- **【目标产出】**：类图中缺失的方法列表，或序列图水平消息名及参数。
- **【题干取证】**：比对题干给出的半成品类图（关注各类的操作 Operation 槽位）与序列图中的交互消息箭头。
- **【推理步骤（时序消息与类方法双向映射四步法）】**：
  1. **第 1 步：定位消息接收端所属类**：
     - 顺着水平消息箭头指向，观察箭头扎入的生命线顶部矩形框 `obj:ClassName`；
     - 接收端对象所属的 `ClassName` 就是该操作的**归属类**（谁接收消息，谁必须提供对应的方法）；
  2. **第 2 步：核对类图方法签名**：
     - 查看类图中该类是否已经列出了该方法：若已列出，序列图消息名称、大小写与形参必须与类图保持 100% 逐字一致；
     - 若类图留空，则由序列图消息直接反填回类图的操作列表；
  3. **第 3 步：题干业务动作与方法名对照**：
     - 题干叙述“系统向仓储模块发送扣减库存指令” -> 接收方为仓储模块，消息名为 `reduceStock(itemId, count)`；
  4. **第 4 步：检查返回消息（虚线）与后续调用级联**：
     - 虚线返回消息携带的数据（如 `return token`），往往作为发送方后续发起下一条消息的输入形参（如 `loginWithToken(token)`）。
- **【答案形态】**：方法名及参数（如 `verifyCredentials(username, pwd)`, `executePayment(amount)`）。
- **【知识依赖】**：[序列图核心语法要素与时序分析](#51-序列图sequence-diagram核心建模要素与时序分析)。
- **【易错与自检】**：
  - *陷阱*：误将发起调用的一方当作方法拥有的类（牢记：**箭头指向谁，方法就属于谁**！）；
  - *自检*：检查接收方类是否确实具备处理该消息的职责与数据支撑。

### 作答卡 UML-CD-06：辨析关联、聚合与组合关系

- **【题型识别】**：常见设问：“指出类 A 与类 B 之间的关系是聚合还是组合，并说明理由” / “在类图中为连线补上空心/实心菱形”。
- **【目标产出】**：关系类型（关联、聚合、组合）、图形符号（空心菱形/实心菱形），以及生命周期耦合度理由。
- **【题干取证】**：找出“整体与部分”在消亡时是否相互依存的描述。
- **【推理步骤（生命周期生死三问）】**：
  1. **第一问：是不是“整体—部分”关系？**
     - 否（只是平级引用，如客户与订单） → **普通关联 (Association)**；
  2. **第二问：当“整体”消亡时，“部分”能否脱离整体独立存在？**
     - 能（部分独立存在，弱整体部分） → **聚合 (Aggregation)**；
       - 图形：**空心菱形**（放在整体端！）；
       - 典型：`学校 ◇── 教师`、`购物车 ◇── 商品`；
  3. **第三问：当“整体”消亡时，“部分”是否同生同灭、绝对不能独立存在？**
     - 是（强整体部分，不可分割） → **组合 (Composition)**；
       - 图形：**实心菱形**（放在整体端！）；
       - 典型：`公司 ◆── 部门`、`订单 ◆── 订单明细`、`窗体 ◆── 按钮`。
- **【答案形态】**：
  ```text
  关系类型: 组合关系 (Composition)
  图形符号: 实心菱形（位于订单端）
  理由: 订单与订单明细是强整体与部分关系，订单明细离开订单无法独立存在，生命周期同生同灭。
  ```
- **【知识依赖】**：[关联、聚合与组合深度对比与判定口诀](#53-关联聚合与组合深度对比与判定)。
- **【易错与自检】**：
  - *陷阱*：菱形画在了“部分”端（**菱形必须画在“整体”端**！）；
  - *自检*：整体散了，部分还在不在？在就是空心聚合，不在就是实心组合。

## 5. 支撑知识详解（下钻专区）

### 5.1 序列图（Sequence Diagram）核心建模要素与时序分析
1. **对象与生命线（Lifeline）**：
   - 顶部矩形框：`对象名:类名` 或 `:类名`；
   - 垂直虚线：生命线，表示该对象在时间维度的存在周期；
2. **激活期 / 控制焦点（Activation Bar）**：
   - 生命线上的细长矩形条，表示对象正在占用线程或 CPU 执行操作；
3. **四类核心消息箭头规范**：
   - **同步消息（Synchronous Call）**：`──▶`（实线 + 实心三角箭头），发送方挂起等待返回；
   - **异步消息（Asynchronous Call）**：`──>`（实线 + 普通线形箭头），发送方不等待立即向下执行；
   - **返回消息（Reply Message）**：`◀--`（虚线 + 普通线形箭头），操作完成返回数据；
   - **自身调用（Self Call）**：自身激活条折回自身的嵌套小激活条。

### 5.2 常用组合片段操作符（Combined Fragments）速查
| 操作符 | 含义与执行语义 | 典型考场场景 |
|:---:|---|---|
| **`alt`** | **互斥多分支 (Alternatives)**：多个区域用水平虚线隔开，有且仅有一个区域守卫条件为真并执行 | `if-else` 判断、密码正确与错误分支 |
| **`opt`** | **单一可选 (Option)**：仅一个操作区域，条件为真执行，条件为假跳过 | 单 `if`、未登录则登录、选择附加险 |
| **`loop`** | **循环迭代 (Loop)**：在满足 `[min, max, guard]` 时重复循环执行内部序列 | 遍历购物车商品、逐个轮询设备 |
| **`par`** | **并发执行 (Parallel)**：内部多个子区域并发并行独立运行 | 多通道同时发送通知、多传感器同步采样 |

### 5.3 关联、聚合与组合深度对比与判定
| 关系类型 | UML 图元标识 | 整体与部分关系强度 | 生命周期耦合度 | 典型业务场景 |
|---|---|---|---|---|
| **关联 (Association)** | 实线带/不带普通箭头 | 静态引用，知晓关系 | 完全无生命周期约束 | 客户与商品、员工与公司 |
| **聚合 (Aggregation)** | **空心菱形**（位于整体端） | **弱“整体—部分”** | **部分可以脱离整体独立存在** | 学校与教师、购物车与商品 |
| **组合 (Composition)** | **实心菱形**（位于整体端） | **强“整体—部分”** | **同生同灭，部分不能脱离整体独立存在** | 订单与订单明细、公司与部门、窗体与控件 |

> **考场速记口诀**：
> **“整体消亡部分死，实心组合不可分；整体散了部分在，空心聚合可独立；菱形统一放整体，箭头始终指被调。”**

## 1. 状态图题型识别与通用破题流程

### 1.1 试题识别与题面结构
- **试题位置**：下午试题三（必答题，满分 15 分，考查对象动态生命周期）。
- **题面两件套**：
  1. **实体生命周期状态描述**：详细阐述单个对象在其生命周期内经历的各个阶段（如自动售货机投币出货、电商订单备货发货、航空会员积分升级）；
  2. **状态机图（半成品）**：
     - 初态（实心黑圆 `●`）与终态（同心实心圆 `◉`）；
     - 圆角矩形（状态 `S1～Sn`，内含状态名）；
     - 迁移箭线（标注格式：`事件 [守卫条件] / 动作`）。

### 1.2 考场四步快速解题流水线
```text
第 1 步：圈持续性词，定状态名 → 圈出形容词或名词短语（如“待付款”、“空闲”、“备货中”），填入圆角矩形
  ↓
第 2 步：抓瞬时动词，定触发事件 → 寻找引起状态跃迁的外来输入或时钟信号（如“投币”、“点击支付”）
  ↓
第 3 步：提取条件动作，规范语法 → 方括号包守卫条件 [Guard]，斜杠后紧跟原子动作 /Action
  ↓
第 4 步：排查死胡同，验证闭环自洽 → 检查各分支是否有退回路径（如投币不足退款、支付失败取消）
```

## 2. 状态图核心作答卡

---

### 作答卡 UML-ST-01：状态机要素与状态识别

- **【题型识别】**：常见设问：“使用说明中的词语，给出图中的状态 S1～Sn 的名称。”（通常 4～8 分）。
- **【目标产出】**：状态编号对应的名称列表（如 `S1: 空闲 (Idle); S2: 待付款; S3: 备货中; S4: 已发货`）。
- **【题干取证】**：
  - 寻找描述对象处于**某一持续性时间段、等待某事发生或持续执行某活动**的语句；
  - 核心词性：**名词短语或形容词短语**（如“挂起”、“就绪”、“已出票”、“银卡会员”）。
- **【推理步骤】**：
  1. 观察初态 `●` 后的第一个状态：通常是“初始化”、“就绪”或“空闲 (Idle)”；
  2. 观察终态 `◉` 前的最后一个状态：通常是“已完成”、“已取消”或“已销毁”；
  3. 观察中间状态的迁移路径：
     - 若经过“支付成功”事件进入该状态，随后执行“发货”动作离开，则该状态必定是“**备货中 (Preparing)**”；
  4. 绝不将瞬时动作（如“用户投币”）填为状态名。
- **【答案形态】**：规范英文或中文状态名（如 `Preparing`, `待出票`）。
- **【知识依赖】**：[状态与事件严格辨析](#51-状态机图的核心要素与辨析规范)。
- **【易错与自检】**：
  - *陷阱*：将动词事件（如“支付费用”、“按下按钮”）误填为状态名；
  - *自检*：这个词能不能用“该对象正处于……状态”造句？能造通才是合法状态名！

---

### 作答卡 UML-ST-02：反应型与事务型状态流转

- **【题型识别】**：常见设问：“补充图中迁移箭线上的事件、守卫条件与动作 (1)～(n)。”（通常 3～6 分）。
- **【目标产出】**：严格符合规范的迁移标注字符串：`Event [Guard] / Action`。
- **【题干取证】**：题干中描述“当发生什么事情时”、“如果满足什么条件”、“系统随即执行什么操作”的复合句。
- **【推理步骤（语法拆解三步）】**：
  1. **找事件（Event）**：触发跃迁的外部信号（动词短语，如 `投币`、`超时`、`点击确认`），写在最前面，**不带任何括号**；
  2. **找守卫条件（Guard）**：触发跃迁必须满足的前提布尔判定（如“金额达到售价”、“重试次数 < 3”），**必须用方括号 `[ ]` 包裹**；
  3. **找动作（Action）**：伴随迁移立即执行的原子操作（如“弹出商品”、“找零”、“记录日志”），**必须紧跟在斜杠 `/` 之后**。
- **【答案形态】**：
  ```text
  (1) 处填: 用户投币 [金额 >= 售价] / 推出商品
  (2) 处填: 超时 [取消订单] / 释放库存并退款
  ```
- **【知识依赖】**：[状态迁移语法要素与两类经典业务流转](#52-两类经典状态机业务流转模型)。
- **【易错与自检】**：
  - *陷阱*：守卫条件漏掉方括号 `[]`；动作漏写斜杠 `/`；
  - *自检*：连线上的标注是否完全符合 `事件 [条件] / 动作` 语法格式？

---

### 作答卡 UML-ST-03：状态机向面向对象状态模式映射

- **【题型识别】**：常见设问：“该状态机如果使用面向对象设计模式实现，应采用哪种设计模式？指出图中的状态与类的映射关系。”（通常 2～4 分）。
- **【目标产出】**：设计模式名称（**状态模式 State Pattern**）+ 抽象状态类与具体状态子类映射列表。
- **【推理步骤】**：
  1. 识别对象状态改变导致其行为随之改变的特征 → **状态模式（State）**；
  2. 映射准则：
     - 状态机图的每个状态圆角矩形 → 映射为一个**具体状态子类**（如 `BasicState`, `SilverState`, `GoldState`）；
     - 箭线上的触发事件 → 映射为抽象状态类声明的**业务操作接口**（如 `handlePayment()`, `upgrade()`）；
     - 状态的宿主对象 → 映射为**环境上下文类（Context）**。
- **【答案形态】**：
  ```text
  设计模式: 状态模式 (State Pattern)
  映射关系:
  - 环境类 (Context): 会员账户 (MemberAccount)
  - 抽象状态类: MemberState
  - 具体状态类: BasicState (普卡), SilverState (银卡), GoldState (金卡)
  ```
- **【知识依赖】**：[状态机与状态模式双向映射](#53-状态机与面向对象状态模式state双向映射)。

---

### 作答卡 UML-ST-04：状态三要素（事件/守卫条件/动作）标注提取模板卡

- **【题型识别】**：常见设问：“根据说明，给出状态转换连线上的事件、条件与响应动作” / “写出从状态 S1 转换至 S2 的标注表达式”。（通常 3～5 分）。
- **【标准语法公式】**：
  ```text
  事件名称 [守卫条件] / 执行动作
  ```
- **【题干文本长句拆解流水线（三步提取法）】**：
  1. **找事件（Event）——“谁触发的”**：
     - 寻找句中的外部动词、时间信号或传感器脉冲（如“当顾客按下出纸键”、“计时器超时 30 秒”、“系统收到第三方支付成功回调”）；
     - 提炼为简洁的动词短语（如 `按下出纸键`、`超时`、`支付成功`），**不带任何符号**，放在最开头；
  2. **找守卫条件（Guard）——“在什么前提下才准走”**：
     - 寻找句中的“如果”、“当且仅当”、“若...满足”等条件分支（如“如果纸巾剩余数量大于0”、“若用户账户未被冻结”）；
     - 提炼为布尔判断式（如 `[纸巾剩余量 > 0]`、`[账户正常]`），**必须使用方括号 `[ ]` 严格包裹**；若无条件则省略方括号；
  3. **找动作（Action）——“伴随迁移立即干什么”**：
     - 寻找句中的“系统随之执行...”、“立即输出...”等伴随操作（如“滚轮旋转出纸一节”、“记录出纸日志并扣减积分”）；
     - 提炼为动作短语（如 `推出纸巾并扣减余额`），**必须紧跟在斜杠 `/` 之后**；若无额外操作则省略斜杠。
- **【答案形态】**：
  ```text
  标准答题范例:
  连线 1 标注: 投币 [投入总额 >= 单价] / 推出饮料并找零
  连线 2 标注: 取消交易 / 全额退币
  连线 3 标注: 超时 15 秒 [未确认订单] / 释放锁定的座位
  ```
- **【易错避坑自检】**：
  - *陷阱 1*：漏掉方括号或斜杠（如写成 `投币 (金额足够) 推出饮料`，直接扣除格式分）；
  - *陷阱 2*：把动作当成事件（事件是引发原因，动作是后续结果）；
  - *自检*：检查语法结构是否严格匹配 `Event [Guard] / Action`。

## 3. 典型真题全链路演练与真题锚点

以已验收真题 2016 年下半年试题三（自动售货机状态图与类图建模）（请在历年真题页面查看） 为例，演示从题面到标准答案的全流程：

### 3.1 题面关键信息提炼
- **业务背景**：某种出售罐装饮料的自动售货机（Vending Machine）工作过程：
  1. 顾客选择所需购买的饮料及数量；
  2. 顾客从投币口投入硬币，硬币器收集并计算价值；若金额足够且饮料库存足够，推出饮料并计算找零，顾客取走饮料与找零；若金额不足或饮料库存不足，提示继续投币或重新选择；
  3. 购买结束后清空硬币器，等待下次交易；设退币按钮退还已投硬币。
- **状态图结构**：题干说明用例“购买饮料”包含 4 个核心状态：**“空闲”状态、“准备服务”状态、“可购买”状态以及“饮料出售”状态**。图 3-2 状态图中标注了 S1～S4 四个状态框，以及状态之间的迁移事件 E1～E4。

### 3.2 逐小问推导演练
- **问题 1（识别状态 S1～S4 的名称）**：
  - **取证与推理**：
    - 初始状态：未投币且未选择时处于初始的“空闲”状态 → S1 为“空闲”；
    - 顾客投入硬币后，机器进入“准备服务”状态，等待进一步选择或投币 → S2 为“准备服务”；
    - 当顾客所投硬币达到或超过饮料售价时，系统迁移至“可购买”状态 → S4 为“可购买”；
    - 确认饮料库存充足并出货时，机器进入“饮料出售”状态 → S3 为“饮料出售”。
  - **答案**：`S1: 空闲; S2: 准备服务; S3: 饮料出售; S4: 可购买`（套用 [作答卡 UML-ST-01](#作答卡-uml-st-01状态机要素与状态识别)）。
- **问题 2（识别迁移事件、守卫条件与动作 E1～E4）**：
  - **取证与推理**：
    - E2 触发从“准备服务”到“可购买”的迁移，对应条件为顾客选择饮料且投入金额足够 → E2 为 `选择饮料[硬币足够购买饮料]`；
    - E1 发生在“可购买”状态下选择某种饮料时，若该饮料库存不足则退回“准备服务” → E1 为 `所选购的饮料数量不足`；
    - E3 触发从“可购买”到“饮料出售”的迁移，对应库存足够并执行推出饮料动作 → E3 为 `所选购的饮料数量足够/推出饮料`；
    - E4 是出货完成后回到“空闲”的处理动作 → E4 为 `取走饮料/找零并清空硬币器`。
  - **答案**：
    - `E1: 所选购的饮料数量不足`
    - `E2: 选择饮料[硬币足够购买饮料]`
    - `E3: 所选购的饮料数量足够/推出饮料`
    - `E4: 取走饮料/找零并清空硬币器`（套用 [作答卡 UML-ST-02](#作答卡-uml-st-02反应型与事务型状态流转)）。
- **问题 3（根据系统结构推导类名 C1～C5）**：
  - **取证与推理**：
    - 顶层系统整体为 C1（自动售货机）；
    - 售货机内部聚合了 C2 与 C3，分别对应“硬币器”与“饮料储存仓”；
    - 对应管理的实体对象分别为 C4（硬币）与 C5（饮料）。
  - **答案**：`C1: 自动售货机; C2: 硬币器（或 饮料储存仓）; C3: 饮料储存仓（或 硬币器）; C4: 硬币（或 饮料）; C5: 饮料（或 硬币）`。

## 5. 支撑知识详解（下钻专区）

### 5.1 状态机图的核心要素与辨析规范
```text
[初态 ●] ──> [状态 1] ──事件 [守卫条件] / 动作──> [状态 2] ──> [终态 ◉]
```

| 要素类型 | 识别标志与词性 | 实例表述 | 考场书写规范 |
|---|---|---|---|
| **状态 (State)** | 对象所处的持续性阶段（形容词/名词） | “空闲 (Idle)”、“待付款”、“出货中” | 填入圆角矩形框内 |
| **事件 (Event)** | 瞬时触发的外部输入或信号（动词短语） | “顾客投币”、“用户点击支付”、“超时” | 标注在连线上，无括号 |
| **守卫条件 (Guard)** | 触发迁移必须满足的布尔判定 | `[硬币数量足够]`、`[库存 > 0]` | **必须用方括号 `[ ]` 包裹** |
| **动作 (Action)** | 伴随状态迁移立即执行的原子操作 | `/ 推出商品`、`/ 计算找零`、`/ 发送短信` | **必须紧跟在斜杠 `/` 之后** |

### 5.2 两类经典状态机业务流转模型
1. **交互反应型系统（以自动售货机为例）**：
   - 强调外部事件输入与硬件动作交互：
   - `[空闲 Idle]` ──投币 / 累加金额──> `[已投币]` ──选择商品 [金额 >= 售价] / 推出商品并找零──> `[出货中]` ──出货完成──> `[空闲 Idle]`；
   - 异常路径：`[已投币]` ──按下退币按钮 / 全额退款──> `[空闲 Idle]`。
2. **业务事务全生命周期流转（以订单状态机为例）**：
   - 强调业务对象自创建直至完结的单向/分支流转：
   - `[创建订单]` ──> `S1: 挂起 (Pending)` ──支付成功──> `S2: 备货 (Preparing)` ──发货──> `S3: 已发货 (Shipped)` ──确认收货──> `S4: 已完成 (Completed)`；
   - 异常路径：`S1: 挂起` ──超时未支付 / 释放库存──> `S5: 已取消 (Cancelled)`。

### 5.3 状态机与面向对象状态模式（State）双向映射
- **映射对照表**：
  | 状态机概念 | 面向对象状态模式（State Pattern）对应角色 |
  |---|---|
  | 拥有状态的实体对象 | **环境上下文类 (Context)** |
  | 状态迁移公共契约 | **抽象状态类 / 接口 (State)** |
  | 图中具体的每个圆角矩形 | **具体状态实现类 (ConcreteState)** |
  | 连线上的触发事件 | **抽象状态类中声明的方法** |
  | 守卫条件与分支 | **方法内部的 `if/else` 阈值检查与状态切换** |

### 5.4 经典真题状态机模型复盘与题干拆解（2017-05 电动玩具与 2016-11 自动售货机）

软考真题试题三对状态机的考查，主要集中在以下两大经典领域模型：

#### 1. 自动售货机状态流转模型 (2016-11 真题)
- **四大核心状态**：
  - `S1: 空闲 (Idle)`：售货机通电就绪，未收到投币信号；
  - `S2: 准备服务 (Ready)`：顾客投入第一枚硬币，系统启动计费流程；
  - `S3: 可购买 (Purchasable)`：累计投入金额达到所选饮料单价且该饮料有库存；
  - `S4: 出售中 (Dispensing)`：电机驱动出货滚轮推出饮料，计算并退出找零。
- **典型迁移三要素标注**：
  - `S1 ──投币 / 显示金额──▶ S2`
  - `S2 ──投币 [金额 >= 单价 且 库存 > 0] ──▶ S3`
  - `S3 ──确认购买 / 推出饮料并找零──▶ S4`
  - `S4 ──出货完成 / 清空硬币器──▶ S1`
  - `S2/S3 ──按下退币按钮 / 全额退款──▶ S1`

#### 2. 电动玩具避障与能源状态流转模型 (2017-05 真题)
- **四大核心状态**：
  - `待机 (Standby)`：系统通电未启动行驶任务；
  - `行进 (Moving)`：马达正转前进；
  - `避障转向 (Turning)`：红外超声波测距传感器检测到障碍；
  - `低电量告警 (LowBattery)`：电池电压低于临界值。
- **典型迁移三要素标注**：
  - `行进 ──测距脉冲 [障碍距离 <= 10cm] / 刹车并启动舵机转向──▶ 避障转向`
  - `避障转向 ──转向完成 [航向角偏差 < 5°] / 恢复前进马达──▶ 行进`
  - `任意运行态 ──电量采样 [电量 < 15%] / 发出蜂鸣警报并熄灭大灯──▶ 低电量告警`

## 2. 算法核心作答卡（小问动作驱动）

---

### 作答卡 ALG-01：识别算法设计策略

- **【题型识别】**：常见设问：“根据以上说明和 C 代码，该算法采用了 (n) 算法设计策略。”（通常 2～4 分）。
- **【目标产出】**：算法策略标准中文名称（动态规划法、分治法、回溯法、贪心法、分支限界法）。
- **【题干取证】**：
  - 观察 C 代码的主体控制结构；
  - 观察问题是否具有“最优子结构”与“重叠子问题”。
- **【推理步骤（特征速查三步法）】**：
  1. **看数据结构与控制流**：
     - 若代码维护了**一维/二维数组（如 `c[i][j]`, `dp[i]`）**，通过双重/三重嵌套 `for` 循环自底向上填表，利用已计算的子状态推导当前状态 → **动态规划法（Dynamic Programming）**；
     - 若代码采用**递归函数**，通过 `for` 循环依次尝试解空间分支，进入前有 `if (剪枝条件)`，递归调用返回后有**完全对称的撤销恢复语句**（如 `cw = cw - w[i];`） → **回溯法（Backtracking）**；
     - 若代码将规模为 n 的问题均等划分为互不相交的子问题（如二分、三分），分别递归求解并合并结果 → **分治法（Divide and Conquer）**；
     - 若代码每一步只做局部最优选择（如按单位价值排序后单向装入），绝不回溯 → **贪心法（Greedy）**；
     - 若代码使用队列（BFS）或优先队列，按广度优先遍历解空间树并利用限界函数剪枝 → **分支限界法（Branch & Bound）**。
- **【答案形态】**：必须写规范全称：`动态规划法` 或 `回溯法`（不写单字“递归”）。
- **【知识依赖】**：[五大核心算法策略对比表](#51-五大核心算法设计策略核心判定与对比)。
- **【易错与自检】**：
  - *陷阱*：将“递归”误填为策略（递归只是一种程序实现机制，其背后的策略可能是分治、回溯或 DP 备忘录）；
  - *自检*：有查表自底向上就是动态规划，有试探回退剪枝就是回溯法。

---

### 作答卡 ALG-02：状态定义与递推方程

- **【题型识别】**：常见设问：“写出求解该问题的递推状态转移方程及边界条件。”（通常 3～6 分）。
- **【目标产出】**：状态物理含义说明 + 分段数学递推公式 + 初值边界。
- **【题干取证】**：题干中对目标函数的定义（最大化价值、最小化标量乘法次数、最少编辑操作）。
- **【推理步骤】**：
  1. **定义状态变量物理意义**：
     - 背包：`dp[i][j]` 表示前 i 个物品、总重不超过 j 时的最大总价值；
     - 矩阵链乘：`m[i][j]` 表示计算矩阵子链 Aᵢ…Aⱼ 所需的最小标量乘法次数；
     - LCS 子串：`c[i][j]` 表示以 X[i] 和 Y[j] 结尾的最长公共子串长度；
  2. **分析当前阶段的决策选择**：
     - **选或不选（0-1 背包）**：
       `dp[i][j] = max(dp[i-1][j], dp[i-1][j - w[i]] + v[i])`；
     - **最优分割点枚举（区间 DP）**：
       `m[i][j] = min { m[i][k] + m[k+1][j] + p[i-1] × p[k] × p[j] }`（`i ≤ k < j`）；
     - **连续匹配中断直接归零（LCS 连续子串）**：
       若字符相等为 `c[i-1][j-1] + 1`，字符不等直接置 `0`；
  3. **明确边界初值**：`dp[0][j] = 0`，`dp[i][0] = 0`，`m[i][i] = 0`。
- **【答案形态】**：清晰分段公式，指明各变量取值范围。

### 作答卡 ALG-03：C 语言核心代码填空

- **【推理步骤（代码填空五步口诀）】**：
  1. **第 1 步：看循环找边界（数组起始是 0 还是 1）**：
     - 检查外层循环变量初始值（`i = 0` 还是 `i = 1`）；
     - 循环条件是严格小于（`i < n`）还是小于等于（`i <= n`）；

     - 若形参是 `int *bestW`，在函数内部赋值必须写 `*bestW = cw;`；

     - 回溯到达叶子结点的判断：`if (i > n) { ... return; }` 或 `if (k == n)`；
     - 分治终止条件：`if (low >= high) return a[low];`；

     - 如果是求最大值：`if (temp > max_val) { max_val = temp; }`；
     - 初始化赋初值：求最小值置极大值（`INT_MAX`），求最大值置 `0`；
  5. **第 5 步：看回溯找撤销（完全对称扣减）**：
     - 在进入递归 `backtrack(i + 1)` 之前有累加 `cw += w[i]`，递归返回后必定填完全对称的扣减：`cw -= w[i];`。
- **【答案形态】**：精准 C 语法代码（如 `dp[i-1][j]`、`cw + w[i] < bestW`、`*bestX = x`）。
- **【知识依赖】**：[C 代码填空实战避坑清单](#57-案例试题四-c-代码填空实战避坑清单)。

### 作答卡 ALG-05：回溯法递归求解框架（解向量/剪枝/恢复现场）模板卡

- **【题型识别】**：常见设问：“写出回溯算法递归终止条件” / “写出第 k 层的约束与限界剪枝条件” / “填充现场恢复语句”。（通常 4～8 分）。
- **【目标产出】**：解空间遍历框架、剪枝 `if` 条件式、镜像对称现场恢复赋值语句。
- **【通用回溯法递归 C 语言代码骨架】**：
  ```c
  void backtrack(int t) {
      if (t > n) { // 到达叶子节点（递归基准出口）
          if (cw < bestW) { // 刷新全局最优解
              bestW = cw;
              for (int i = 1; i <= n; i++) bestX[i] = x[i]; // 保存最优解向量
          }
          return;
      }
      for (int i = 0; i <= 1; i++) { // 枚举当前分支（如选0或选1）
          x[t] = i;
          if (constraint(t) && bound(t)) { // 剪枝判断：约束函数与限界函数
              cw += w[t] * x[t];           // 进入子树前：修改现场
              backtrack(t + 1);            // 递归深入下一层
              cw -= w[t] * x[t];           // 递归返回后：镜像对称恢复现场！
          }
      }
  }
  ```
- **【双重剪枝与现场恢复三大铁律】**：
  1. **可行性约束剪枝 (Constraint)**：当前局部累加代价若已超出硬性上限（如累加重量 `cw + w[t] > W`），直接剪枝；
  2. **最优性限界剪枝 (Bound)**：当前累加价值加上剩余所有物品的最大可能价值之后，仍不优于已知全局最优解 `bestV`，直接剪枝；
  3. **现场恢复绝对镜像对称**：
     - 若进入前为 `cw += w[t]; cp += p[t]; visited[t] = 1;`；
     - 递归返回后**必须逐行完全反向扣减**：`cw -= w[t]; cp -= p[t]; visited[t] = 0;`。
- **【知识依赖】**：[回溯法最小覆盖集模型](#53-回溯法backtracking题型突破与最小覆盖集)。

### 作答卡 ALG-07：算法时空复杂度分析与渐进记号速查卡

- **【题型识别】**：设问：“根据以上说明和 C 代码，该算法的时间复杂度为 (n)，空间复杂度为 (m)（用大 O 符号表示）。”（通常 2～4 分）。

- **【推理步骤】**：
  1. **看循环嵌套重数**：
     - 单层循环扫描：`O(n)`；
     - 两层嵌套循环：`O(n²)` 或 `O(m × n)`（如 0-1 背包外层物品 n，内层容量 W，为 `O(n × W)`）；
     - 三层嵌套循环（如矩阵链乘）：外层链长，中层起点，内层分割点，为 `O(n³)`；
  2. **看二叉/三叉递归与树高**：
     - 假币称重（三分分治）：树高 `log₃ n`，每层代价 `O(1)` → 时间复杂度为 `O(log₃ n)` 或 `O(log n)`；
     - 堆排序全过程：建堆为 `O(n)`，排序下滤为 `O(n log n)`，总时间复杂度为 `O(n log n)`；
  3. **空间复杂度检查**：
     - 若只使用常数个临时变量，辅助空间复杂度为 `O(1)`；
     - 若开辟了与输入规模相同的二维表 `dp[m][n]`，辅助空间复杂度为 `O(m × n)`。
- **【答案形态】**：大 O 规范写法（如 `O(n log n)`, `O(n³)`）。

## 3. 典型真题全链路演练与真题锚点

以已验收真题 2022 年上半年试题四（矩阵链乘动态规划算法）（请在历年真题页面查看） 为例，演示从题面到标准答案的全流程：

### 3.1 题面关键信息提炼
- **问题背景与递归式**：
  - 矩阵链乘问题：给定 n 个矩阵序列 A₁ × A₂ × ... × Aₙ，维数序列为 `seq` 数组，求使得总乘法运算次数最少的完全加括号方案；
  - 动态规划递归式：
    ```text
    cost[i][j] = 0                                                                           (若 i = j)
    cost[i][j] = min_{i ≤ k < j} (cost[i][k] + cost[k+1][j] + seq[i] × seq[k+1] × seq[j+1]) (若 i < j)
    ```
- **算法代码结构**：
  - 函数 `matrixChain(int n, int seq[], int cost[][MAX], int trace[][MAX])` 采用三重循环自底向上填表：
    - 外层循环链长跨度增量 `p`（从 1 到 n-1）；
    - 中层循环起始下标 `i`（从 0 到 n-p-1），计算终止下标 `j = i + p`；
    - 内层循环断开分割点 `k`（从 i 到 j-1），寻找最小乘法代价并记录最优断点 `tempTrace`。

### 3.2 逐小问推导演练
- **问题 1（C 语言核心代码填空 (1)～(4)）**：
  - **取证与推理**：
    - 空 (1)：矩阵链从第 i 个开始，跨度为 p，终止下标为 `j = i + p`（或 `i + p`）；
    - 空 (2)：内层最优断开位置枚举，根据递归式 `i ≤ k < j`，内层初值为 `k = i`，故初始候选最优分割点填 `k`；
    - 空 (3)：标量乘法代价累计，根据状态转移方程，从矩阵 i 到 j 在点 k 处断开的代价为左段最优代价、右段最优代价与当前标量乘法代价之和，填 `cost[i][k] + cost[k + 1][j] + seq[i] * seq[k + 1] * seq[j + 1]`；
    - 空 (4)：记录最优分割点到追踪表，内层循环结束后将记录的最优分割点 `tempTrace` 存入追踪表数组，填 `trace[i][j] = tempTrace`。
  - **答案**：
    - `(1) j = i + p（或 i + p）`
    - `(2) k`
    - `(3) cost[i][k] + cost[k + 1][j] + seq[i] * seq[k + 1] * seq[j + 1]`
    - `(4) trace[i][j] = tempTrace`（套用 [作答卡 ALG-03](#作答卡-alg-03c-语言核心代码填空)）。
- **问题 2（算法策略与时空复杂度判定 (5)～(6)）**：
  - **取证与推理**：
    - 该算法将问题分解为相互重叠的子问题并自底向上查表填表，属于**动态规划算法（Dynamic Programming）**；
    - 代码由外层链长增量、中层起点下标、内层最优分割点枚举三层嵌套循环组成，时间复杂度为 **`O(n³)`**（或 `O(n^3)`）。
  - **答案**：
    - `(5) 动态规划算法（Dynamic Programming）`
    - `(6) O(n³)`（套用 [作答卡 ALG-01](#作答卡-alg-01识别算法设计策略)、[作答卡 ALG-05](#作答卡-alg-05计算时空复杂度)）。
- **问题 3（算例手工推演与加括号顺序 (7)～(8)）**：
  - **取证与推理**：
    - 给定实例 n = 4，矩阵维数分别为 A₁(15×5)、A₂(5×10)、A₃(10×20)、A₄(20×25)，维数序列为 `15, 5, 10, 20, 25`；
    - 经填表推演得出最优加括号顺序为：`A1 * ((A2 * A3) * A4)`（或 `A1((A2A3)A4)`）；
    - 所需的最少乘法运算次数为 `5375`。
  - **答案**：
    - `(7) A1 * ((A2 * A3) * A4)`（或 `A1((A2A3)A4)`）
    - `(8) 5375`（套用 [作答卡 ALG-04](#作答卡-alg-04手动推演算例与状态值)）。

## 5. 支撑知识详解（下钻算法卡库）

### 5.1 五大核心算法设计策略核心判定与对比
| 算法策略 | 核心机制与特征 | 最优子结构 | 重叠子问题 | 典型试题场景 |
|---|---|:---:|:---:|---|
| **动态规划法 (DP)** | 自底向上查表或备忘录记忆，分解为重叠子问题 | 具备 | 具备 | 0-1背包、矩阵链乘、LCS、编辑距离、钢条切割 |
| **回溯法 (Backtracking)** | 深度优先搜索（DFS）解空间树，遇到死路则撤销回退 | 不一定 | 通常不强调 | n皇后、哈密尔顿回路、最小重量机器设计 |
| **分治法 (Divide & Conquer)** | 将问题均等划分为互不相交的子问题，递归求解后合并 | 具备 | 不具备（相互独立） | 假币称重、归并排序、快速排序 |
| **贪心法 (Greedy)** | 每一步做出局部最优选择，绝不回溯 | 具备 | 不强调 | 活动选择、霍夫曼编码、Dijkstra 最短路 |
| **分支限界法 (Branch & Bound)** | 广度优先（BFS）遍历解空间树，利用上/下界函数剪枝 | 具备 | 可重叠 | 0-1背包分支限界搜索 |

### 5.2 动态规划（DP）题型突破与最小覆盖集

#### (1) 0-1 背包问题（0-1 Knapsack）
- **状态转移方程**：
  - `j < w[i]` 时：`dp[i][j] = dp[i - 1][j]`
  - `j ≥ w[i]` 时：`dp[i][j] = max(dp[i - 1][j], dp[i - 1][j - w[i]] + v[i])`
- **复杂度**：时间复杂度 `O(n × W)`，空间复杂度 `O(n × W)`（滚动数组可优化为 `O(W)`）。

#### (2) 矩阵链乘问题（Matrix Chain Multiplication）
- **状态转移方程**：
  - `i = j` 时：`m[i][j] = 0`
  - `i < j` 时：`m[i][j] = min { m[i][k] + m[k + 1][j] + p[i - 1] × p[k] × p[j] }`（`i ≤ k < j`）
- **复杂度**：时间复杂度 `O(n³)`，空间复杂度 `O(n²)`。

#### (3) 最长公共子串（LCS Substring，严格连续）
- **状态转移方程**：
  - 若 `X[i - 1] == Y[j - 1]`：`c[i][j] = c[i - 1][j - 1] + 1`
  - 若 `X[i - 1] ≠ Y[j - 1]`：`c[i][j] = 0`（连续中断，直接归零！）
- **复杂度**：时间复杂度 `O(m × n)`。

#### (4) 字符串编辑距离（Edit Distance）
- **状态转移方程**：
  `dp[i][j] = min(dp[i - 1][j] + 1, dp[i][j - 1] + 1, dp[i - 1][j - 1] + cost)`（字符相同 cost=0，不同 cost=1）。
- **复杂度**：时间复杂度 `O(m × n)`。

#### (5) 钢条切割问题（Cutting Rod）
- **递推方程**：`r[n] = max { p[i] + r[n - i] }`（`1 ≤ i ≤ n`）。时间复杂度为 `O(n²)`。

#### (6) 凸多边形最优三角剖分（Optimal Polygon Triangulation）
- **同构性**：与矩阵链乘完全同构，时间复杂度 `O(n³)`。

### 5.3 回溯法（Backtracking）题型突破与最小覆盖集

#### (1) n 皇后问题（n-Queens Problem）
- **剪枝条件**：
  - 同列冲突：`x[i] == x[k]`；
  - 同对角线冲突：`abs(x[i] - x[k]) == abs(i - k)`。

#### (2) 最小重量机器设计（双约束剪枝与回溯现场恢复）
- **双重剪枝**：价格上限 `cp + c[i][j] <= cc` 且重量最优限界 `cw + w[i][j] < bestW`；
- **对称现场恢复**：递归调用后必须完全镜像执行 `cw -= w[i][j]; cp -= c[i][j];`。

#### (3) 哈密尔顿回路（Hamiltonian Circuit）
- 检查顶点相邻（`graph[x[k-1]][x[k]] == 1`）且未被访问；放置第 n 个顶点还需检查回程边（`graph[x[n-1]][x[0]] == 1`）。

#### (4) 0-1 背包问题（回溯限界法与贪心松弛上界剪枝）
- **问题描述**：n 个物品，重量 `w[i]`，价值 `v[i]`，背包容量 W。选入物品使总价值最大且总重量不超过 W。
- **解空间树**：二叉树。第 k 层向左分支表示装入第 k 个物品（`x[k] = 1`），向右分支表示不装入第 k 个物品（`x[k] = 0`）。
- **上界函数 BOUND 设计（贪心松弛）**：
  将物品按单位价值 `v[i] / w[i]` 从大到小预排序。当前已考察到第 k 个物品，累计重量为 cw，累计价值为 cp：
  - 尽量装入后续物品；当某物品无法完整装入时，允许装入其一部分（背包问题贪心松弛），计算出剩余物品的最大理论价值上界；
  - 若该理论上界 `BOUND ≤ fp`（`fp` 为当前已找到的最优解价值），则该子树不可能突破现有最优解，直接剪枝。
- **非递归 BKNAP 回溯骨架（解题核心）**：
  - 向左深入装入：`cw = cw + w[k]; cp = cp + v[k]; Y[k] = 1; k = k + 1;`
  - 叶子结点更新最优解：若 `fp < cp`，则 `fp = cp; fw = cw; X = Y;`
  - 向上剪枝回退：若 `BOUND ≤ fp`，持续回溯 `while (k != 0 && Y[k] != 1) { k = k - 1; }`；
  - 撤销选择并转向右分支：`Y[k] = 0; cw = cw - w[k]; cp = cp - v[k]; k = k + 1;`

### 5.4 分治法（Divide and Conquer）与模式匹配
- **假币检测（天平称重）**：三分递归，时间复杂度为 `O(log₃ n)`，最少称重次数为 `⌈log₃ n⌉`；
- **KMP 模式匹配与 next 数组**：利用真前后缀公共长度避免主串回溯，匹配时间为 `O(m + n)`。

### 5.5 堆排序（Heap Sort）与希尔排序（Shell Sort）
- **大顶堆性质**：`A[i] ≥ A[2i + 1]` 且 `A[i] ≥ A[2i + 2]`；
- **建堆复杂度**：严格数学证明为 **`O(n)`**（从最后一个非叶子节点 `⌊n/2⌋ - 1` 逆序下滤）；
- **排序全过程复杂度**：最好、最坏与平均时间复杂度均为 **`O(n log₂ n)`**，空间复杂度为 `O(1)`，不稳定排序；
- **希尔排序（Shell Sort）**：缩小增量排序，空间复杂度 `O(1)`，不稳定排序。

### 5.6 算法题常见时间复杂度阶数速查
| 复杂度阶数 | 中文名称 | 典型算法案例 |
|---|---|---|
| `O(1)` | 常数阶 | 数组下标寻址、哈希查找（理想状态） |
| `O(log₂ n)` / `O(log n)` | 对数阶 | 二分查找、天平三分称重 |
| `O(n)` | 线性阶 | 单层线性扫描、**大顶堆建堆过程** |
| `O(n log₂ n)` | 线性对数阶 | 堆排序全过程、归并排序、快速排序平均情况 |
| `O(n²)` | 平方阶 | 双重循环、直接插入排序、钢条切割 DP |
| `O(n³)` | 立方阶 | 矩阵链乘 DP、最优三角剖分 DP、Floyd 最短路 |
| `O(m × n)` | 双变量二项阶 | 0-1 背包 DP（n 物品, W 容量）、编辑距离 DP、LCS |
| `O(2ⁿ)` | 指数阶 | 暴力子集枚举、递归回溯最坏情况 |
| `O(n!)` | 阶乘阶 | 旅行商问题（TSP）暴力全排列 |

### 5.7 案例试题四 C 代码填空实战避坑清单
1. **0-indexed vs 1-indexed**：严格核实数组是从 0 开始还是从 1 开始，循环条件是 `< n` 还是 `≤ n`；
2. **指针解引用**：形参为指针时，赋值必须加 `*`（如 `*bestW = cw`）；数值交换必须传地址 `&x, &y`；
3. **递归基与退出条件**：进入递归前必须检查递归终止条件，防止无限递归栈溢出；
4. **查表初值与偏移**：求最小值初始置 `INT_MAX`，求最大值置 `0`；查表偏移量注意减 1；
5. **回溯状态完全对称撤销**：进入递归前如何累加，递归返回后必须完全镜像扣减。
